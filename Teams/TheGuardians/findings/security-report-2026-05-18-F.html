1. Executive Summary

Overall Grade: F — Triggered automatically by confirmed live exploitation of all four critical red-team objectives. The application has zero authentication or authorization on every endpoint, enabling any anonymous caller to bypass the entire state machine, inject arbitrary data, enumerate the full dataset, and cause permanent denial-of-service conditions. The compliance pass rate is 28% (5/18 controls). This application must not be exposed to any non-isolated network in its current state.

Top 3 Risks:

  1. No Authentication (Critical, Confirmed): Every API endpoint — including state transitions, approvals, rejections, and dispatch — is reachable by any anonymous HTTP client. This is the root finding from which all other exploits derive their feasibility.
  2. State Machine Bypass via Fast-Track Override (Critical, Confirmed): The POST /api/work-items/:id/route endpoint accepts an overrideRoute: "fast-track" field with no role check, allowing any caller to promote any work item directly from backlog to approved, skipping the entire assessment pod.
  3. Intake Webhook Enum Injection (Critical, Confirmed): The Zendesk and automated intake endpoints accept arbitrary strings for type and priority fields with no enum validation or HMAC signature verification, allowing creation of corrupted work items and Prometheus label pollution.

Full API Requires Zero Authentication
PEN-001RED-001COMP-001 CriticalConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer, compliance-auditor 📂 Source/Backend/src/app.ts (all routes)
Description

app.ts mounts all routers with no authentication middleware whatsoever. There are no JWT checks, no session guards, no API key validation, and no RBAC anywhere in the codebase. The red team confirmed: POST /api/work-items with no Authorization header returns HTTP 201; GET /metrics returns HTTP 200. Every endpoint — create, update, delete, approve, reject, dispatch — is accessible to any anonymous client.

Evidence (Red Team)

HTTP 201/200 from all endpoints with zero credentials. GET /metrics, GET /health, and all /api/* routes confirmed unauthenticated.

Remediation: Add JWT or API-key authentication middleware in app.ts applied before all route groups. GET /health may remain public. Protect /metrics with a bearer token or bind it to a separate internal port. Frameworks: express-jwt, passport-jwt. Controls satisfied: SOC2 CC6.1, CC6.2; OWASP-ASVS V2.1.1, V4.2.1.
Fast-Track Override Bypasses Entire State Machine
PEN-002RED-002 CriticalConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer 📂 Source/Backend/src/routes/workflow.ts:39-64 · Source/Backend/src/services/router.ts:66-88
Description

POST /api/work-items/:id/route accepts overrideRoute: "fast-track" in the request body. When present, classifyRoute() in router.ts returns targetStatus = WorkItemStatus.Approved unconditionally with no role check. Any item in backlog status can be instantly promoted to approved, bypassing proposed → reviewing → assessment-pod.

Exploit Chain (Red Team — RED-002)
POST /api/work-items          → {id: "8d570e8f...", status: "backlog"}   [WI-003, type: feature]
POST /api/work-items/8d570e8f.../route  {"overrideRoute":"fast-track"}
→ status: "approved"  (backlog → routing → approved; skips proposed/reviewing/assessment)
POST /api/work-items/8d570e8f.../dispatch
→ status: "in-progress", assignedTeam: "TheATeam"
Result: feature-type item reached in-progress in 3 unauthenticated requests.
Remediation: Remove overrideRoute from the public API entirely, or gate it behind an elevated role check (e.g., role: "admin") enforced at the route middleware layer before the service call. The check must occur server-side before classifyRoute() is invoked.
Intake Webhook Enum Injection & No Signature Verification
PEN-003RED-003COMP-013 CriticalConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer, compliance-auditor 📂 Source/Backend/src/routes/intake.ts:11-55
Description

Both intake endpoints (POST /api/intake/zendesk, POST /api/intake/automated) are unauthenticated, lack HMAC signature verification, and pass type and priority fields directly to store.createWorkItem() with no enum validation. By contrast, POST /api/work-items validates enums. Injected values persist in the store, corrupt routing logic, and pollute Prometheus metric labels.

Evidence (Red Team — RED-003)
POST /api/intake/zendesk  {"title":"Injected","description":"...","type":"ADMIN_OVERRIDE","priority":"CRITICAL_OVERRIDE"}
→ HTTP 201  — WI-006 created with type:"ADMIN_OVERRIDE", priority:"CRITICAL_OVERRIDE"

GET /metrics
→ workflow_items_created_total{source="zendesk",type="ADMIN_OVERRIDE"} 1
   Injected labels confirmed in Prometheus telemetry.
Remediation: (1) Apply the same enum validation in intake.ts as in workItems.ts: check Object.values(WorkItemType).includes(body.type). (2) Add HMAC-SHA256 signature verification middleware for the Zendesk endpoint using process.env.ZENDESK_WEBHOOK_SECRET. Reject unsigned requests with 401. Controls satisfied: SOC2 CC8.1; OWASP-ASVS V13.2.6.

Cascade Dispatch via Unauthenticated Blocker Rejection
PEN-004RED-004 HighConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer 📂 Source/Backend/src/routes/workflow.ts:144-208 · Source/Backend/src/services/dependency.ts:251-315

When a blocker item is rejected, onItemResolved() automatically dispatches any dependent items in Approved status with no remaining blockers. Because the reject endpoint is unauthenticated, an attacker can engineer: (1) create blocker B, (2) create target A with B as blocker, (3) fast-track A to approved, (4) route B to proposed, (5) reject B → A auto-dispatches to a team without human authorization.

Remediation: onItemResolved() should require explicit re-approval before auto-dispatching, or emit a high-severity audit event requiring operator acknowledgement. The reject endpoint must also be protected by authentication (see COMP-001).
Unbounded Pagination — Full Dataset Enumeration in One Request
PEN-005RED-006COMP-007 HighConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer, compliance-auditor 📂 Source/Backend/src/routes/workItems.ts:68-75 · routes/dashboard.ts:17-18

GET /api/work-items?limit=999999999 returns all 19 items in one unauthenticated response. limit=-1 returns all-except-last (JavaScript slice(0,-1) behavior). Same flaw confirmed in GET /api/dashboard/activity (66 entries returned). Red team confirmed all 4 pagination objectives achieved.

Remediation: const limit = Math.min(Math.max(parseInt(req.query.limit as string, 10) || 20, 1), 100); in both routes. Document the cap in the API contract.
Soft-Deleted Blocker Causes Permanent Dispatch Denial-of-Service
PEN-006RED-005 HighConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer 📂 Source/Backend/src/services/dependency.ts:64-75 · store/workItemStore.ts:23-26

findById() returns undefined for soft-deleted items. computeHasUnresolvedBlockers() treats undefined as unresolved. Dependency links are not cleaned up on deletion. A victim item with a stale link to a deleted blocker permanently returns 400 on POST /dispatch, with no automated resolution. Red team confirmed WI-013 is permanently blocked after WI-014 soft-deletion.

Remediation: On soft-delete of an item, cascade-remove all stale dependency links in items that list it as a blocker. Alternatively, treat findById() === undefined (deleted) as resolved in computeHasUnresolvedBlockers().

PEN-007RED-009COMP-009 HighConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer, compliance-auditor 📂 Source/Backend/src/app.ts:34-37 · src/metrics.ts

GET /metrics requires no authentication and exposes workflow throughput counters (creation volume by source/type, routing decisions, approval rates, dispatch team names), default Node.js metrics (heap, CPU, GC, uptime), and — after RED-003 — injected enum label values that confirm successful injection attacks. No Role-Based Access Control (RBAC)
COMP-002 HighTheoretical
📡 Specialists: compliance-auditor 📂 Source/Backend/src/routes/ (all route files)

Even after authentication is added (COMP-001), there are zero role or permission checks anywhere. Any authenticated user would be able to perform every action — including sensitive state transitions (/approve, /reject, /dispatch) and delete operations. Controls failed: SOC2 CC6.3, OWASP-ASVS V4.1.1, V4.2.1.

Remediation: Define roles (operator, reviewer, admin) in JWT claims. Add authorize(role) middleware to each route group. Apply least-privilege: GET to all authenticated users; state-transition routes to reviewer+; dispatch to admin only.
No HTTP Security Headers (Missing Helmet)
COMP-003 HighTheoretical
📡 Specialists: compliance-auditor, static-analyzer 📂 Source/Backend/src/app.ts · Source/Frontend/vite.config.ts

Neither helmet nor any security-header middleware appears in package.json or app.ts. API responses carry no X-Content-Type-Options, X-Frame-Options, Strict-Transport-Security, Content-Security-Policy, or X-XSS-Protection headers. Controls failed: OWASP-ASVS V14.4.1, V14.4.2, V14.4.3.

Remediation: npm install helmet; add app.use(helmet()) as the first middleware in app.ts. One line, immediate win. For HSTS: helmet.hsts({ maxAge: 31536000 }).
No Rate Limiting on Any Endpoint
COMP-005 HighTheoretical
📡 Specialists: compliance-auditor, static-analyzer 📂 Source/Backend/src/app.ts

No rate-limiting middleware is present. All endpoints — including the intake webhooks and state-transition routes — accept unlimited requests per second. This enables denial-of-service via write amplification against the in-memory store, and credential-stuffing attacks once authentication is added. Controls failed: OWASP-ASVS V2.2.1, SOC2 CC6.1.

Remediation: npm install express-rate-limit; apply a global limiter (100 req/min per IP) and a stricter limiter on intake routes (10 req/min per IP).

Assessment Pod Hard-Rejects Items That Only Need Clarification
PEN-008RED-007 MediumConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer 📂 Source/Backend/src/services/assessment.ts:162-173

Any non-Approve pod-lead verdict (including NeedsClarification) maps to WorkItemStatus.Rejected. Items without a complexity field always receive NeedsClarification from the domain-expert, causing them to be permanently rejected rather than held for clarification. Red team confirmed WI-015 reaches rejected status despite only needing the complexity field set.

Remediation: Add a third branch in runAssessmentPod(): if (verdict === NeedsClarification) → targetStatus = WorkItemStatus.NeedsClarification. Add NeedsClarification as a valid status in the state machine and define a transition back to proposed after clarification is provided.
Stored Unsanitized Payloads in Audit Change History
PEN-012RED-008 MediumConfirmed (Live Exploit — storage)
📡 Specialists: pen-tester, red-teamer 📂 Source/Backend/src/routes/workflow.ts:114-116, 169-171

The reason field in approve/reject requests is passed verbatim to buildChangeEntry() and stored in changeHistory with no length validation or content sanitization. Red team confirmed <script>alert(document.domain)</script> is stored and returned verbatim in all subsequent GET responses. If any consumer renders entry.reason as raw HTML (admin dashboard, log viewer, webhook consumer), stored XSS executes.

Remediation: Sanitize reason at write time (strip HTML tags or HTML-encode). Enforce a maximum length of 1000 characters. Never render audit history via dangerouslySetInnerHTML. Add a test that asserts HTML tags in reason are rejected or escaped.
Body Parser Returns 500 Instead of 413 on Oversized Payload
PEN-009RED-010 MediumConfirmed (Live Exploit)
📡 Specialists: pen-tester, red-teamer 📂 Source/Backend/src/app.ts:13 · src/middleware/errorHandler.ts

app.use(express.json()) is called without an explicit limit option. Payloads >~100 KB return HTTP 500 ({"error":"Internal server error"}) instead of 413 (Payload Too Large). The body parser's PayloadTooLargeError is not handled specifically in errorHandler.ts. Also: no per-field length validation exists for title, description, or reason.

Remediation: Set app.use(express.json({ limit: '50kb' })) explicitly. Add a PayloadTooLargeError handler in errorHandler.ts returning HTTP 413. Add max-length validation: title ≤ 255 chars, description ≤ 5000 chars, reason ≤ 1000 chars.
No CORS Policy Configured
PEN-010COMP-004 MediumTheoretical
📡 Specialists: pen-tester, compliance-auditor 📂 Source/Backend/src/app.ts

No CORS middleware is configured. While the current absence of CORS headers is safer than a wildcard Access-Control-Allow-Origin: *, the lack of an explicit policy means any future naive addition of CORS headers could expose all endpoints to cross-origin exploitation. Controls failed: OWASP-ASVS V14.4.6.

Remediation: npm install cors @types/cors; app.use(cors({ origin: process.env.ALLOWED_ORIGINS?.split(',') })) with an explicit allowlist. Default to deny-all except known origins.
No TLS / HTTPS Enforcement
COMP-010 MediumTheoretical
📡 Specialists: compliance-auditor 📂 Source/Backend/src/app.ts · Source/Frontend/src/api/client.ts

The backend starts a plain HTTP server. There is no HTTPS enforcement, no HSTS header, and no redirect from HTTP to HTTPS. If deployed without a TLS-terminating reverse proxy, all traffic — including credentials once auth is added — is transmitted in plaintext. Controls failed: OWASP-ASVS V9.1.1, SOC2 CC6.1.

Remediation: Document and enforce that the app must only be deployed behind a TLS-terminating reverse proxy. Add an env-var check on startup that warns loudly if BEHIND_TLS_PROXY is not set. Add HSTS via helmet.hsts().
No Hard-Delete / GDPR Right to Erasure
COMP-011 MediumTheoretical
📡 Specialists: compliance-auditor 📂 Source/Backend/src/store/workItemStore.ts:78

Only a soft-delete mechanism exists. Work items (including title, description, and changeHistory entries that may contain user-supplied PII) remain in memory indefinitely. No endpoint or mechanism exists to perform a hard delete, violating GDPR Article 17 Right to Erasure.

Remediation: Add a hardDelete(id) function to the store. Expose as an admin-only endpoint. Ensure changeHistory entries referencing the deleted item are also purged. Add to the data retention policy documentation.
Sequential Predictable DocIDs — Enumeration Oracle
PEN-011 MediumTheoretical
📡 Specialists: pen-tester 📂 Source/Backend/src/utils/id.ts:12-15

Work items receive sequentially incrementing docId values (WI-001, WI-002, …) via a module-level counter. Any observer can infer total items ever created and creation activity from a single response. Additionally, server restarts reset the counter, creating docId collisions with prior items. Combined with zero auth, this leaks operational throughput.

Remediation: Replace the sequential counter with a random or time-based prefix (e.g., WI-{timestamp-hash}). Persist the counter if restarts should not cause collisions.
Dockerfile Runs as Root (portal/Dockerfile)
SAST-001 MediumTheoretical
📡 Specialists: static-analyzer 📂 portal/Dockerfile

The portal Dockerfile has no USER directive. The container process runs as root (UID 0). If the container is compromised, the attacker has full root access within the container and potential host breakout depending on the container runtime configuration. CWE-250.

Remediation: Add RUN addgroup -S appgroup && adduser -S appuser -G appgroup and USER appuser before the ENTRYPOINT/CMD in portal/Dockerfile.
Vite Dev Server Binds to 0.0.0.0 in Docker
SAST-002 MediumTheoretical
📡 Specialists: static-analyzer 📂 portal/Dockerfile (CMD)

The Dockerfile CMD runs the Vite dev server with --host 0.0.0.0, exposing the dev server on all network interfaces inside the container. Vite dev servers are not designed for production and lack security hardening. If this container is reachable from an external network, it exposes internal build artifacts. CWE-923.

Remediation: For production, build to a static bundle and serve via nginx. For development-only containers, restrict host network exposure via Docker network policies. Never bind dev servers to 0.0.0.0 in production or shared environments.
iframe Missing sandbox Attribute (DebugPortalPage)
SAST-003 MediumTheoretical
📡 Specialists: static-analyzer 📂 Source/Frontend/src/pages/DebugPortalPage.tsx

The <iframe> embedding the debug portal URL does not include a sandbox attribute. Without it, the iframe content can execute scripts, navigate the top-level page, and access storage, potentially enabling clickjacking or cross-frame scripting. CWE-1021.

Remediation: Add sandbox="allow-scripts allow-same-origin" (or a more restrictive set) to the iframe element. Evaluate whether allow-same-origin is required for the portal's functionality.
Raw Exception Messages Returned to Clients in Workflow Routes
SAST-004 MediumTheoretical
📡 Specialists: static-analyzer 📂 Source/Backend/src/routes/workflow.ts (500 handlers)

Some 500 error handlers in workflow.ts return raw exception messages (e.g., err.message) to the client rather than the sanitized "Internal server error" string used by the central errorHandler.ts. This can leak internal function names, file paths, and library versions to attackers. CWE-209.

Remediation: Remove all inline 500 handlers that return err.message and let errors propagate to the central errorHandler.ts middleware, which already returns the safe generic message. Add a lint rule to prohibit res.status(500).json({ error: err.message }) patterns.

Stack Traces Logged at Server Level (Production Risk)
COMP-012 LowTheoretical
📡 Specialists: compliance-auditor 📂 Source/Backend/src/middleware/errorHandler.ts:6

logger.error({ ..., stack: err.stack }) logs full stack traces. Stack traces are correctly not sent to clients. Unimplemented /api/search Endpoint — Future Attack Surface
PEN-013 LowTheoretical
📡 Specialists: pen-tester 📂 Source/Backend/tests/routes/search.test.ts · Source/Frontend/src/api/client.ts:101-105

The frontend calls GET /api/search?q= but the endpoint is not registered in app.ts (returns 404). When implemented, the q parameter will be used for full-text search.
