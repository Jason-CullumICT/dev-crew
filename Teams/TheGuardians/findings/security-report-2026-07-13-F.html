Top 3 Risks

  1. Zero authentication/authorization (CRIT-001): Every one of 18 API endpoints — including approve, reject, dispatch, and delete — is callable by any anonymous HTTP client. Confirmed live exploitation achieved full workflow state-machine bypass in three requests.
  2. Webhook spoofing + enum injection (CRIT-002): Intake endpoints accept payloads from any caller with no HMAC verification and no enum validation. Confirmed live: arbitrary type/priority strings persisted to the system and appeared in the dashboard and Prometheus metrics.
  3. Mass enumeration + bulk IDOR delete (HIGH-001): GET /api/work-items?limit=999999 dumps the entire dataset in one unauthenticated request. Combined with the unauthenticated DELETE endpoint, 86% of all work items were wiped in a single automated pass during the red team exercise.

Root Cause

Eight of ten confirmed exploit chains share a single missing control: no authentication middleware in app.ts. Adding JWT verification globally closes the primary attack surface for CRIT-001, HIGH-001, HIGH-002, HIGH-003, and the unauthenticated vector of CRIT-002. The remaining issues require targeted individual fixes (HMAC validation, enum validation, overrideRoute guard, dependency logic fix, error message sanitization).

🔴 Critical — Confirmed Live Exploit
CRIT-001

Full Workflow Takeover — Zero Authentication + State Machine Bypass

Critical Confirmed (Live)

Specialists static-analyzer · pen-tester · red-teamer

Source IDs SAST-01 · PEN-001 · PEN-003 · RED-001 · RED-010

OWASP A01: Broken Access Control · A07: Identification and Authentication Failures  |  CWE CWE-306, CWE-862

Objective Breached "Bypass work item state machine to reach an invalid status"

Description
The Express application (app.ts) registers zero authentication or authorization middleware. All 18 endpoints — including destructive state-machine transitions (/approve, /dispatch, /route) and DELETE — are reachable by any unauthenticated HTTP client. Additionally, the /route endpoint passes body.overrideRoute directly to routeWorkItem() without a privilege check or enum validation — any truthy string skips the 4-role assessment pod and promotes an item to approved status with assessments=[]. Arbitrary strings also corrupt the item.route field permanently.

Confirmed Evidence (RED-001)
WI-001 (UUID 9513fe57-6491-422e-9e93-cee88a9ab370) traversed backlog → approved → in-progress via three unauthenticated HTTP calls: POST /api/work-items, POST /:id/route {"overrideRoute":"fast-track"}, POST /:id/dispatch {"team":"TheATeam"}. assessments=[] confirms no assessment pod ran. Change history records "reason":"Fast-tracked: bypasses assessment pod". RED-010 additionally confirmed arbitrary string route field corruption via {"overrideRoute":"ANYTHING_TRUTHY_ATTACKER_CONTROLS"}.

Remediation

  • Add JWT bearer verification middleware globally in app.ts before any route registration.
  • Add RBAC: only pod_lead role may supply overrideRoute.
  • Validate overrideRoute against WorkItemRoute enum — reject non-enum values with HTTP 422.
  • Emit a structured audit event for every overrideRoute usage, including actor identity.
CRIT-002

Webhook Spoofing + Enum Injection via Unauthenticated Intake Endpoints

Critical Confirmed (Live)

Specialists static-analyzer · pen-tester · red-teamer

Source IDs SAST-02 · SAST-03 · PEN-002 · RED-005

OWASP A07: Auth Failures · A08: Software and Data Integrity Failures  |  CWE CWE-306, CWE-345, CWE-20

Objective Breached "Submit a malformed assessment verdict that bypasses routing logic"

Description
POST /api/intake/zendesk and /api/intake/automated perform no HMAC-SHA256 signature verification (Zendesk signs payloads with X-Zendesk-Webhook-Signature; this is never read). Additionally, type and priority fields from webhook bodies are passed through without enum membership checks before store.createWorkItem() — the main CRUD route validates these correctly; the intake routes do not. Arbitrary strings are stored, appear in dashboard priorityCounts, corrupt assessment switch-cases, and create unbounded Prometheus label cardinality.

Confirmed Evidence (RED-005)
WI-012 created with source=zendesk, type="malicious_type", priority="ultra-critical". WI-013 created with type="PWNED", priority="CRITICAL_OVERRIDE". Both surfaced in GET /api/work-items and dashboard/summary.priorityCounts. Prometheus recorded workflow_items_created_total{source="zendesk",type="malicious_type"} 1.

Remediation

  • Verify X-Zendesk-Webhook-Signature header with HMAC-SHA256 against a shared secret from env vars before processing any zendesk body. Reject with HTTP 401 on failure.
  • Validate type against Object.values(WorkItemType) and priority against Object.values(WorkItemPriority) in both intake routes — return HTTP 422 on invalid values.
  • Mirror the validation pattern from workItems.ts:29-40.
🟠 High
HIGH-001

Mass Data Enumeration + Bulk Unauthenticated IDOR Delete

High Confirmed (Live)

Specialists static-analyzer · pen-tester · red-teamer

Source IDs SAST-09 · PEN-004 · PEN-006 · RED-002

OWASP A01: Broken Access Control  |  CWE CWE-400, CWE-639

Objective Breached "Enumerate all work items without pagination limit enforcement"

Description
GET /api/work-items?limit=999999 returns all items in a single response — no server-side cap enforced. DELETE /api/work-items/:id performs no authorization check. UUIDs harvested from the list endpoint enable bulk deletion of the entire dataset.

Confirmed Evidence (RED-002)
data.length == total (7) confirmed on limit=999999. 6 of 7 items soft-deleted via sequential DELETE calls without credentials. GET /api/dashboard/activity?limit=999999 dumped 35 change-history records.

Remediation

  • const safeLimit = Math.min(parseInt(req.query.limit, 10), 100); in workItems.ts and dashboard.ts.
  • Return HTTP 400 for non-numeric or negative limit values.
  • Require authentication + ownership check on the DELETE endpoint.
HIGH-002

Cascade Auto-Dispatch via Unauthenticated Blocker Rejection

High Confirmed (Live)

Specialists pen-tester · red-teamer

Source IDs PEN-007 · RED-003

OWASP A04: Insecure Design  |  CWE CWE-841

Description
DISPATCH_TRIGGER_STATUSES includes Rejected. Rejecting a work item triggers onItemResolved() which auto-dispatches any Approved dependents — bypassing the manual dispatch step. A rejected blocker (failed quality review) causes its dependents to be dispatched to a team without human authorization.

Confirmed Evidence (RED-003)
Rejecting Item B caused Item A (Approved, blocked by B) to auto-dispatch: status=in-progress, assignedTeam=TheFixer. Change history recorded agent='cascade-dispatcher' with no human dispatch action.

Remediation

  • Remove Rejected from DISPATCH_TRIGGER_STATUSES (keep only Completed).
  • When a blocker is rejected, flag dependents as requires_reapproval — require explicit re-approval before dispatch.
HIGH-003

Permanent Dispatch Freeze via Soft-Deleted Blocker (DoS)

High Confirmed (Live)

Specialists pen-tester · red-teamer

Source IDs PEN-008 · RED-004

OWASP A04: Insecure Design  |  CWE CWE-404, CWE-834

Description
computeHasUnresolvedBlockers() in dependency.ts:64-75 treats store.findById()→undefined (soft-deleted item) as an unresolved blocker. Soft-deleting any in-flight blocker permanently freezes all its dependents: computeHasUnresolvedBlockers always returns true, and dispatch fails forever with "Cannot dispatch: work item has unresolved blocking dependencies."

Confirmed Evidence (RED-004)
Item C (Approved, blocked by Item D) permanently stuck after DELETE /api/work-items/:D. POST /api/work-items/:C/dispatch returned HTTP 400 indefinitely. GET /api/work-items/:C/ready showed ready=false with dead dependency link in unresolvedBlockers.

Remediation

  • Change condition in dependency.ts:64: if (!blocker || !RESOLVED_STATUSES.includes(blocker.status)) → if (blocker && !RESOLVED_STATUSES.includes(blocker.status))
  • Auto-remove or tombstone dependency links when a blocker is soft-deleted.
HIGH-004

Internal Error Messages Leaked to HTTP Clients

High Theoretical

Specialists static-analyzer

Source IDs SAST-04

OWASP A05: Security Misconfiguration  |  CWE CWE-209

Description
All seven workflow action endpoints (/route, /assess, /approve, /reject, /dispatch, /dependencies, /ready) send raw err.message from caught exceptions back to the HTTP client as JSON. This exposes internal store state, item IDs, dependency graph messages, and error conditions to any caller. The global errorHandler middleware correctly sanitizes 500s — the vulnerability is in the per-route catch blocks in workflow.ts which bypass it.

Affected Files
Source/Backend/src/routes/workflow.ts — catch blocks at lines 60–62, 87–89, 138–140, 205–207, 292–294, 331–333, 368–370.

Remediation

  • In each catch block: replace res.status(500).json({ error: message }) with res.status(500).json({ error: 'Internal server error' }).
  • Log the full error (message + stack) server-side only.

MED-001

NaN / Invalid Pagination Parameters Cause Misleading Responses

Medium Confirmed (Partial)

Source IDs PEN-005 · RED-006  |  CWE CWE-20

limit=-1 confirmed to silently drop the last record (slice(0,-1)). limit=0 returns all items. page=NaN returns empty results on dashboard endpoint. Remediation: validate and clamp: const safeLimit = (isNaN(l) || l < 1) ? 20 : Math.min(l, 100).

MED-002

Prometheus /metrics Exposed Without Authentication + Framework Disclosure

Medium Confirmed (Live)

Source IDs SAST-05 · PEN-009 · RED-007  |  CWE CWE-200

Confirmed live: 120MB RSS, 0.898s CPU, p99 event loop lag=11ms, all workflow counters exposed. X-Powered-By: Express header present on all responses. Remediation: restrict /metrics to internal network or add bearer token check; app.disable('x-powered-by').

MED-003

NeedsClarification Verdict Silently Mapped to Rejected Status

Medium Confirmed (Live)

Source IDs PEN-011 · RED-009  |  CWE CWE-710

runAssessmentPod() uses a binary if/else — NeedsClarification maps to Rejected. Confirmed live: feature item without complexity was rejected with verdict=needs-clarification. Attackers can repeatedly cycle items through reject→backlog to prevent approval. Remediation: add WorkItemStatus.NeedsClarification and handle all three verdict enum values explicitly.

MED-004

No CORS Policy — Missing Access-Control Headers

Medium Confirmed (Live)

Source IDs SAST-06 · PEN-012  |  CWE CWE-942

No Access-Control-Allow-Origin header on any response. Confirmed absent. Remediation: npm install cors; app.use(cors({ origin: ['http://localhost:5173'], credentials: true })) as first middleware.

MED-005

Missing HTTP Security Headers — No Helmet, CSP, HSTS, X-Frame-Options

Medium Confirmed (Live)

Source IDs SAST-07  |  CWE CWE-693

No CSP, X-Frame-Options, HSTS, X-Content-Type-Options, or Referrer-Policy. helmet not installed. Confirmed live (RED-007: no protective headers on any response). Remediation: npm install helmet; app.use(helmet()) as first middleware.

MED-006

No Rate Limiting on Any Endpoint

Medium Theoretical

Source IDs SAST-08  |  CWE CWE-770

No express-rate-limit or equivalent middleware anywhere. Intake and workflow endpoints callable at unlimited speed. Remediation: global limiter (60 req/min) + tighter limits on /api/intake (10 req/min per IP).
