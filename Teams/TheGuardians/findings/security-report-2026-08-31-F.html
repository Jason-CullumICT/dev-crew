📋 Executive Summary
System is fully unauthenticated and actively exploitable. Every API endpoint — including privileged operations like approve, reject, dispatch, and force-approve — is publicly accessible with no credentials required. The red-team confirmed live exploits against a running instance in an ephemeral Docker environment, achieving state machine bypass, dependency gating bypass, and full dataset enumeration. The compliance pass rate of 12% (2/17 controls) reflects the near-total absence of foundational security controls.
🔴 Risk 1: No Authentication — All Endpoints Public (F-001)
Any internet client can create, read, modify, approve, reject, and delete any work item. This is the root cause enabling all other confirmed breaches. Closing this single gap has the highest security leverage of any item in this report.
🔴 Risk 2: State Machine Bypass via Force-Approve (F-002)
Confirmed live: item FR-0001 was approved with votes:[] — zero AI votes, zero human review — in 3 anonymous HTTP requests. The entire assessment pipeline can be circumvented by any caller.
🟠 Risk 3: Dependency Gating Bypass + Unbounded Pagination (F-003, F-004)
Confirmed live: blockers can be silently cleared via PATCH, allowing dispatch of items with unresolved dependencies. Separately, the full dataset (79 items) was dumped in one unauthenticated request via limit=999999.

⬤ Critical — Confirmed (Live Exploit)
F-001 Complete Absence of Authentication on All API Endpoints
Critical Confirmed (Live Exploit) SAST-001PEN-001RED-001COMP-001
CWE / Frameworks
CWE-306 · SOC2 CC6.1, CC6.2 · OWASP-ASVS V2.1, V4.1
File
Source/Backend/src/app.ts — all route registrations
Description
Zero authentication middleware is configured anywhere in the application. All endpoints — including CRUD, state transitions (approve, reject, dispatch), fast-track routing, and webhook intake — are fully public. Any unauthenticated HTTP client can perform any operation. All other confirmed breaches depend on this root cause.
Live Evidence (RED-001)
curl http://localhost:3001/api/feature-requests → 200 OK (full dataset) POST /api/feature-requests (no auth) → 201 Created FR-0001 DELETE /api/feature-requests/FR-0005 (no auth) → 204 No Content
Remediation
Add JWT authentication middleware in app.ts applied globally before all /api/* routes. Exempt only /health and /metrics (with separate token protection). Gate force-approve, approve, reject, dispatch behind a reviewer or admin role (see F-007). For webhook routes, use HMAC-SHA256 verification instead of bearer token (see F-006).
F-002 State Machine Bypass — Force-Approve Skips All Human Review
Critical Confirmed (Live Exploit) PEN-003RED-002COMP-002
CWE / Frameworks
CWE-284 · SOC2 CC6.3 · OWASP-ASVS V4.2
File
Source/Backend/src/routes/workflow.ts (force-approve) · Source/Backend/src/services/router.ts (overrideRoute fast-track)
Description
The /force-approve endpoint and overrideRoute: "fast-track" parameter allow any unauthenticated caller to bypass the entire assessment pipeline and set an item to approved with zero votes and zero human review. Additionally, PATCH status accepts arbitrary status values that dedicated action endpoints would reject, providing a second bypass path.
Live Evidence (RED-002)
POST /api/feature-requests → FR-0001 (potential) PATCH /api/feature-requests/FR-0001 {"status":"voting"} → voting POST /api/feature-requests/FR-0001/force-approve → approved Response: {"status":"approved","votes":[],"human_approval_approved_at":"2026-08-31T09:38:55.093Z"}
Remediation
Require authenticated admin role for force-approve. The PATCH status endpoint must enforce the same state machine transitions as dedicated action endpoints — reject arbitrary status values. overrideRoute: "fast-track" must require manager role with audit logging.
⬤ High — Confirmed + Theoretical
F-003 Dependency Gating Bypass — PATCH blocked_by:[] Clears Blockers Without Authorization
High Confirmed (Live Exploit) PEN-005RED-003
Description
PATCH /api/work-items/:id with blocked_by:[] silently strips all dependency blockers regardless of item status. Confirmed live: FR-0028 advanced to approved while its blocker FR-0029 remained in potential — the dependency was never resolved.
Live Evidence (RED-003)
FR-0028: pending_dependencies (blocker: FR-0029 active) PATCH /api/feature-requests/FR-0028 {"blocked_by":[]} → has_unresolved_blockers: false PATCH /api/feature-requests/FR-0028 {"status":"approved"} → approved FR-0029: still in 'potential' (unresolved)
Remediation
Clearing blockers must only be possible via the /dependencies endpoint with proper resolution semantics. State transitions away from pending_dependencies must re-validate has_unresolved_blockers server-side rather than trusting the cached field.
F-004 Unbounded Pagination — Full Dataset Enumeration via limit=999999
High Confirmed (Live Exploit) SAST-005PEN-004RED-005
File
Source/Backend/src/routes/workItems.ts:70 · Source/Backend/src/routes/dashboard.ts:18
Description
The limit query parameter has no upper cap. page=-1 and non-numeric values also bypass pagination. Confirmed live: 79 items returned in a single unauthenticated request with limit=999999.
Live Evidence (RED-005)
GET /api/feature-requests?limit=999999 → 200, all 79 items, no auth required GET /api/feature-requests?page=-1&limit=5 → returns full dataset GET /api/feature-requests?limit=abc → NaN → falls back to full dump
Remediation
const limit = Math.min(parseInt(req.query.limit as string, 10) || 20, 100);
Reject negative/NaN page values with 400 Bad Request. Apply uniformly to all list endpoints including dashboard.ts.
F-005 Rejection Cascade Triggers Unintended Auto-Dispatch of Dependent Items
High Theoretical PEN-006
File
Source/Backend/src/routes/workflow.ts:193–201 · Source/Backend/src/services/dependency.ts:251–315
Description
POST /reject calls onItemResolved() which auto-dispatches any approved dependent item that becomes unblocked. An attacker can create item B depending on A, bring B to Approved, then reject A — triggering dispatch of B with no explicit human action on B's dispatch.
Remediation
Auto-dispatch via rejection cascade should require explicit human confirmation or gating behind the same role check as direct dispatch. Log cascade dispatch as a distinct audit event with actor identity.
F-006 Unauthenticated Webhook Endpoints — No HMAC Signature Verification
High Theoretical SAST-002PEN-007COMP-003
File
Source/Backend/src/routes/intake.ts:11–55
Description
Both /api/intake/zendesk and /api/intake/automated accept unauthenticated POST requests with no HMAC-SHA256 verification. Any external actor can spoof Zendesk events and inject arbitrary work items, indistinguishable from legitimate submissions. Combined with F-009 (unvalidated enums), this enables data integrity attacks.
Remediation
Verify X-Zendesk-Webhook-Signature HMAC-SHA256 using a shared secret from env vars. For automated intake, require Authorization: Bearer <key> against process.env.INTAKE_API_KEY. Reject with 401 on failure.
F-007 No Role-Based Access Control on Privileged State Transitions
High Theoretical COMP-002
Frameworks
SOC2 CC6.3 · OWASP-ASVS V4.2
Description
Even once authentication is added (F-001), there is no role concept. Any authenticated user would be able to approve, reject, and dispatch — there is no least-privilege enforcement. This is a separate remediation effort beyond authentication alone.
Remediation
Introduce role-check middleware after implementing F-001. approve, reject, dispatch require reviewer or manager role. Centralize in middleware, not per-handler.
F-008 No TLS — All API Traffic Travels in Plaintext
High Theoretical COMP-004
Frameworks
OWASP-ASVS V9.1.1 · SOC2 CC6.1
Description
The Express server binds to plain HTTP on port 3001. All API traffic — including state transitions and work item content — is transmitted in cleartext. The Vite dev proxy also proxies to http://localhost:3001.
Remediation
Enforce HTTPS at infrastructure layer via Nginx/Caddy with TLS certificates. Add HTTP→HTTPS redirect middleware in production. Replace Vite dev proxy with reverse-proxy TLS termination.
F-009 Unvalidated Enum Inputs via Intake Routes — Data Integrity Bypass
High Theoretical SAST-004PEN-002
File
Source/Backend/src/routes/intake.ts:22–23, 45–46
Description
Intake webhook handlers pass body.type and body.priority to createWorkItem() without enum validation. Arbitrary strings are stored verbatim, corrupting routing logic. The regular /api/work-items POST validates these fields correctly — intake bypasses that guard entirely.
Remediation
Add if (!Object.values(WorkItemType).includes(body.type)) return res.status(400)... to both intake handlers, matching the pattern in workItems.ts POST handler.

F-010Soft-Deleted Item ID Leak via Dependency Response (Partial IDOR)
MediumConfirmed (Live Exploit)PEN-011RED-004
Description
Soft-deleted items are correctly 404'd on direct GET, but their internal IDs leak via the blocked_by array of dependent items. has_unresolved_blockers: true persists indefinitely when a blocker is deleted — it can never auto-resolve. Confirmed live: FR-0005 ID leaked in FR-0006 response after deletion.
Live Evidence
{"blocked_by":[{"item_id":"FR-0005","status":"unknown"}],"has_unresolved_blockers":true}
Remediation
When a blocker is soft-deleted, cascade-resolve or cascade-remove its dependency links. Filter soft-deleted blockers from the blocked_by response array.

F-016No Persistent Storage — Data Lost on Restart, No Encryption at Rest
MediumTheoreticalCOMP-010
Description
