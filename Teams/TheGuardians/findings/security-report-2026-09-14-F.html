Executive Summary

The dev-crew Source App / portal backend has zero authentication, zero authorization, and zero rate limiting on every API endpoint. Any unauthenticated HTTP caller can enumerate, create, modify, approve, force-approve, deny, reject, delete, and dispatch any resource in the system. The red-team confirmed three out of four pentest objectives as live, exploitable breaches in under five HTTP requests each.

Grade F is automatic under the grading rubric: confirmed red-team breaches of critical objectives were demonstrated. The compliance pass rate (23%) is below all grade thresholds (Grade D requires ≥60%). No hardcoded secrets, SQL injection vectors, or dangerous APIs were found.

Consolidated Findings

Critical 2 findings — both confirmed live
CRIT-001 Complete Absence of Authentication and Authorization
Confirmed (Live Exploit) CWE-306 · CWE-862 ASVS V2.1 · V4.1 · SOC2 CC6.1/2/3
Sources: SAST-001 · PEN-001 · PEN-002 · COMP-001 · COMP-002 · RED-001 · RED-003
Every API endpoint accepts anonymous HTTP requests with no token, session, API key, or identity check. Red team confirmed HTTP 200 across all seven primary endpoint families with zero credentials. Full CRUD verified: read (200), create (201), modify (200), delete (204). Any caller can also deny or delete any record: POST /deny and DELETE /:id both executed with no authorization.
Remediation: Add JWT authentication middleware globally in app.ts before all /api/* routes. Implement RBAC (viewer/operator/admin). Derive actor identity from authenticated token — never from request body. Protect /metrics with bearer token or network restriction.
CRIT-002 State Machine Bypass via Unauthenticated Force-Approve
Confirmed (Live Exploit) ✅ Objective Achieved CWE-284 · CWE-285 ASVS V4.1 · SOC2 CC6.3
Sources: PEN-003 · PEN-004 · RED-002
POST /api/feature-requests/:id/force-approve requires no authentication. Red team: (1) created item → potential, (2) triggered voting → voting, (3) force-approved → approved with human_approval_approved_at set as if legitimately approved, (4) advanced to in_development via PATCH. The entire voting/human-review pipeline was bypassed in 5 HTTP requests with no credentials. Approval timestamp is indistinguishable from legitimate approval.
Remediation: All approval endpoints (/approve, /force-approve, /deny) must require authenticated admin role. Rate-limit force-approve to 5/min per operator. Log as structured audit event with actor identity.
High 7 findings — 2 confirmed, 3 theoretical, 2 compliance gaps
HIGH-001 Full Data Exfiltration via Unbounded Pagination
Confirmed (Live Exploit) ✅ Objective Achieved CWE-770 ASVS V13.1 · SOC2 CC6.1
Sources: SAST-005 · PEN-009 · RED-006
The limit query parameter is completely ignored. GET /api/feature-requests?limit=1 and ?limit=999999 both return the full dataset (67 items after flood test). No pagination metadata in response. Any unauthenticated caller exfiltrates the entire dataset in one HTTP request.
Remediation: Implement server-side pagination with hard max of 100 per page. Return {data, total, page, limit, totalPages}. Return HTTP 400 for invalid limit/page values.
HIGH-002 Stored XSS via Unvalidated Title and Description Fields
Confirmed (Live Exploit) CWE-79 ASVS V5.3 · SOC2 CC6.1
Sources: RED-004 (new — not in SAST or PEN reports)
Three XSS payloads stored verbatim: <script>alert(document.cookie)</script>, <img src=x onerror=alert(1)>, <svg onload=alert(1)>. All return HTTP 201 and are served to any client loading the feature-requests list. If the frontend renders these as HTML, XSS fires in every user's browser.
Remediation: Apply server-side HTML sanitization (sanitize-html or DOMPurify) before storing. Use React's default JSX rendering — never dangerouslySetInnerHTML for user content. Add Content-Security-Policy via Helmet blocking inline scripts.
HIGH-003 Webhook Intake Lacks HMAC/Signature Verification
Theoretical CWE-346 · CWE-290
Sources: SAST-002 · PEN-005  |  File: Source/Backend/src/routes/intake.ts:11-54
Zendesk and automated intake endpoints accept any POST with title+description. No HMAC-SHA256 verification, no API key header, no IP allowlist. An attacker can impersonate Zendesk and inject arbitrary work items indistinguishable from legitimate tickets.
Remediation: Verify X-Zendesk-Webhook-Signature using HMAC-SHA256 against ZENDESK_WEBHOOK_SECRET env var. Require bearer token for /automated endpoint.
HIGH-004 Unvalidated Enum Inputs in Intake Webhook
Theoretical CWE-20
Sources: SAST-003 · PEN-006  |  File: Source/Backend/src/routes/intake.ts:22-23,45-46
Intake routes use body.type || WorkItemType.Bug without enum validation — any truthy string bypasses the default. Main /api/work-items validates enums correctly; intake routes do not. Inconsistency allows data integrity violations and may corrupt assessment routing logic.
Remediation: Apply Object.values(WorkItemType).includes(body.type) validation. Reject HTTP 400 for invalid enum values — same pattern as workItems.ts lines 29-42.
HIGH-005 Soft-Delete Creates Permanent Dispatch Denial-of-Service
Theoretical CWE-400
Sources: PEN-007  |  File: Source/Backend/src/services/dependency.ts:64-75
When a blocker item is soft-deleted, findById() returns undefined. computeHasUnresolvedBlockers() treats undefined as an unresolved blocker — permanently blocking dispatch of any dependent item with no recovery path.
Remediation: On soft-delete, cascade-remove item ID from all dependency arrays. Treat undefined blocker as resolved. Or implement hard-delete.
HIGH-006 All Four Required Audit Events Missing
Compliance Gap SOC2 CC7.1 · ASVS V7.2
Sources: COMP-003  |  File: Source/Backend/src/utils/logger.ts
None of the four mandated audit events are emitted: login_attempt, permission_denied, state_transition, data_export. State transitions logged as operational info — not filterable for compliance review. No auth layer means no login/denial events possible.
Remediation: Add audit severity level to logger with type:"audit_event" tagging. Emit typed events on every state change. Once auth exists, emit login_attempt and permission_denied events.
HIGH-007 No Data Encryption at Rest — In-Memory Ephemeral Store
Compliance Gap ASVS V8.3 · SOC2 CC6.1
Sources: COMP-007  |  File: Source/Backend/src/store/workItemStore.ts
All application data stored in a JavaScript Map — no persistence, no database, no encryption at rest. Data lost on process restart. Zendesk intake can store arbitrary PII-containing descriptions. No field-level encryption or masking.
Remediation: Migrate to PostgreSQL or SQLite with encrypted storage volumes. Document permitted data types until migration is complete.
Medium 10 findings — 3 confirmed, 6 theoretical, 1 compliance gap
MED-001Soft-Deleted Item IDOR via Dependency References
Confirmed (Live Exploit)✅ Objective AchievedCWE-284 · CWE-639
Sources: PEN-008 · RED-005
After soft-deleting FR-0012, its ID remained in FR-0011's blocked_by array. Red team used leaked ID to invoke POST /dependencies {"action":"remove","blocker_id":"FR-0012"} — modifying state via a soft-deleted reference. has_unresolved_blockers persists, causing dispatch denial.
Remediation: On soft-delete, cascade-remove item ID from all dependency arrays. Filter soft-deleted IDs from dependency payloads.
MED-002No Rate Limiting — Request Flood Confirmed
Confirmed (Live Exploit)CWE-799 · ASVS V13.1 · SOC2 CC6.1
Sources: SAST-009 · PEN-014 · COMP-006 · RED-007
50 concurrent POST requests all succeeded — no HTTP 429, no backpressure. Database grew from 17 to 67 records in a single burst. Linear DoS risk at scale.
Remediation: Add express-rate-limit globally (100 req/min GETs, 20 req/min POSTs). Tighter limits on /approve, /force-approve, /deny, /vote (5/min). IP allowlisting for webhook intake.
MED-003Unauthenticated Dashboard Exposes Full Internal State
Confirmed (Live Exploit)CWE-200 · CWE-306 · SOC2 CC6.1
Sources: PEN-011 · RED-008
GET /api/dashboard/summary and /activity return full internal state with zero credentials: status breakdowns, full audit trail (14 events), agent names, entity IDs, state transitions — complete reconnaissance map for attackers.
Remediation: Require read-only authenticated session for all dashboard endpoints.
MED-004Internal Error Messages Leaked to HTTP Clients
TheoreticalCWE-209 · ASVS V7.4
Sources: SAST-006 · COMP-009  |  File: Source/Backend/src/routes/workflow.ts (all catch blocks)
All six workflow handlers return raw Error.message in HTTP 500 responses. The existing errorHandler middleware sanitizes correctly, but in-handler catches bypass it.
Remediation: Return generic {"error":"Internal server error"} for all 500s. Log full error internally. Call next(err) to use existing errorHandler.
MED-005Missing HTTP Security Headers (No Helmet)
TheoreticalCWE-16 · OWASP A05:2021 · ASVS V14.4
Sources: SAST-007 · COMP-004  |  File: Source/Backend/src/app.ts
CSP, X-Frame-Options, HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy — all absent. Without CSP, stored XSS payloads (HIGH-002) have no browser-level mitigation.
Remediation: npm install helmet; app.use(helmet()) as first middleware. One-line fix. Tune CSP for application origins.
MED-006iframe Debug Portal Missing sandbox Attribute
TheoreticalCWE-1021
Sources: SAST-008  |  File: Source/Frontend/src/pages/DebugPortalPage.tsx:9-15
iframe embeds VITE_PORTAL_URL with no sandbox attribute and no frame-src CSP. If portal URL redirects to attacker-controlled page, it can operate within parent app's DOM.
Remediation: Add sandbox="allow-scripts allow-same-origin". Add CSP frame-src restricted to expected portal origin.
MED-007Unauthenticated Prometheus /metrics Endpoint
TheoreticalCWE-200 · SOC2 CC6.1
Sources: SAST-004 · COMP-010  |  File: Source/Backend/src/app.ts:34-37
Publicly accessible with no authentication. Exposes workflow throughput, team assignment patterns, dispatch rates, and Node.js runtime internals — complete operational reconnaissance.
Remediation: Bearer-token middleware keyed by METRICS_TOKEN env var, or bind to internal-only port.
MED-008Cascade Dispatch DoS via Deep Dependency Chain
TheoreticalCWE-400
Sources: PEN-012  |  File: Source/Backend/src/services/dependency.ts:251-315
onItemResolved() synchronously auto-dispatches all N items blocked by a resolved item, no depth/breadth limit. Star-topology with 100+ dependents causes N synchronous store updates per single reject request.
Remediation: Move cascade dispatch to async queue. Add maximum cascade breadth limit (50) per resolution event.
MED-009Negative Page Number Causes Unexpected Slice Behavior
TheoreticalCWE-20
Sources: PEN-010  |  File: Source/Backend/src/routes/workItems.ts:68-74
page=-1 → offset=-40 → Array.slice(-40,-20) returns elements from the end of the array, exposing a different data window than page 1.
Remediation: Enforce Math.max(1, page) before computing offset. Return HTTP 400 for non-positive page values.
MED-010Soft Delete Does Not Satisfy Right-to-Erasure (GDPR Art. 17)
Compliance GapASVS V8.3 · GDPR Art. 17
Sources: COMP-008  |  File: Source/Backend/src/store/workItemStore.ts
softDelete sets item.deleted=true but record remains in memory. No hard-delete, no anonymization, no data retention TTL. PII in description fields is never purged.
Remediation: Implement hard-delete path. Add data retention TTL (90 days for completed/rejected items). Document erasure policy in specifications.
