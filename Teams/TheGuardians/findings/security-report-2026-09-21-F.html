1. Executive Summary

The dev-crew Source App has no authentication or authorization system anywhere in its codebase. This single architectural gap is the root cause of every critical and high-severity finding in this report. During the red-team phase, an active attacker against an ephemeral isolated instance was able to bypass the state machine, create unauthorized CI/CD pipeline runs, and complete a full 5-stage development pipeline — all without any credentials, in under 30 seconds using 12 HTTP requests. The application is not safe to expose beyond a single developer's local machine.

Top 3 Risks:

  • 🔴 Zero authentication — every endpoint is publicly writable; any attacker can read, create, approve, reject, and dispatch any work item.
  • 🔴 Full CI/CD pipeline takeover — an unauthenticated actor can inject a feature request into the pipeline and advance it through all 5 stages (requirements → API contract → implementation → QA → integration) with zero human approval.
  • 🟠 State machine completely bypassable — the voting quorum requirement (5 agent votes) is nullified by direct status mutation and force-approve endpoints, reachable without authentication.

🔴 Critical — Confirmed (Live Exploit)
SEC-001 · SAST-001 + COMP-001 + PEN-001 + RED-001

No Authentication on Any API Endpoint

Critical Confirmed (Live Exploit) 4 sources merged
📡 Sources: static-analyzer · compliance-auditor · pen-tester · red-teamer

Every API endpoint — /api/work-items, /api/workflow, /api/intake, /api/dashboard, /api/cycles, /api/feature-requests — is publicly writable with zero credentials. The Express application registers no authentication middleware of any kind. RED-001 confirmed: curl -X POST /api/feature-requests with no auth headers returns HTTP 201. This is the root cause enabling every other confirmed breach in this report.

Remediation: Add JWT bearer token validation middleware (e.g., express-jwt) before all /api/* routes in Source/Backend/src/app.ts. Propagate req.user to all service and logging layers. Protect intake endpoints with HMAC shared-secret verification instead of bearer tokens.
SEC-002 · PEN-002 + RED-002 + RED-008 + RED-009

State Machine Bypass, Unauthorized Cycle Injection & Full CI/CD Pipeline Takeover

Critical Confirmed (Live Exploit) 4 sources merged
📡 Sources: pen-tester · red-teamer

Three independent confirmed exploits that together constitute a complete pipeline takeover:
(a) RED-002 Force-Approve Bypass: A feature request was promoted from potential to approved in 3 unauthenticated requests, bypassing the 5-agent voting quorum entirely via POST /api/feature-requests/:id/force-approve.
(b) RED-008 Unauthorized Cycle Creation: POST /api/cycles with an empty body auto-selected the next approved FR and created a full 5-stage pipeline run.
(c) RED-009 Full Pipeline Completion: All 5 stages (requirements, api_contract, implementation, QA, integration) were completed unauthenticated via sequential /start+/complete?verdict=approved calls in ~30 seconds.

Remediation: (1) Require authentication and a manager role for /force-approve, /cycles creation, and all /stages/:id/complete endpoints. (2) Remove or protect the force-approve escape hatch — it nullifies the voting system. (3) Add pipeline stage signing: each stage completion must carry a signed token from the authorized agent that ran the stage.
🟠 High — Confirmed (Live Exploit)
SEC-003 · SAST-005 + COMP-007 + PEN-003 + RED-003

Full Dataset Enumeration via Unbounded Pagination Limit

High Confirmed (Live Exploit) 4 sources merged
📡 Sources: static-analyzer · compliance-auditor · pen-tester · red-teamer

RED-003 confirmed: GET /api/feature-requests?limit=999999999 returned all 60 items in a single unauthenticated response with no server-side cap. The limit parameter is read via parseInt(req.query.limit, 10) with no upper bound. This enables complete data exfiltration in one request and can exhaust server memory at scale.

Remediation: const limit = Math.min(req.query.limit ? parseInt(..., 10) : 20, 100); in Source/Backend/src/routes/workItems.ts:70 and dashboard.ts:18. Validate that limit and page are positive integers (guard against NaN).
SEC-004 · RED-005

Vote Manipulation via Unauthenticated Retrigger

High Confirmed (Live Exploit)
📡 Sources: red-teamer

RED-005 confirmed: POST /api/feature-requests/:id/retrigger (no auth required) clears all existing agent votes and re-runs AI evaluation from scratch. An attacker can invoke this endpoint repeatedly to game the voting outcome indefinitely — resetting unfavorable vote tallies until a desired verdict is achieved.

Remediation: Require manager role for /retrigger. Add rate-limiting (max 3 retriggers per item per 24h). Log retrigger events with actor identity in the audit trail.
SEC-005 · PEN-006 + RED-004

Soft-Deleted Blocker Permanently Locks Dependent Items (Denial of Service)

High Confirmed (Live Exploit) 2 sources merged
📡 Sources: pen-tester · red-teamer

RED-004 confirmed: Deleting a blocker item does not clean up its dependency links. Dependents remain permanently locked in pending_dependencies status with has_unresolved_blockers=true. The deleted blocker appears as {"title":"Unknown","status":"unknown"}. There is no recovery path — affected items are permanently stalled. This is an exploitable denial-of-service: create a blocker, add it as a dependency, delete the blocker.

Remediation: When soft-deleting an item, scan all dependents and remove the deleted item from their blocker lists. Recalculate has_unresolved_blockers and re-evaluate pending_dependencies status.

SEC-006 · COMP-002

No Authorization / RBAC on Privileged Endpoints

HighTheoretical
📡 Sources: compliance-auditor

Even once authentication (SEC-001) is resolved, there is no role-based access control. Any authenticated user could approve, reject, or dispatch any work item. The workflow routes (/approve, /reject, /dispatch) require different authorization levels but enforce none. OWASP-ASVS V4.1/V4.2 and SOC2 CC6.3 require operation-level access control.

Remediation: Define roles: viewer | submitter | reviewer | manager. Implement authorization middleware checking req.user.role. Apply: read-only routes → viewer+; state transitions → reviewer+; approve/reject/dispatch → manager.
SEC-007 · SAST-002 + COMP-012 + PEN-004

Intake Webhooks Accept Forged Requests — No HMAC Signature Verification

HighTheoretical3 sources merged
📡 Sources: static-analyzer · compliance-auditor · pen-tester

The /api/intake/zendesk and /api/intake/automated endpoints accept JSON payloads with no HMAC signature verification, no bearer token, and no source IP allowlist. Any actor who discovers these endpoints can inject arbitrary work items. Real webhook providers (Zendesk, GitHub) sign payloads with a shared secret; the signature is never verified here. CWE-345.

Remediation: Verify X-Zendesk-Webhook-Signature via HMAC-SHA256 using crypto.timingSafeEqual(). Store the shared secret in env var. For automated endpoint, require a bearer token. Add express.json({ limit: '1mb' }) to cap payload size.
SEC-008 · PEN-005

Rejection Cascades to Auto-Dispatch Dependents (Business Logic Flaw)

HighTheoretical
📡 Sources: pen-tester

When a blocking item is rejected, the cascade logic may auto-dispatch its dependents — meaning a rejected prerequisite can trigger downstream work to proceed. This is semantically backwards: a rejected blocker should halt dependents, not release them. An attacker can exploit this to advance items through the pipeline without proper approval.

Remediation: Audit the cascade logic in workflow.ts. When a blocker is rejected, dependents should move to blocked or cancelled status, not proceed. Add a state machine unit test covering the rejection cascade path.
SEC-009 · COMP-003

Missing Required Audit Events (login_attempt, permission_denied, data_export)

HighTheoretical
📡 Sources: compliance-auditor

SOC2 CC7.1 and the project's own security.config.yml mandate four audit events: login_attempt, permission_denied, state_transition, and data_export. login_attempt and permission_denied can never be emitted (no auth system). data_export has no endpoint. state_transition is logged via generic logger.info without actor identity — not a structured tamper-evident audit log.

Remediation: Implement a auditLog(event, actor, context) function emitting structured {event, actor, workItemId, timestamp, outcome} records. Emit login_attempt from auth middleware, permission_denied from authorization guard, state_transition from all workflow handlers with full actor identity.

Prometheus /metrics Endpoint Publicly Accessible — Operational Intelligence Leak

MediumConfirmed (Live Exploit)4 sources merged

RED-006 confirmed: GET /metrics exposes all route labels including specific entity IDs (e.g. route="/api/feature-requests/FR-0001/approve"), request counts, error rates, and response timings — all publicly accessible without credentials. SEC-011 · SAST-004 + PEN-010 + RED-007

MediumConfirmed (Live Exploit)3 sources merged
📡 Sources: static-analyzer · pen-tester · red-teamer

RED-007 confirmed: Error messages expose internal ID format schema ("Must be BUG-XXXX or FR-XXXX"), entity naming conventions, and exact validation rules. All catch blocks in workflow.ts return err.message directly in 500 responses. CWE-209.

SEC-012 · SAST-006 + COMP-006 + PEN-011

No Rate Limiting on Any Endpoint

MediumTheoretical3 sources merged
📡 Sources: static-analyzer · compliance-auditor · pen-tester

No rate-limiting middleware anywhere. Enables data flooding via POST /api/work-items, brute-force against any future auth endpoints, and CPU/memory exhaustion via repeated expensive assessment operations. CWE-770.

SEC-013 · SAST-007 + COMP-004

Missing HTTP Security Headers (No helmet)

MediumTheoretical2 sources merged
📡 Sources: static-analyzer · compliance-auditor

No helmet middleware. Missing: Content-Security-Policy, X-Frame-Options, Strict-Transport-Security, X-Content-Type-Options, Referrer-Policy. Express 4.x emits X-Powered-By: Express leaking stack. No CSP amplifies XSS impact. OWASP-ASVS V14.4.

Remediation: npm install helmet. Add app.use(helmet()) before all routes. app.disable('x-powered-by'). Configure CSP to restrict scripts to same-origin.
SEC-014 · SAST-008 + COMP-005

No CORS Policy Configured

MediumTheoretical2 sources merged
📡 Sources: static-analyzer · compliance-auditor

No CORS middleware. Once authentication is added, any third-party site could make cross-origin authenticated API calls on behalf of a logged-in user. No explicit origin allowlist means the future attack surface grows with every frontend deployment. CWE-942 / OWASP-ASVS V14.5.3.

Remediation: app.use(cors({ origin: process.env.ALLOWED_ORIGIN, credentials: true })). Never use wildcard * on credentialed endpoints.
SEC-015 · SAST-003

Intake Routes Skip Enum Validation on type and priority

MediumTheoretical
📡 Sources: static-analyzer

The intake routes (/zendesk, /automated) use body.type || WorkItemType.Bug without enum validation. Arbitrary strings can be stored as type and priority values, corrupting state machine routing and classification heuristics. CWE-20.

Remediation: Apply the same enum validation pattern from workItems.ts lines 29–42 to both intake routes.
SEC-016 · PEN-008

Race Condition in setDependencies (Non-Atomic Remove+Add)

MediumTheoretical
📡 Sources: pen-tester

The setDependencies operation performs a non-atomic remove-then-add sequence. Concurrent requests can observe an intermediate state where dependencies are partially updated, leading to inconsistent blocker resolution and incorrect has_unresolved_blockers calculations.

Remediation: Wrap dependency update logic in a synchronous atomic operation. If a persistent store is introduced, use a database transaction for dependency mutations.
SEC-017 · PEN-009

routing→approved Transition Enables Partial State Machine Bypass

MediumTheoretical
📡 Sources: pen-tester

A direct routing→approved transition is permitted by the state machine, enabling items to skip the assessment stage entirely via this path. This can be exploited to advance items through the workflow without assessment completion.

Remediation: Audit the state machine transition table. Remove the routing→approved edge if items must pass through assessment. Add a unit test asserting all expected forbidden transitions are rejected.
SEC-018 · COMP-009

No Encryption at Rest — In-Memory Store with No Persistence

MediumTheoretical
📡 Sources: compliance-auditor

All data lives in a JavaScript Map in process memory. No persistence, no encryption at rest, no disaster recovery. Data is lost on restart. OWASP-ASVS V8.1.1 / SOC2 CC6.1 require stored data protection. If PII from Zendesk payloads is ever stored, there is no erasure mechanism.

Remediation: Introduce a persistent store (PostgreSQL or SQLite) with encrypted storage. Inject database credentials via env vars. Implement hardDelete(id) for right-to-erasure compliance.
SEC-019 · COMP-010

No TLS/HTTPS Enforcement

MediumTheoretical
📡 Sources: compliance-auditor

The backend binds to plain HTTP with no TLS. The Vite proxy targets http://localhost:3001. No HSTS header prevents downgrade attacks. No startup check warns if production runs without TLS termination. OWASP-ASVS V9.1.1.

Remediation: Document and enforce TLS termination at ingress for all production deployments. Add HSTS via helmet (SEC-013). Add startup warning if NODE_ENV=production and TRUST_PROXY is unset.

No Data Retention / Hard Delete Mechanism

Remediation: Implement hardDelete(id) in the store. Define a retention policy (e.g., purge soft-deleted items after 90 days). Scrub/mask PII from intake payloads before storage.

Remediation: Add actor parameter to buildChangeEntry(), sourced from req.user.id once SEC-001 is resolved. Ensure audit log records are immutable and separately retained.
