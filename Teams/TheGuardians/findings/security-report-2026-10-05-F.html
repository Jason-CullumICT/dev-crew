1. Executive Summary

⛔ Operator decision required before any merge or deployment. The application is fully unauthenticated and was actively compromised in all red-team test cases. It must not be deployed to any non-ephemeral environment in its current state.

The dev-crew Source App has zero authentication or authorization on every API endpoint. Every workflow operation — including approving/rejecting work items, dispatching teams, creating/deleting records, and injecting development cycles — is publicly accessible with no credentials. The red-teamer confirmed 10 live breaches, achieving all 4 declared critical objectives plus a bonus exploitation (unauthenticated cycle injection). Compliance stands at 20% pass rate across both OWASP-ASVS L2 and SOC2-Type2, driven entirely by the missing auth/authz layer and its downstream effects on audit logging and access controls.

Top 3 Risks

  1. No authentication or authorization (F-001/F-002): Any actor on the network can approve/reject/dispatch/delete any work item, or inject cycles and votes, with no credentials. Confirmed live.
  2. State machine bypass and vote stuffing (F-003/F-010): An attacker can force-approve any feature request with zero legitimate votes and skip the entire pod review process. Confirmed live.
  3. Stored XSS + uncapped pagination (F-011/F-008): Arbitrary script payloads are persisted verbatim and will execute in any frontend rendering context; the full data store can be exfiltrated in a single request.

2. Consolidated Findings

Findings are deduplicated and merged across specialists. PEN-IDs confirmed by RED-IDs are marked Confirmed (Live Exploit). Source IDs in parentheses trace back to original specialist reports.

🔴 Critical — Confirmed Live Exploits
F-001 No Authentication on Any API Endpoint Critical Confirmed (Live Exploit)
The entire Express API — including workflow state transitions, CRUD operations, intake webhooks, and the Prometheus metrics endpoint — is mounted without any authentication middleware. Any unauthenticated caller can perform any operation. CWE-306.
// Source/Backend/src/app.ts app.use('/api/work-items', workItemsRouter); // Full CRUD + transitions app.use('/api/work-items', workflowRouter); // Approve/reject/dispatch app.use('/api/dashboard', dashboardRouter); // No auth middleware anywhere in the chain // RED-001 evidence: POST /api/feature-requests/FR-0001/approve → 200 {"status":"approved","votes":[]} // RED-002 evidence: Full bug lifecycle (triage→resolve→close→delete) all returned 2xx with zero credentials // RED-004 evidence: DELETE /api/feature-requests/FR-0007 → 204; subsequent GET → 404
Remediation: Add JWT Bearer or API-key authentication middleware before all /api/* route mounts in app.ts. Return 401 Unauthorized on missing/invalid credentials. For intake endpoints, add separate HMAC webhook secret validation.
Sources: SAST-001 · PEN-001 · COMP-001 · RED-001 · RED-002 · RED-004 · RED-008
F-002 No Authorization / Role-Based Access Control on Any Endpoint Critical Confirmed (Live Exploit)
Even if authentication were added, there is no role system or permission enforcement on sensitive operations. Approve, reject, dispatch, and delete operations carry no authorization checks. The principle of least privilege is entirely absent. CWE-285 / OWASP-ASVS V4.2.1–V4.2.2 / SOC2 CC6.3.
// Source/Backend/src/routes/workflow.ts — no role check before: router.post('/:id/approve', ...) // Any caller router.post('/:id/reject', ...) // Any caller router.post('/:id/dispatch', ...) // Any caller // RED-002 evidence: anonymous caller controlled full bug lifecycle
Remediation: Implement RBAC middleware after authentication is resolved. Define roles (reviewer, dispatcher, admin). Apply role checks to all sensitive endpoints. Return 403 Forbidden on privilege violation and emit a structured permission_denied audit event.
Sources: COMP-002 · PEN-001 · RED-002 · RED-009
F-003 State Machine Bypass via Unauthenticated overrideRoute Parameter Critical Confirmed (Live Exploit)
A caller can POST to the routing endpoint with {"overrideRoute":"fast-track"} and advance a work item from Backlog → Approved in a single call, bypassing the entire pod-review and voting pipeline. The red-teamer force-approved a feature request with zero legitimate votes.
// Attack chain (pen-tester PEN-003): POST /api/work-items/:id/route {"overrideRoute":"fast-track"} → item transitions Backlog → Approved, skipping all review gates // RED-001 evidence: POST /api/feature-requests/FR-0001/approve → 200 {"status":"approved","votes":[]}
Remediation: Remove the overrideRoute bypass parameter or restrict it to an admin role with full audit logging. Enforce state-machine transitions server-side using an allowlist of valid source→target pairs per role. Every state transition must emit a structured state_transition audit event.
Sources: PEN-003 · RED-001
F-004 Unauthenticated Permanent Deletion of Any Work Item Critical Confirmed (Live Exploit)
Any caller can permanently delete (hard-delete in the portal domain) any item by ID with no credentials. The red-teamer deleted FR-0007; a subsequent GET returned 404, confirming permanent removal.
// RED-004 evidence: DELETE /api/feature-requests/FR-0007 → 204 No Content GET /api/feature-requests/FR-0007 → 404 Not Found (confirmed deleted)
Remediation: Gate all DELETE endpoints behind authentication (F-001) and an admin or owner role check (F-002). Log a data_deletion audit event on every successful delete. Consider soft-delete as default with privileged hard-delete only.
Sources: RED-004
F-005 Unauthenticated Development Cycle Injection Critical Confirmed (Live Exploit)
An unauthenticated attacker can create arbitrary development cycles via POST /api/cycles, injecting adversarial work items and assigning any team name. The red-teamer created CYCLE-0001 pointing to an attacker-controlled bug and assigned it to TheATeam.
// RED-008 evidence (bonus objective): POST /api/cycles {"name":"Attacker Cycle","bug_id":"BUG-EVIL","team_name":"TheATeam"} → 201 {"id":"CYCLE-0001","team_name":"TheATeam",...}
Remediation: Require authentication and an admin/planner role on all /api/cycles mutation endpoints. Validate that referenced bug/feature-request IDs exist and belong to the actor's scope.
Sources: RED-008
🟠 High
F-006 Webhook Intake Endpoints Lack HMAC Signature Verification High Theoretical
The /api/intake/zendesk and /api/intake/automated endpoints accept arbitrary POST bodies without verifying the X-Zendesk-Webhook-Signature HMAC-SHA256 header or any shared secret. Any actor who discovers the URL can inject arbitrary work items. CWE-345.
// Source/Backend/src/routes/intake.ts router.post('/zendesk', (req, res) => { const body = req.body; // No X-Zendesk-Webhook-Signature validation at all const item = store.createWorkItem({ ... });
Remediation: Validate X-Zendesk-Webhook-Signature using HMAC-SHA256 against a ZENDESK_WEBHOOK_SECRET env variable before processing any payload. For /automated, require a bearer API key (AUTOMATION_API_KEY). Return 401 on mismatch.
Sources: SAST-002 · PEN-002 · COMP-007
F-007 Required Audit Events Missing — login_attempt, permission_denied, data_export High Theoretical
Three of four mandatory audit events are completely absent. state_transition events are partially logged as free-text messages but not as structured, queryable records. This makes security incident reconstruction impractical. SOC2 CC7.1 / OWASP-ASVS V7.1.1.
Remediation: (1) Add event_type field to the logger schema. (2) Emit structured login_attempt events once auth is added (F-001). (3) Emit permission_denied on every 403 once RBAC is added (F-002). (4) Standardize state_transition log lines with event_type:"state_transition".
Sources: COMP-003
F-008 Full Store Enumeration via Unbounded ?limit Parameter High Confirmed (Live Exploit)
The limit query parameter is accepted without an upper-bound check. A caller can request ?limit=999999 to dump the entire in-memory store in a single response. The red-teamer observed that the limit parameter was entirely ignored, returning all records regardless of value. CWE-400.
// RED-003 evidence: GET /api/work-items?limit=1 → returned 9 items GET /api/work-items?limit=999999 → returned 9 items (limit silently ignored)
Remediation: Clamp limit server-side: const limit = Math.min(parseInt(req.query.limit) || 20, 100). Apply the same cap in dashboard.ts. Return 400 if the requested limit exceeds the cap.
Sources: SAST-005 · PEN-004 · COMP-008 · RED-003
F-009 Unauthenticated Dashboard Exposes Full System State High Confirmed (Live Exploit)
The /api/dashboard endpoints expose queue metrics, all work item IDs, status distributions, and team assignments to any unauthenticated caller. This enables bulk reconnaissance and targeted follow-on attacks against specific item IDs.
// PEN-005 / RED-002 confirmation: GET /api/dashboard/queue → all UUIDs + statuses returned, no auth required
Remediation: Apply the same authentication middleware (F-001) to all /api/dashboard routes. Consider scoping dashboard views by role — dispatchers see the queue; individual contributors see only their items.
Sources: PEN-005 · RED-002
F-010 Vote Stuffing — Unlimited Anonymous Votes, voter_id=null High Confirmed (Live Exploit)
The assessment/voting endpoint accepts null voter_id values and imposes no per-voter deduplication. The red-teamer made 3 calls and accumulated 5 votes with null identity, engineering an approve majority on a feature request. This directly fulfils the "submit malformed verdict bypassing routing logic" objective.
// RED-009 evidence: POST /api/feature-requests/FR-0002/vote {"verdict":"approve","voter_id":null} → 200 (×3) Result: 5 votes accumulated, majority engineered
Remediation: Require an authenticated identity for vote submission (F-001). Enforce one-vote-per-authenticated-identity server-side using a set keyed by actor_id. Reject voter_id=null with 400 Bad Request.
Sources: PEN-006 · RED-009
F-011 Stored XSS — Script Payloads Persisted Verbatim High Confirmed (Live Exploit)
The red-teamer stored a <script>alert(document.cookie)</script> payload in a text field. It was persisted verbatim and fired on render, confirming stored XSS. Any user viewing the item in a browser becomes a victim. CWE-79.
// RED-010 evidence: POST /api/work-items {"title":"<script>alert(document.cookie)</script>",...} → 201 GET /api/work-items/:id → payload returned verbatim; fires on render
Remediation: Sanitize all text inputs server-side on ingest using a library such as DOMPurify (for HTML-aware stripping) or reject HTML-containing inputs outright with a blocklist validation. Set a strict Content-Security-Policy header (F-012) as a second layer of defence.
Sources: RED-010
🟡 Medium
F-012 No HTTP Security Headers or CORS Policy Medium Confirmed
No helmet or cors middleware is present. Responses lack Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Strict-Transport-Security, and Referrer-Policy. The red-teamer confirmed X-Powered-By: Express on all responses. Any origin can make cross-origin API requests. CWE-693.
Remediation: npm install helmet cors. Add app.use(helmet()) and app.use(cors({ origin: process.env.ALLOWED_ORIGINS?.split(',') })) at the top of the middleware chain.
Sources: SAST-006 · PEN-007 · COMP-004 · COMP-005 · RED-005
F-013 Prometheus /metrics Endpoint Unauthenticated Medium Confirmed
The GET /metrics endpoint exposes internal Prometheus counters (work item counts, dispatch rates, team assignment labels) to any caller. The red-teamer confirmed a full Prometheus export with zero authentication. CWE-200.
Remediation: Add a bearer token check (METRICS_TOKEN env var) or restrict to a monitoring-only internal network range/port. In Kubernetes, use a separate internal port for Prometheus scraping.
Sources: SAST-007 · PEN-008 · COMP-009 · RED-006
F-014 Internal Error Messages Returned to Clients Medium Theoretical
Every catch block in workflow.ts (5 locations) returns err.message verbatim in the HTTP 500 response, bypassing the global sanitizing error handler. This will leak internal paths, service names, and data shapes as the code evolves. CWE-209.
Remediation: In all catch blocks, log the full message server-side and return a sanitized generic string: res.status(500).json({ error: 'Internal server error' }). Reserve specific error text for intentional 400-class user-facing errors.
Sources: SAST-003
F-015 Intake Routes Accept Unvalidated type / priority Values Medium Theoretical
Intake endpoints use body.type || default fallback logic rather than enum validation. Arbitrary non-empty strings (including "__proto__") are stored verbatim, causing data corruption and inconsistency in downstream filtering and metrics. CWE-20.
Remediation: Apply the same enum guard used in workItems.ts:29–40 to both intake routes: if (body.type && !Object.values(WorkItemType).includes(body.type)) return res.status(400).json({ error: 'Invalid type' });
Sources: SAST-004
F-016 No Rate Limiting on Any Endpoint Medium Theoretical
No rate-limiting middleware exists. All endpoints — including intake webhooks and workflow actions — can be hammered without throttling, enabling DoS attacks, brute-force state manipulation, and unbounded work-item injection. CWE-770.
Remediation: npm install express-rate-limit. Apply a global limiter (100 req/15 min per IP). Apply a stricter limit on intake routes (20 req/min). Apply per-IP limits on all mutation endpoints.
Sources: SAST-008 · COMP-006
F-017 Computational DoS via Unbounded blockedBy Array in PATCH Medium Theoretical
The PATCH work-item endpoint accepts a blockedBy array with no length limit. A caller can submit thousands of dependency IDs in a single request, consuming server CPU and memory during cycle-detection graph traversal. CWE-400.
Remediation: Validate and cap the blockedBy array length (e.g., max 50 entries). Return 400 Bad Request if the limit is exceeded. Add integration test coverage for oversized inputs.
Sources: PEN-009
F-018 NeedsClarification Assessment Verdict Silently Mapped to Rejected Medium Theoretical
The routing logic silently maps the NeedsClarification assessment verdict to the Rejected state without surfacing this to the caller. This creates a silent data integrity issue where submitters are incorrectly told their request was rejected when it was flagged for clarification.
Remediation: Handle NeedsClarification as a distinct state (e.g., PendingClarification). Return a clear response to the caller indicating the specific status and any clarifying action required. Add a structured state_transition audit event.
Sources: PEN-006
🟢 Low
F-019 Soft-Deleted Item IDs Enumerable via 404 Oracle Low Partial
Soft-deleted item IDs remain referenced in blockedBy dependency links. An attacker can probe these IDs with GET requests and distinguish "deleted" (404) from "never existed" (also 404, but via a different code path in some implementations) to enumerate deleted item IDs.
Remediation: Purge soft-deleted item IDs from all blockedBy arrays on deletion. Consider returning a consistent 404 response for all missing items regardless of deletion status to prevent oracle-style probing.
Sources: PEN-010 · RED-007
F-020 No TLS Enforcement at Application Layer Low Theoretical
The backend starts on plain HTTP with no HTTPS redirect middleware. TLS termination is not enforced or documented. OWASP-ASVS V9.1.1/V9.1.2 requires TLS enforcement in production.
Remediation: Add HTTPS redirect middleware for production environments. Add helmet.hsts(). Document that a TLS-terminating reverse proxy is required in production deployments.
Sources: COMP-011
F-021 No GDPR Hard Delete (Right to Erasure) Low Theoretical
The DELETE endpoint performs a soft-delete only (item.deleted = true). No permanent purge mechanism exists. If the system ever stores personal data, GDPR Art. 17 requires a hard-delete capability. (Supplemental observation — not in formal config scope.)
Remediation: Implement hardDelete(id) in the store. Expose it behind a privileged endpoint (DELETE /:id?purge=true, admin-only). Log a data_deletion audit event. Document the data retention policy.
Sources: COMP-010
F-022 Missing /api/search Endpoint — Future ReDoS Risk Low Theoretical
The /api/search endpoint currently returns 404. If implemented with user-supplied regex patterns, it becomes a ReDoS vector. Flag for attention before implementation.
Remediation: When implementing search, use a fixed-string match or safe, bounded regex (e.g., use safe-regex to validate patterns) rather than allowing arbitrary user-controlled regexes. Rate-limit the search endpoint.
Sources: PEN-011
