1. Consolidated Findings

🔴 Critical — Confirmed Live Exploit

CRIT-001
Entire API Completely Unauthenticated & Unauthorized — Every Endpoint Open to Anonymous Callers
Critical Confirmed
Sources: SAST-001COMP-001COMP-002PEN-001RED-001
Specialists

static-analyzer · compliance-auditor · pen-tester · red-teamer

Description

The Express application mounts every route (/api/work-items, /api/dashboard, /api/intake, /metrics, all workflow endpoints) with zero authentication or authorization middleware. No JWT validation, no session check, no API key, no RBAC. Any HTTP client on the network can create, read, update, delete, approve, reject, or dispatch work items without any credential.

🔴 Red Team Evidence (RED-001)
curl -s http://localhost:3001/api/feature-requests → HTTP 200 (no Authorization header sent — returns all 29 items) curl -s http://localhost:3001/metrics → HTTP 200 (Prometheus telemetry, no auth)

All subsequent RED-002 through RED-007 exploit chains were executed without any authentication token.

Remediation
  1. Add JWT bearer token middleware (e.g., express-jwt) applied globally before all /api/* routes in app.ts.
  2. Introduce a role model (viewer, contributor, manager) and add RBAC middleware for each sensitive action (approve, reject, dispatch, delete).
  3. Return 401 Unauthorized for unauthenticated requests and 403 Forbidden for insufficient role, before any business logic runs.
  4. Restrict /metrics to internal network (bind to 127.0.0.1 or add IP-allowlist middleware).
CRIT-002
State Machine Bypass — Force-Approve with Zero Votes & No Authorization
Critical Confirmed
Sources: PEN-002RED-002
Specialists

pen-tester · red-teamer

Description

The /force-approve endpoint (portal) and the overrideRoute: "fast-track" parameter (Source/Backend router.ts:66-75) allow bypassing the 4-role assessment pod entirely. In the live exploit, a critical-priority feature request targeting main was transitioned from potential → voting → approved with zero agent votes and no authorization check. Reproduced twice (FR-0001, FR-0029).

POST /api/feature-requests          → 201  {id:"FR-0001", status:"potential"}
PATCH /api/feature-requests/FR-0001  body:{"status":"voting"}  → 200
POST /api/feature-requests/FR-0001/force-approve  → 200
{
  "id": "FR-0001",
  "status": "approved",
  "votes": [],                          ← zero votes
  "human_approval_approved_at": "2026-10-26T08:48:54.216Z"
}
🔴 Red Team Evidence (RED-002) — Objective #1 & #3 Achieved

Critical feature targeting main approved with 0 agent votes, no majority, no role check. Chain reproduced twice without credentials.

Remediation
  1. Gate /force-approve and overrideRoute behind an authenticated manager role check (depends on CRIT-001 fix).
  2. Add a required reason field for force-approvals; write an audit log entry recording the authenticated user identity.
  3. Add a minimum-vote guard: even a force-approve should require at least 1 confirming vote, configurable per item priority.
  4. Integration test: assert that unauthenticated /force-approve returns 401 and that votes: [] cannot result in approved status.

🟠 High — Confirmed Live Exploit

HIGH-001
Cross-User Dependency Injection → Ghost Blocker DoS on Victim Work Items
High Confirmed
Sources: PEN-003RED-003
Specialists

pen-tester · red-teamer

Description

The dependency API has no ownership check — any caller can inject a blocker dependency onto any work item they do not own. By adding a blocker they control and then deleting it, the dependencies table retains an orphaned row (no FK CASCADE), causing the victim's item to permanently report has_unresolved_blockers: true and blocking all dispatch operations.

POST /api/feature-requests/FR-0006/dependencies  {"action":"add","blocker_id":"FR-0007"}
DELETE /api/feature-requests/FR-0007  → 204
GET  /api/feature-requests/FR-0006/ready
→ {"ready":false,"unresolved_blockers":[{"item_id":"FR-0007","status":"unknown"}]}
Remediation
  1. Add foreign key ON DELETE CASCADE on dependencies.blocker_item_id so deleting a blocker auto-removes the dependency row.
  2. Enforce ownership: only the item's owner or an admin may add dependencies TO an item they do not own.
  3. When a blocker is soft-deleted, explicitly remove all associated dependency links in the delete handler.
HIGH-002
Pagination limit Parameter Entirely Ignored — Full Data Dump in One Request
High Confirmed
Sources: SAST-006PEN-006RED-004
Specialists

static-analyzer · pen-tester · red-teamer

Description

The list endpoints (GET /api/work-items, GET /api/feature-requests) completely ignore the limit parameter. Any value — including 1, 0, -1, or 999999 — returns the full dataset in a single unauthenticated request.

GET /api/feature-requests?limit=1   → 29 items (limit ignored)
GET /api/feature-requests?limit=0   → 29 items
GET /api/feature-requests?limit=-1  → 29 items
Remediation
  1. Enforce a max limit cap: const limit = Math.min(parseInt(req.query.limit) || 25, 100);
  2. Return proper PaginatedResponse<T> with page, limit, total, and totalPages per CLAUDE.md API response pattern.
  3. Add integration test asserting ?limit=99999 returns at most 100 records.
HIGH-003
Unauthenticated Prometheus /metrics Exposure — Full Telemetry to Anonymous Callers
High Confirmed
Sources: SAST-008PEN-005RED-005
Specialists

static-analyzer · pen-tester · red-teamer

Description

The Prometheus scrape endpoint is registered with no authentication. It exposes HTTP request durations per route, Node.js heap usage, event loop lag, GC durations, item creation/dispatch counts, and team assignment telemetry to any anonymous caller.

Remediation
  1. Bind /metrics to 127.0.0.1 only, or use a separate internal-only HTTP server port for scraping.
  2. Alternatively, add a bearer token check: if (req.headers.authorization !== 'Bearer ' + process.env.METRICS_TOKEN) { res.status(401).end(); return; }

🟠 High — Theoretical (Not Live-Exploited)

HIGH-004
Unauthenticated Webhook Intake — No HMAC Signature Verification
High Theoretical
Sources: SAST-002PEN-004
Specialists

static-analyzer · pen-tester

Description

Both /api/intake/zendesk and /api/intake/automated accept POST requests from any caller without verifying an HMAC-SHA256 signature. Any HTTP client can forge Zendesk events or flood the intake queue with arbitrary work items. (Not live-tested — intake routes not present in portal target; analogous vulnerability confirmed in Source/Backend via static analysis.)

Remediation
  1. Validate X-Zendesk-Webhook-Signature header using HMAC-SHA256 against a shared secret in environment variables.
  2. Apply shared-secret gating to /api/intake/automated as well.
  3. Reject requests where signature doesn't match with 401 before parsing body.
HIGH-005
No HTTP Security Headers — Missing Helmet, CORS Policy, CSP, HSTS
High Theoretical
Sources: SAST-004COMP-003
Specialists

static-analyzer · compliance-auditor

Description

The Express application sets no HTTP security headers. Missing: Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Strict-Transport-Security, Referrer-Policy. No CORS policy is configured — the Vite dev proxy masks this in development, but production frontend-to-API calls will fail without it, or be inadvertently opened to all origins. Violates OWASP-ASVS L2 §14.4.1, §14.4.3, §14.4.6.

Remediation
  1. npm install helmet cors in Source/Backend/.
  2. Add as first middleware: app.use(helmet()); app.use(cors({ origin: process.env.ALLOWED_ORIGINS?.split(',') ?? [] }));
  3. Configure HSTS for production: helmet({ hsts: { maxAge: 31536000, includeSubDomains: true } }).
HIGH-006
Required Audit Events Missing — login_attempt, permission_denied, data_export Not Logged
High Theoretical
Sources: COMP-004
Specialists

compliance-auditor

Description

security.config.yml requires four audit events. Analysis shows: login_attempt — absent (no auth system); permission_denied — absent (no authZ layer); data_export — absent (no logging when large datasets are returned); state_transition — partial (logged but lacks canonical event: "state_transition" key). Violates SOC2-Type2 CC7.1 and OWASP-ASVS L2 §7.2.1–7.2.2.

Remediation
  1. Add login_attempt logging once authentication is implemented (log success/failure, IP, timestamp).
  2. Add permission_denied logging in RBAC middleware (once CRIT-001 is fixed).
  3. Add data_export log event in GET /api/work-items when result set exceeds 100 records.
  4. Tag all state-transition log entries with event: "state_transition" for SIEM parseability.

🟡 Medium — Confirmed

MED-001
No Rate Limiting on Any Endpoint — Brute Force, DoS & Injection Amplification
Medium Confirmed
Sources: SAST-005PEN-011RED-006
Specialists

static-analyzer · pen-tester · red-teamer

Description

No rate-limiting middleware is applied to any route. The red-teamer sent 100 rapid GET requests with zero 429 responses. This amplifies all other attack chains: unlimited enumeration (HIGH-002), unlimited webhook injection (HIGH-004), and memory exhaustion (MED-003).

Remediation
  1. Apply express-rate-limit: 100 req/min reads, 20 req/min writes, 10 req/min intake webhooks.
  2. Return Retry-After header with 429 responses.
MED-002
Body Size Overflow Returns 500 Instead of 413 Payload Too Large
Medium Confirmed
Sources: PEN-009RED-007
Specialists

pen-tester · red-teamer

Description

Sending a body exceeding the configured size limit returns HTTP 500 Internal Server Error instead of HTTP 413 Payload Too Large. The error handler does not catch Express's PayloadTooLargeError (err.type === 'entity.too.large'), causing monitoring noise and masking size-based abuse.

Remediation
  1. In errorHandler.ts, add: if (err.type === 'entity.too.large') { res.status(413).json({ error: 'Payload too large' }); return; }
  2. Consider lowering the body size limit from the default 100 KB to a tighter constraint (e.g., 16 KB for API, 100 KB only for attachment endpoints).

🟡 Medium — Theoretical

MED-003
Cascade Auto-Dispatch via Blocker Rejection — No Human Gate
Medium Theoretical
Sources: PEN-008
Specialists

pen-tester

Description

When a blocker item is rejected, onItemResolved() automatically dispatches all approved dependents. No human authorization gate, no notification, and no audit trail exists for the cascade. The dispatch agent is logged as 'cascade-dispatcher' (an internal string), not a real user identity.

Remediation
  1. Add a configuration flag to disable auto-dispatch cascades, or require explicit confirmation before cascading.
  2. Log the cascade with event: "cascade_dispatch", including the triggering item ID and the actor who performed the rejection.
MED-004
Unvalidated Enum Inputs in Intake Routes Allow Arbitrary type and priority Values
Medium Theoretical
Sources: SAST-003PEN-004
Specialists

static-analyzer · pen-tester

Description

Intake routes (/api/intake/zendesk, /api/intake/automated) accept body.type and body.priority without validating them against the allowed enum values. Non-empty truthy strings bypass the default fallback and are stored directly, corrupting classification and routing logic.

Remediation

Apply the same enum validation used in workItems.ts:

if (body.type && !Object.values(WorkItemType).includes(body.type)) {
  res.status(400).json({ error: 'Invalid type value' }); return;
}
MED-005
No TLS / HTTPS Enforcement — Backend Listens on Plain HTTP
Medium Theoretical
Sources: COMP-006
Specialists

compliance-auditor

Description

The backend server listens on plain HTTP only. No TLS certificates, no HTTPS redirect, and no production reverse-proxy TLS configuration is documented. Violates OWASP-ASVS L2 §9.1.1, §9.1.2 and SOC2-Type2 CC6.1.

Remediation
  1. Add a reverse proxy (nginx or Caddy) with TLS termination for all production deployments.
  2. Add HTTP-to-HTTPS redirect middleware for any non-localhost listener.
  3. Document the production TLS setup in CLAUDE.md or a deployment guide.
MED-006
No Schema Validation Library — Incomplete Injection Protection & No Field Length Limits
Medium Theoretical
Sources: COMP-009
Specialists

compliance-auditor

Description

Validation is done manually with Object.values(Enum).includes() checks. No schema library (Zod, Joi) is used. No field-length limits on title or description. Oversized payloads are currently caught by the body-size limit (MED-002) but per-field limits are absent. Violates OWASP-ASVS L2 §5.1.1, §5.1.3.

Remediation
  1. Adopt Zod (idiomatic with TypeScript): define schemas for all request bodies and use them in route handlers.
  2. Add express.json({ limit: '100kb' }) explicitly rather than relying on the default.
  3. Define field-level maxLength constraints (e.g., title: z.string().max(200)).

LOW-003
No Hard-Delete / Data Erasure Mechanism — Future GDPR Art. 17 Risk
Low Theoretical
Sources: COMP-008
Specialists

compliance-auditor

Description

The only delete mechanism is a soft-delete (item.deleted = true). No hard-purge exists. While the in-memory store currently clears on restart, adding a persistent database without a hard-purge path would create GDPR Art. 17 non-compliance if the app ever processes personal data. Relates to SOC2-Type2 CC8.1.

Document in Specifications/ that a future persistence layer must include a DELETE /api/work-items/:id/purge endpoint (privileged role only) that physically removes the record and all associated history.
