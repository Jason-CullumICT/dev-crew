2. Consolidated Findings

🔴 Critical

Critical CRIT-001 Complete Absence of Authentication & Authorization Confirmed (Live Exploit)
Sources: SAST-001 · PEN-001 · COMP-001 · COMP-002 · RED-001 · RED-005 CWE: CWE-306 · CWE-862 Specialists: static-analyzer, pen-tester, compliance-auditor, red-teamer

Zero authentication or authorization middleware is registered in Source/Backend/src/app.ts. Every endpoint — including privileged state-mutation operations such as /api/work-items/:id/approve, /api/work-items/:id/dispatch, /api/feature-requests/:id/force-approve, and /api/intake/* — is fully accessible to any unauthenticated caller that can reach port 3001. No JWT validation, API-key check, session cookie, or any identity mechanism exists anywhere in the codebase. Neither passport, express-jwt, nor any auth library appears in package.json.


Confirmed by red-teamer (RED-001, RED-005): POST /api/feature-requests/FR-007/force-approve returned {"status":"approved","votes":[]} with zero credentials. POST /api/feature-requests/FR-0032/deny denied an item anonymously.


Compliance failures: SOC2 CC6.1, CC6.2, CC6.3; OWASP-ASVS V2.1.1, V4.1.1, V4.2.1.

Remediation

1. Introduce an authentication layer (JWT bearer tokens recommended for this stack) before all /api/* route registrations.
2. Define a role model (submitter, reviewer, approver, dispatcher) in the specification first.
3. Implement authorize(role) middleware that reads the verified identity from the request and maps roles to allowed actions per endpoint.
4. Block every state-mutation route (approve, reject, dispatch, force-approve) behind role checks.

Critical CRIT-002 State Machine Bypass — Unauthenticated Force-Approve & Cycle Early Completion Confirmed (Live Exploit)
Sources: SAST-002 · PEN-004 · PEN-005 · RED-001 · RED-002 CWE: CWE-20 · CWE-284 Specialists: static-analyzer, pen-tester, red-teamer

Two confirmed exploit chains:


Chain A — Force-Approve (RED-001): Three unauthenticated requests fully bypass the community voting process:

POST /api/feature-requests                           # create, status: potential
PATCH /api/feature-requests/FR-007 -d '{"status":"voting"}'   # move to voting
POST /api/feature-requests/FR-007/force-approve              # APPROVED — 0 votes
# Result: {"status":"approved","votes":[],"human_approval_approved_at":"2026-11-02T10:52:17Z"}

The "human override" endpoint has zero authentication middleware and no vote-count threshold check.


Chain B — Cycle Early Completion (RED-002):

POST /api/cycles          # creates CYCLE-0001 in spec_changes status
POST /api/cycles/CYCLE-0001/complete   # COMPLETE — no phase progression

completeCycle() only checks for incomplete tickets; new cycles have zero tickets so the guard trivially passes. Side effects: auto-creates Feature + Learning records as if real work was completed.


Theoretical chain (SAST-002): POST /api/work-items/:id/route passes body.overrideRoute directly to classifyRoute() without enum validation. Sending {"overrideRoute":"fast-track"} instantly approves any backlog item, bypassing the assessment pod entirely.

Remediation

1. Add authentication (CRIT-001 prerequisite) to all state-mutation endpoints.
2. Add enum validation guard in the route handler: if (!Object.values(WorkItemRoute).includes(body.overrideRoute)) { res.status(400)... }
3. Add vote-count threshold check in force-approve handler (minimum required votes).
4. Add phase-progression guard in completeCycle(): require at least one completed ticket or minimum time in phase before allowing completion.

Critical CRIT-003 Full Unauthenticated Data Exfiltration — No Pagination Cap Confirmed (Live Exploit)
Sources: PEN-002 · PEN-012 · RED-003 CWE: CWE-200 · CWE-862 Specialists: pen-tester, red-teamer

Three unauthenticated GET requests dump the entire system state:

GET /api/feature-requests      # ALL 31 items, full detail, no pagination cap
GET /api/dashboard/summary     # real-time counts by status, severity, priority
GET /metrics                   # 531-line Prometheus dump — transition counts, team assignments, request patterns

The limit parameter on GET /api/work-items is parsed but never range-validated, allowing ?limit=999999999 to attempt returning the entire store in a single response. The dashboard endpoint has no equivalent parameter at all. The /api/dashboard/activity endpoint additionally leaks full change history including oldValue/newValue pairs for every state transition.

Remediation

1. Add authentication (CRIT-001) to all read endpoints as the primary control.
2. Cap pagination: const limit = Math.min(Math.max(parseInt(...) || 20, 1), 100);
3. Restrict /metrics to internal network access only (bind to separate port or add IP allowlist).
4. Audit /api/dashboard/activity — consider omitting oldValue/newValue from the API response or requiring elevated role to access full audit trail.

🟠 High

High HIGH-001 No Rate Limiting — Confirmed Unlimited Request Flood Confirmed (Live)
Sources: SAST-006 · PEN-009 · COMP-010 · RED-004 CWE: CWE-770 Specialists: static-analyzer, pen-tester, compliance-auditor, red-teamer

20 rapid POST requests produced 20 HTTP 201 responses with no throttling of any kind. No 429 Too Many Requests, no Retry-After header. No express-rate-limit or equivalent middleware is installed. The intake endpoints (/api/intake/zendesk, /api/intake/automated) are especially at risk: an attacker or misconfigured integration can flood the in-memory store, exhausting memory and degrading service for all users. Without authentication (CRIT-001), the attack surface is the entire internet.

Remediation

import rateLimit from 'express-rate-limit';
const globalLimiter = rateLimit({ windowMs: 15 * 60_000, max: 100 });
const intakeLimiter = rateLimit({ windowMs: 60_000, max: 20 });
app.use('/api/', globalLimiter);
app.use('/api/intake/', intakeLimiter);
High HIGH-002 No TLS / HTTPS Enforcement — All Data in Transit Unencrypted Theoretical
Sources: COMP-003 Controls: SOC2 CC6.1 · OWASP-ASVS V9.1.1, V9.1.2 Specialists: compliance-auditor

The backend binds plain HTTP (app.listen(PORT, ...)). There is no HTTPS redirect, no Strict-Transport-Security header, and no TLS termination configuration. The frontend Vite proxy targets http://localhost:3001. All work item content and workflow state changes are transmitted unencrypted, making them susceptible to interception by any network-layer observer.

Remediation

Terminate TLS at the reverse proxy level (nginx/Caddy) and enforce HTTPS-only redirects. Add Strict-Transport-Security via Helmet.js (see HIGH-003). Ensure the frontend proxy config uses HTTPS in all non-local environments. Document the TLS termination architecture in the deployment specification.

High HIGH-003 Missing HTTP Security Headers — No Helmet.js Theoretical
Sources: COMP-004 Controls: OWASP-ASVS V14.4.1, V14.4.3, V14.4.6 Specialists: compliance-auditor

Helmet.js is absent from package.json and not applied in app.ts. The following headers are missing on all responses: Content-Security-Policy, X-Frame-Options / frame-ancestors, X-Content-Type-Options: nosniff, Strict-Transport-Security, Referrer-Policy, Permissions-Policy. This leaves the application vulnerable to XSS, clickjacking, and MIME-sniffing attacks.

Remediation

// npm install helmet
import helmet from 'helmet';
app.use(helmet());  // one-liner, large surface reduction

Configure CSP to restrict script sources to the frontend origin.

High HIGH-004 Intake Webhooks — No Auth, No HMAC Verification, Unvalidated Enum Fields Theoretical
Sources: SAST-003 · SAST-005 · PEN-003 CWE: CWE-20 · CWE-345 Specialists: static-analyzer, pen-tester

/api/intake/zendesk and /api/intake/automated accept POST requests with: (1) no X-Zendesk-Webhook-Secret-Token HMAC-SHA256 signature verification — any caller can forge Zendesk webhook payloads; (2) no enum validation on body.type or body.priority — arbitrary strings are stored in enum fields, corrupting data integrity. The CRUD route (POST /api/work-items) correctly validates these fields; the intake routes do not.

Remediation

1. Implement HMAC-SHA256 signature verification using Node.js crypto module against the shared Zendesk secret.
2. Add enum validation matching the pattern in Source/Backend/src/routes/workItems.ts:29-42: if (body.type && !Object.values(WorkItemType).includes(body.type)) { res.status(400)... }

High HIGH-005 SOC2 Audit Events Structurally Absent — login_attempt & permission_denied Theoretical
Sources: COMP-006 · COMP-007 Controls: SOC2 CC7.1 · OWASP-ASVS V7.2.1 Specialists: compliance-auditor

security.config.yml requires login_attempt and permission_denied events in audit logs. Because no authentication or authorization system exists, these events are structurally impossible to emit. No login endpoint exists; no request is ever denied on access-control grounds. Unauthorized access attempts are silently fulfilled rather than logged and blocked. This makes SOC2 CC7.1 compliance impossible in the current architecture.

Remediation

Implement authentication (CRIT-001) first. Then: every authentication attempt must emit { event: 'login_attempt', outcome: 'success'|'failure', userId, ip, timestamp } at INFO level. Every 403 response must emit { event: 'permission_denied', userId, role, resource, action, timestamp }. Centralize in authenticate() and authorize() middleware.

High HIGH-006 Prometheus /metrics Endpoint Publicly Accessible — Confirmed Dumped Confirmed (Live)
Sources: SAST-008 · PEN-008 · COMP-011 · RED-003 CWE: CWE-200 Controls: SOC2 CC6.1 · OWASP-ASVS V4.1.1 Specialists: static-analyzer, pen-tester, compliance-auditor, red-teamer

A 531-line Prometheus metrics dump was retrieved with zero credentials by the red-teamer (part of RED-003). The endpoint exposes workflow operation counters (items created/dispatched per team, route, type, priority), Node.js runtime metrics (memory, CPU, event loop lag, file descriptors), and request rate patterns. This operational intelligence enables targeted reconnaissance for a subsequent attack.

Remediation

Restrict /metrics to internal scrape access only. Options: (a) bind metrics to a separate internal-only port (e.g., 9090); (b) add a static Bearer scrape token; (c) apply IP-allowlist middleware for the scraping agent. This is a quick fix that can be implemented independently of the auth overhaul.

🟡 Medium

Medium MED-001 Internal Error Messages Returned Verbatim to API Clients Theoretical
Sources: SAST-004 CWE: CWE-209 File: Source/Backend/src/routes/workflow.ts:62, 89, 140, 207, 294, 350, 370

All catch blocks in workflow.ts return the raw exception message directly in 500-level responses (res.status(500).json({ error: message })). Internal error messages may contain internal IDs, code paths, store state, or data-layer details that assist attackers in reconnaissance.

Remediation

// Replace: res.status(500).json({ error: message });
// With:
res.status(500).json({ error: 'Internal server error' });
// Keep the logger.error({ msg: '...', error: message, ... }) call server-side
Medium MED-002 No Explicit JSON Body Size Limit Theoretical
Sources: SAST-007 CWE: CWE-770 File: Source/Backend/src/app.ts:13

app.use(express.json()) is called without a body size limit. Express defaults to 100 KB but this is implicit and easily overlooked during upgrades. An attacker can send large JSON bodies to cause memory pressure on the in-process store.

Remediation

app.use(express.json({ limit: '100kb' }));
Medium MED-003 Data Export Events Not Audit Logged Theoretical
Sources: COMP-008 Controls: SOC2 CC7.1 · OWASP-ASVS V7.2.2

security.config.yml requires data_export events in audit logs. Bulk data reads (GET /api/work-items, dashboard endpoints) are only logged at debug level. Bulk data access is effectively invisible in the audit trail.

Remediation

Add logger.info({ event: 'data_export', endpoint, caller, recordCount, filters, timestamp }) in GET handlers for work-items and dashboard routes. Post-auth (CRIT-001), include the caller identity.

Medium MED-004 State Transition Events Lack Structured event: Field Theoretical
Sources: COMP-009 Controls: SOC2 CC7.1 · OWASP-ASVS V7.2.1

State transitions are logged with human-readable messages but without a queryable event: 'state_transition' field. This makes it impossible to filter, alert on, or forward state transition events as a class to a SIEM.

Remediation

Add event: 'state_transition' to every workflow state-change log call in workflow.ts: logger.info({ event: 'state_transition', fromStatus, toStatus, workItemId, ... })

Medium MED-005 No Session Management Policy Defined Theoretical
Sources: COMP-012 Controls: OWASP-ASVS V3.1.1, V3.3.1, V3.3.2

OWASP-ASVS L2 requires session tokens to expire after inactivity (≤30 min for sensitive operations) and be invalidated on logout. No session management exists because there is no authentication. When auth is added, session lifetime and invalidation policies must be designed from the start.

Remediation

When implementing auth (CRIT-001): use short-lived JWT access tokens (≤15 min) with refresh token rotation, or server-side session with inactivity timeout. Define timeout values in the specification.

Medium MED-006 Assessment Re-Entry Allows Unbounded Record Accumulation Theoretical
Sources: PEN-010 CWE: CWE-770

A work item can be submitted for assessment repeatedly, accumulating an unbounded number of assessment records without any guard against duplicate or repeated submissions. This can be abused to exhaust the in-memory store and degrade service.

Remediation

Add a guard in the assessment submission handler to reject re-submission when an assessment is already pending or completed. Alternatively, cap the number of assessment records per work item.

Medium MED-007 Assessment Pod is Fully Deterministic — Crafted Items Guarantee Approval Theoretical
Sources: PEN-011 CWE: CWE-284

The assessment pod scoring logic is fully deterministic and observable. An attacker can craft work items with specific field values to guarantee automated approval, bypassing the intended quality gate entirely. The scoring algorithm effectively becomes a public specification for crafting passing submissions.

Remediation

Consider adding non-deterministic elements to the scoring (e.g., human review flag for borderline scores), or apply the scoring algorithm only after human review for high-priority items. At minimum, add authentication (CRIT-001) so the submitter identity is known and logged.

🔵 Low

Low LOW-001 CORS Policy Not Explicitly Configured (Limited Residual Risk) Theoretical
Sources: PEN-013 · COMP-005 Controls: OWASP-ASVS V13.1.3 · SOC2 CC6.1

No cors() middleware is configured. However, the red-teamer confirmed that browser-level CORS correctly blocks cross-origin requests from evil.example.com (no Access-Control-Allow-Origin header is returned). Non-browser clients are unaffected by CORS regardless. The primary access control gap is CRIT-001 (no auth), not CORS. Risk is classified Low in this context.

Remediation

import cors from 'cors';
app.use(cors({ origin: ['https://app.example.com'], methods: ['GET','POST','PATCH','DELETE'] }));
Low LOW-002 No Hard-Delete Mechanism — Right to Be Forgotten Gap Theoretical
Sources: COMP-013 Controls: OWASP-ASVS V8.3.4

DELETE handler performs soft-delete only. No purgeWorkItem(id) function exists. Limited practical risk with the current in-memory store (all data lost on restart), but persistent storage implementations must honour erasure on the underlying medium.

Remediation

Add a purgeWorkItem(id) function to the store. Expose it behind a privileged admin endpoint (once auth exists). Document purge requirements for future persistent storage implementations.

Low LOW-003 No Persistent Storage — Data Durability Gap (SOC2 CC8.1) Theoretical
Sources: COMP-014 Controls: SOC2 CC8.1

All work item data is held in a JavaScript Map in process memory. All data is lost on process restart. SOC2 CC8.1 requires availability protections. This may be intentional for a prototype stage but blocks production readiness and SOC2 compliance.

Remediation

For production readiness: replace the in-memory store with PostgreSQL or SQLite. Define a backup and recovery policy. Until then, document in the specification that the system is a prototype and data loss on restart is expected behaviour.

Low LOW-004 Sensitive Field Encryption Policy Not Pre-Documented Theoretical
Sources: COMP-015 Controls: SOC2 CC6.1 · OWASP-ASVS V8.2.1

security.config.yml lists email, password, token, secret, api_key as sensitive fields requiring encryption/masking. None of these fields exist in the current data model — no risk today — but when authentication is added, these fields will be introduced and encryption must be in place from day one, not retrofitted.

Remediation

When adding authentication: (1) passwords stored as bcrypt/argon2 hashes only; (2) tokens/api_keys stored as hashed values with only the hash persisted; (3) email masked in log output (u***@example.com); (4) add a log sanitizer that strips/masks these fields from all log entries.
