## Findings

### QO-001: `GET /api/search` endpoint declared but not wired
- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts` + `Source/Backend/tests/routes/search.test.ts:1-6`
- **Detail:** `FR-dependency-search` requires a cross-entity search endpoint (`GET /api/search?q=`). The test file explicitly documents at lines 1–6: *"NOTE: As of this review cycle the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."* The frontend `client.ts:101-104` already calls `/search?q=` in `searchItems()` — any user of `DependencyPicker` will receive a network error at runtime.
- **Recommendation:** Implement the route in `Source/Backend/src/routes/` (filter non-deleted items by title/description match, return `{data: WorkItem[]}`), mount it in `app.ts`, and remove the "intentionally failing" comment from the test file.
- **Cross-ref:** [ESCALATE → TheFixer] — code fix required.

### QO-002: Traceability enforcer blind to entire `portal/` application
- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py:77-97` + `Teams/TheInspector/inspector.config.yml:42-48`
- **Detail:** The enforcer scans only `["Source", "E2E"]` (hardcoded in the script, mirrored in config). The `portal/` directory contains **1,041** `// Verifies:` comments covering FR-001 through FR-095, FR-DUP-* — the entire dev-workflow-platform implementation. Running `python3 tools/traceability-enforcer.py --file Specifications/dev-workflow-platform.md` reports 76 requirements missing — all of them — because `portal/` is never scanned. The gate says PASSED while the portal's actual coverage is completely unvalidated.
- **Recommendation:** Add `"portal"` to the `source_dirs` list in both the enforcer script and `inspector.config.yml`. This is a one-line fix in each file.
- **Cross-ref:** [ESCALATE → TheFixer].

### QO-003: `pending_dependencies` status absent from `WorkItemStatus` enum
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Shared/types/workflow.ts:5-15`
- **Detail:** `FR-dependency-types` specifies that `pending_dependencies` must be added to status enums. `FR-dependency-dispatch-gating` specifies that status transitions to `approved`/`in_development` with unresolved blockers should result in `status = pending_dependencies` (HTTP 200) rather than an error. The current implementation returns HTTP 400 (`"Cannot dispatch: work item has unresolved blocking dependencies"`) instead. The `BlockedBadge` component (`Source/Frontend/src/components/BlockedBadge.tsx`) renders an amber badge when `status === 'pending_dependencies'`, but since this status value cannot be produced, that code path is permanently dead.
- **Recommendation:** Add `PendingDependencies = 'pending-dependencies'` to `WorkItemStatus`. Update `VALID_STATUS_TRANSITIONS` to include transitions from/to it. Update the dispatch handler (`workflow.ts`) to set the status instead of returning 400.
- **Cross-ref:** Related to QO-001. [ESCALATE → TheFixer].

### QO-004: `dependencyCheckDuration` histogram missing from metrics
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/metrics.ts`
- **Detail:** `FR-dependency-metrics` requires 4 Prometheus metrics: `dependencyOperations` counter ✅, `dispatchGatingEvents` counter ✅, `dependencyCheckDuration` histogram ❌ (missing), `cycleDetectionEvents` counter ✅. The readiness-check operation (called on every dispatch attempt and from `computeHasUnresolvedBlockers`) has no latency instrumentation despite being a potentially O(n) BFS traversal.
- **Recommendation:** Add `const dependencyCheckDuration = new Histogram({ name: 'dependency_check_duration_seconds', ... })` to `metrics.ts`. Wrap `isReady()` in `dependency.ts` with `const end = timer(); ... end()`.
- **Cross-ref:** [ESCALATE → TheFixer].

### QO-005: Route handlers call store directly (architecture violation)
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:12`, `Source/Backend/src/routes/workflow.ts:15`
- **Detail:** Both route files `import * as store from '../store/workItemStore'` and call `store.findById`, `store.createWorkItem`, `store.findAll`, `store.updateWorkItem`, `store.softDelete` directly from HTTP handlers. CLAUDE.md rule: *"No direct DB calls from route handlers — use the service layer."* The `workflow.ts` handlers additionally mutate `item.changeHistory` in-place before calling `store.updateWorkItem`, coupling route logic to store internals. This also explains why the missing search endpoint could not be naturally placed — there's no `workItemService` to receive the new business logic.
- **Recommendation:** Create `Source/Backend/src/services/workItemService.ts` exposing `createWorkItem`, `getWorkItem`, `listWorkItems`, `updateWorkItem`, `deleteWorkItem`. Route handlers call service; service calls store. The `changeHistory` mutation should move into the service or `changeHistory.ts`.
- **Cross-ref:** QO-001 (search needs a service layer to land in). [ESCALATE → TheFixer].

### QO-006: Traceability enforcer non-deterministically selects active plan
- **Severity:** P2
- **Category:** pattern-violation
- **File:** `tools/traceability-enforcer.py:48-57`
- **Detail:** When no `--plan` flag is passed, the enforcer selects the plan with the most-recently-modified `requirements.md`. All 8 plans in `Plans/` have identical mtimes (`Apr 30 05:36`), making the selection non-deterministic across filesystems. Currently Python selects `Plans/self-judging-workflow/requirements.md` (FR-WF-001–013), leaving 7 plans unverified:
  - `Plans/dependency-linking/requirements.md` — 7 FRs (FR-0002, FR-0003, FR-070, FR-085 etc.)
  - `Plans/dev-workflow-platform/requirements.md` — 32 FRs
  - `Plans/orchestrated-dev-cycles/requirements.md` — 17 FRs
  - `Plans/dev-cycle-traceability/requirements.md` — 20 FRs
  - `Plans/duplicate-deprecated-status/requirements.md` — FR-DUP-*
  - `Plans/image-upload/requirements.md` — FR-07x
  - `Plans/orchestrator-cycle-dashboard/requirements.md` — FR-07x
- **Recommendation:** The enforcer should either (a) accept a list of requirement files and scan all of them, or (b) be invoked from CI with explicit `--plan` flags for each plan. Add a CI wrapper that iterates all plans.
- **Cross-ref:** Compound with QO-002.

### QO-008: Silent JSON parse failure swallowed in API client
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/api/client.ts:26`
- **Detail:** `const body = await response.json().catch(() => ({}));` — the catch silently returns `{}` when the error-response body is not valid JSON. CLAUDE.md rule: *"Never swallow errors silently — every catch block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."* When the server returns non-JSON (e.g., a 502 from a proxy), the thrown error becomes `"Request failed: 502"` with no additional context, hindering debugging.
- **Recommendation:** Add a comment: `// intentional: non-JSON error bodies treated as empty — status code in thrown message is sufficient context`. Or log the parse failure at debug level before returning `{}`.
