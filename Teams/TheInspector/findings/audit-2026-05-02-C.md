## Findings

### QO-001: `GET /api/search` not implemented — DependencyPicker typeahead has no backend
- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts` (missing route), `Source/Backend/tests/routes/search.test.ts:1-7` (acknowledged gap)
- **Detail:** `FR-dependency-search` requires `GET /api/search?q=` cross-entity typeahead endpoint for the DependencyPicker modal. The test file at `Source/Backend/tests/routes/search.test.ts` explicitly documents: *"NOTE: As of this review cycle the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."* No search route file exists under `Source/Backend/src/routes/`, and `app.ts` has no `/api/search` registration. The `DependencyPicker` component's typeahead (`searchItems()`) will receive 404s in production.
- **Recommendation:** Create `Source/Backend/src/routes/search.ts` that searches `store.getAllItems()` by title/description, returning `{ data: WorkItem[] }`. Register with `app.use('/api/search', searchRouter)` in `app.ts`. The 5 test cases in `search.test.ts` already define the contract.
- **Cross-ref:** frontend-coder should verify `DependencyPicker.tsx` correctly calls the search endpoint once wired up

### QO-002: Traceability enforcer covers only the most recently modified plan — 16+ requirements unpatrolled
- **Severity:** P2
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py:49-57` (fallback to `max(req_files, key=os.path.getmtime)`)
- **Detail:** The enforcer defaults to a single `requirements.md` — the one with the latest `mtime`. Currently that is `Plans/self-judging-workflow/requirements.md` (FR-WF-001…FR-WF-013). `Plans/dependency-linking/requirements.md` with 16 FR-dependency-* requirements is **never automatically enforced**. The CLAUDE.md rule "Every FR needs a test with `// Verifies: FR-XXX`" cannot be enforced for FR-dependency-* unless the operator explicitly passes `--plan dependency-linking`. Additionally, the canonical `Specifications/*.md` files (the "domain truth" per CLAUDE.md) contain FR-001…FR-069 and FR-TMP-* IDs that are mapped to different apps (portal/, platform/) — there is no automated enforcement path linking Specifications/ IDs to any implementation at all.
- **Recommendation (short-term):** Add a CI step that runs the enforcer against **all** plan requirements files: `for req in Plans/*/requirements.md; do python3 tools/traceability-enforcer.py --file "$req"; done`. Any exit code > 0 fails the gate.
- **Recommendation (long-term):** The enforcer should accept `--all-plans` flag that aggregates all `Plans/*/requirements.md` files and reports combined coverage. Consider adding a Specifications/-to-Plans mapping table to CLAUDE.md so agents know which spec maps to which plan.
- **Cross-ref:** requirements-reviewer should add spec→plan ID cross-reference to CLAUDE.md

### QO-003: `dependencyCheckDuration` histogram absent from Source/ metrics — partial FR-dependency-metrics implementation
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/metrics.ts`
- **Detail:** `FR-dependency-metrics` requires **4** Prometheus instruments: `dependency_operations_total` counter ✅, `dispatch_gating_events_total` counter ✅, `cycle_detection_events_total` counter ✅, and `dependency_check_duration_seconds` **histogram** ❌. The histogram exists in `portal/Backend/src/metrics.ts` (correctly) but is absent from `Source/Backend/src/metrics.ts`. The dependency service in Source/ (`services/dependency.ts`) never starts a timer on readiness checks or cascade operations. The metrics test at `tests/routes/metrics.test.ts` does not test for the histogram, meaning this gap passes the test suite undetected.
- **Recommendation:** Add `export const dependencyCheckDuration = new Histogram({ name: 'dependency_check_duration_seconds', help: '...', labelNames: ['check_type'], registers: [registry] })` to `Source/Backend/src/metrics.ts`. Instrument `isReady()` and `detectCycle()` in `services/dependency.ts` similarly to how portal/Backend does it (lines 147, 209). Add a test case to `tests/routes/metrics.test.ts` asserting `dependency_check_duration_seconds_bucket` appears in `GET /metrics`.
- **Cross-ref:** [ESCALATE → TheFixer] for implementation

### QO-004: Route handlers bypass service layer — architecture rule violated in 2 routes
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:44-56, 73, 79, 134, 141` and `Source/Backend/src/routes/intake.ts:19-30, 42-52`
- **Detail:** CLAUDE.md states: "No direct DB calls from route handlers — use the service layer." Both `workItems.ts` and `intake.ts` import `* as store from '../store/workItemStore'` and call `store.createWorkItem()`, `store.findAll()`, `store.findById()`, `store.updateWorkItem()`, `store.softDelete()` directly. The store is the data-access layer (equivalent to a DB in this in-memory architecture). By contrast, `dashboard.ts` correctly delegates to `dashboardService`, and `workflow.ts` correctly uses `routeWorkItem()` and `assessWorkItem()` from the service layer. The pattern is inconsistent: 2 of 4 route files violate the rule.
- **Recommendation:** Extract a `workItemService.ts` with `createItem()`, `listItems()`, `getItem()`, `updateItem()`, `deleteItem()` — thin wrappers that call the store. Update `workItems.ts` and `intake.ts` to import from the service. This also makes the service layer the correct place to add cross-cutting concerns (metrics, logging) in one place.
- **Cross-ref:** [ESCALATE → TheFixer] for refactor

### QO-005: FR-dependency-dispatch-gating acceptance criterion not met — status never transitions to `pending_dependencies`
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/routes/workflow.ts:230-244`, `Source/Shared/types/workflow.ts:5-15` (WorkItemStatus enum)
- **Detail:** `FR-dependency-dispatch-gating` acceptance criterion: *"PATCH to approved with unresolved blocker → 200 with status=`pending_dependencies`"*. The Source/ implementation instead returns HTTP 400 with `{error: "Cannot dispatch: ..."}` and does NOT transition the item to any special status. Furthermore, `pending_dependencies` does not exist in the `WorkItemStatus` enum at all. The spec's intent — making the blocked state visible in the work item's status field — is unimplemented. The `Verifies: FR-dependency-dispatch-gating` comment on this code claims coverage but the acceptance criterion diverges significantly.
- **Recommendation:** Either (a) add `PendingDependencies = 'pending_dependencies'` to `WorkItemStatus`, update `VALID_STATUS_TRANSITIONS`, and implement the gating as a status transition rather than a 400 error; or (b) update the `FR-dependency-dispatch-gating` acceptance criterion in the plan file to reflect the 400-based approach as the intentional design choice for this domain. The current state is spec/code misalignment without documentation of the design decision.
- **Cross-ref:** requirements-reviewer to adjudicate intent; [ESCALATE → TheFixer] for code change if spec is correct

### QO-006: Dual logger abstractions — two active log sinks with different calling conventions
- **Severity:** P3
- **Category:** architecture-violation
- **File:** `Source/Backend/src/logger.ts` and `Source/Backend/src/utils/logger.ts`
- **Detail:** CLAUDE.md: "Use the project's logger abstraction, never `console.log`." There are **two** logger abstractions:
  1. `src/utils/logger.ts` — primary structured logger (named export `{ logger }`), used by `workItemStore.ts`, models
  2. `src/logger.ts` — compat wrapper (default export), used by all route/service files  
  The wrapper normalizes calling conventions between object-style `{ msg, ...ctx }` and string-style `(msg, ctx)`. This adds a translation layer, makes stack traces slightly harder to follow, and means new developers may choose the wrong logger. Both are technically correct (no `console.log`), but the split violates "single log sink" intent.
- **Recommendation:** Standardize on one interface. The object-style (`logger.info({ msg, ...ctx })`) is more structured and idiomatic for JSON logging. Migrate `utils/logger.ts` to export a default (or vice versa) and remove the wrapper. Update all import sites.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-007: `eslint-disable-next-line` suppressing react-hooks/exhaustive-deps
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** The `useWorkItems` hook suppresses the exhaustive-deps rule by manually enumerating `filters.status`, `filters.type`, `filters.priority`, `filters.source`, `filters.page`, `filters.limit` as dependencies instead of passing the `filters` object directly. If a new field is added to `WorkItemFilters`, it will silently not trigger re-fetches. The comment doesn't explain why the object reference is not used (identity equality concern?). CLAUDE.md: "No eslint-disable unless the error is intentionally suppressed" — this case lacks a justification comment.
- **Recommendation:** Either (a) memoize `filters` with `useMemo` in the calling component and pass the memoized reference; or (b) add a comment explaining why enumeration is preferable (`// Intentional: object reference changes on every render, individual fields are stable`).

- **Files:** `Source/Frontend/src/components/PriorityBadge.tsx`, `StatusBadge.tsx`, `TypeBadge.tsx`, `Layout.tsx`
- **Detail:** These components have `Verifies:` traceability comments but no corresponding `tests/components/{Name}.test.tsx` files.
