## Findings

### QO-001: `/api/search` route not wired — tests explicitly document failure
- **Severity:** P1
- **Category:** untested / spec-drift
- **File:** `Source/Backend/src/app.ts` (missing route registration) / `Source/Backend/tests/routes/search.test.ts:1-7`
- **Detail:** `GET /api/search` is required by `FR-dependency-search` to power the DependencyPicker typeahead. A `search.test.ts` file exists and traces `FR-dependency-search`, causing the traceability enforcer to report PASS. However, the test file opens with an explicit comment: *"the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests will FAIL until the route is implemented."* The `DependencyPicker` component will therefore fail at runtime when users attempt to add dependencies — the typeahead will never return results.
- **Recommendation:** Create `Source/Backend/src/routes/search.ts` implementing `GET /api/search?q=<query>` against the workItemStore, register it in `app.ts` as `app.use('/api/search', searchRouter)`. The test file already specifies the full contract (title/description match, {data:[]}, soft-deleted exclusion, empty-query guard).
- **Cross-ref:** security (unbounded search potential), TheFixer team

- **Category:** architecture-violation / spec-drift
- **File:** `Teams/TheInspector/inspector.config.yml:41-44`

The `portal/` directory contains 30 source files and 15 test files implementing FR-033 through FR-089 (orchestrated cycles, dev-cycle traceability, orchestrator dashboard, dependency linking for the portal app, duplicate/deprecated status, image upload). - **Cross-ref:** quality-oracle future runs

### QO-003: `POST /api/work-items/:id/dependencies` returns wrong response shape
- **Severity:** P2
- **Category:** spec-drift / architecture-violation
- **File:** `Source/Backend/src/routes/workflow.ts:324`
- **Detail:** `Source/Shared/api-contracts.md` specifies the Add Dependency response as `{data: WorkItem}` (201 Created). The actual implementation returns `res.json(link)` where `link` is a `DependencyLink` object — not the updated WorkItem, not wrapped in `{data:}`. Any frontend code or API client expecting `{data: WorkItem}` will receive an unexpected shape and potentially crash or silently discard the result.
- **Recommendation:** Change the handler in `workflow.ts` to: (1) call `addDependency`, (2) retrieve the updated item via `store.findById(id)` with dependency hydration, (3) respond `res.status(201).json({ data: updatedItem })`. Update `tests/routes/dependencies.test.ts` expectations to match.
- **Cross-ref:** TheFixer

### QO-004: `pending_dependencies` status referenced in contracts but absent from enum
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Shared/types/workflow.ts:214` / `Source/Shared/api-contracts.md:182`
- **Detail:** `api-contracts.md` states: *"If transitioning to `approved` and `blockedBy` contains any unresolved items → set status to `pending_dependencies` instead."* The `WorkItemStatus` enum has no `PendingDependencies` value. The dispatch route (`workflow.ts:231`) instead returns HTTP 400 — a different contract (error vs. state transition). This creates a spec-to-implementation gap: an approved item with unresolved blockers cannot be tracked at `pending_dependencies`; it simply fails dispatch with no persisted state change. The auto-advance cascade (`onItemResolved`) also cannot auto-advance from `pending_dependencies` to `approved` because the status is unrepresentable.
- **Recommendation:** Add `PendingDependencies = 'pending_dependencies'` to `WorkItemStatus`; add it to `VALID_STATUS_TRANSITIONS` (`[WorkItemStatus.Approved]: [WorkItemStatus.InProgress, WorkItemStatus.PendingDependencies]`); update dispatch logic to set this status instead of returning 400; implement auto-advance in `onItemResolved`. This is a coordinate-first change (Shared types + backend + frontend).
- **Cross-ref:** api-contract agent, TheFixer

### QO-006: Two `eslint-disable-next-line react-hooks/exhaustive-deps` suppressions in production hooks
- **Severity:** P3
- **Category:** pattern-violation
- **Files:** `Source/Frontend/src/hooks/useWorkItems.ts:63` / `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** These suppressions hide potential stale closure bugs. React hooks exhaustive-deps warnings exist specifically to prevent bugs where a callback or effect captures an outdated variable. Suppressing without explicit reasoning is a technical debt marker. Neither suppression has a comment explaining why the exclusion is safe.
- **Recommendation:** Investigate each suppression: (1) if the exclusion is intentional (e.g., mount-only effect), add an inline comment explaining the invariant; (2) if not intentional, fix the hook to include the missing dependency. Do not leave silent suppressions.
- **Cross-ref:** frontend-coder
