## Findings

### QO-001: Traceability Enforcer Blind to `portal/` — False-Pass Verification Gate
- **Severity:** P2
- **Category:** architecture-violation / tooling
- **File:** `tools/traceability-enforcer.py:78` — `source_dirs = ["Source", "E2E"]`
- **Detail:** The standard verification gate (`python3 tools/traceability-enforcer.py`) silently selects
  the most-recently-modified plan (`Plans/self-judging-workflow/requirements.md`, 13 requirements in
  `Source/`) and reports **PASS**. However, this repository contains a second application in `portal/`
  that implements 7 additional plan files (FR-001..FR-069, FR-dependency-*, FR-DUP-*, FR-07x..FR-09x).
  Running the enforcer against each of those plans with `--file` reports 7–32 "missing" FRs each,
  because the enforcer never scans `portal/`. All those FRs are **actually implemented** with `// Verifies:`
  comments in `portal/` — but they are invisible to the gate.

  **Impact:** Any agent that runs the default verification gate gets a false confidence signal. An agent
  could ship portal code with zero traceability comments and the gate would still report PASS.

- **Recommendation:**
  1. Add `"portal"` to the `source_dirs` list in `tools/traceability-enforcer.py` (line 78).
  2. Update `Teams/TheInspector/inspector.config.yml` `source.dirs` to include `portal/`.
  3. Update CLAUDE.md verification gate docs to note multi-plan enforcement: `python3 tools/traceability-enforcer.py --file Plans/<plan>/requirements.md`.
- **Fix team:** TheFixer (tools/ change, not Source/)

### QO-002: Direct DB Calls in Route Handler — Architecture Violation
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `portal/Backend/src/routes/teamDispatches.ts:37, 41, 72`
- **Detail:** The team dispatches route handler calls `db.prepare(...)` directly inside `router.get`
  and `router.post` handlers — there is no `TeamDispatchService` or equivalent service-layer abstraction.
  CLAUDE.md mandates: *"No direct DB calls from route handlers — use the service layer."*

  ```ts
  // Line 37 — route handler directly calls db:
  rows = db.prepare(`SELECT * FROM team_dispatches WHERE team = ? ...`).all(team, limitNum);

  // Line 72 — route handler directly calls db:
  db.prepare(`INSERT INTO team_dispatches ...`).run(...);
  ```

  This is the **only** route file in either `Source/` or `portal/` that violates this rule.

- **Recommendation:** Extract a `teamDispatchService.ts` with `listDispatches(team?, limit)` and
  `createDispatch(data)` functions; import and call those from the route handler.
- **Fix team:** TheFixer (portal/Backend/)

### QO-004: Two `eslint-disable` Suppressions for `react-hooks/exhaustive-deps`
- **Severity:** P2
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Both files suppress ESLint's `react-hooks/exhaustive-deps` rule. This rule exists to
  prevent stale-closure bugs. Suppressing it without documenting *why* the dependency is intentionally
  omitted (and confirming the behavior is correct) is a known source of hard-to-diagnose bugs in React.

  ```ts
  // DependencyPicker.tsx:82
  // eslint-disable-next-line react-hooks/exhaustive-deps
  [currentItemId],

  // useWorkItems.ts:63
  // eslint-disable-next-line react-hooks/exhaustive-deps
  ```

  Neither suppression has an explanatory comment justifying why the missing dependency is safe.

- **Recommendation:** For each suppression: either (a) add the missing dependency to the array (preferred),
  or (b) add a comment explaining the intentional omission (e.g., `// currentItemId is stable ref`).
- **Fix team:** TheFixer (Source/Frontend/)

### QO-007: Silent Search Error in DependencyPicker — No Log Emitted
- **Severity:** P4
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/components/DependencyPicker.tsx:56-57`
- **Detail:** The catch block for the search API call is documented as intentional:
  ```ts
  } catch {
    // Search errors are intentionally suppressed: UI falls back to empty results
    setSearchResults([]);
  }
  ```
  Per CLAUDE.md, *"every catch block must either re-throw, log with full context, or explicitly
  document why the error is intentionally suppressed."* The documentation comment satisfies the
  rule's third branch. However, no log is emitted — a degraded typeahead silently returns no results
  with no diagnostic signal in production logs.
- **Recommendation:** Add a `console.warn` or logger call (if a frontend logger exists) to emit
  something observable: `logger.warn('DependencyPicker search failed', err)`.
