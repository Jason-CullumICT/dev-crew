### QO-001: Traceability Enforcer Has a Blind Spot for `portal/` and `platform/`
- **Severity:** P2
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py`, `Teams/TheInspector/inspector.config.yml`
- **Detail:** The enforcer scans only `Source/` and `E2E/` (hard-coded in the tool and reflected in `inspector.config.yml source.dirs: ["Source/"]`). The `dev-workflow-platform.md` spec (FR-001 to FR-069 + 15 FR-dependency-* requirements) is implemented across **113 TypeScript files** in `portal/`. The `tiered-merge-pipeline.md` spec (FR-TMP-001 to FR-TMP-010) is implemented in `platform/orchestrator/`. Running `python3 tools/traceability-enforcer.py` without flags picks up `Plans/self-judging-workflow/requirements.md` (most recently modified) and reports PASSED — masking the fact that two full specification documents have zero enforcer coverage.
  - `portal/` has 653 `// Verifies:` comments across 50 files — the work is done but not checked
  - Running `python3 tools/traceability-enforcer.py --file Specifications/dev-workflow-platform.md` reports **76 MISSING** (because it still scans only `Source/`)
  - Running against `Specifications/tiered-merge-pipeline.md` reports **13 MISSING** (all FR-TMP-* plus 3 NFR regex false-positives)
- **Recommendation:** Add `portal/` to `source.dirs` in `inspector.config.yml` and update the enforcer to iterate all `Plans/*/requirements.md` files (not just the most recently modified one). Alternatively add a second enforcer run step: `python3 tools/traceability-enforcer.py --file Specifications/dev-workflow-platform.md` targeting `portal/`. Also add a `platform/` note acknowledging FR-TMP-* are tested via `platform/orchestrator/lib/workflow-engine.test.js`.
- **Cross-ref:** TheFixer for the enforcer fix; TheATeam for `inspector.config.yml` update

### QO-002: Architecture Violation — Direct DB Calls in Route Handler
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `portal/Backend/src/routes/teamDispatches.ts:37,41,72`
- **Detail:** The team dispatches route handler calls `db.prepare(...).all(...)` and `db.prepare(...).run(...)` directly — three direct SQL calls at lines 37, 41, and 72. CLAUDE.md architecture rule is explicit: **"No direct DB calls from route handlers — use the service layer."** No service module exists for team dispatches; the DB layer is embedded inline in the router. This file also has no `// Verifies:` comment (see QO-005).
  ```typescript
  // portal/Backend/src/routes/teamDispatches.ts:37
  rows = db.prepare(
    `SELECT * FROM team_dispatches WHERE team = ? ORDER BY dispatched_at DESC LIMIT ?`
  ).all(team, limitNum) as TeamDispatch[];
  ```
- **Recommendation:** Extract a `teamDispatchService.ts` with `listDispatches(filter)` and `createDispatch(data)` functions. Route handler should call service only. Add `// Verifies: FR-XXX` once the owning spec FR is assigned (or add a new FR to the spec).
- **Cross-ref:** [ESCALATE → TheFixer] for the service extraction

### QO-003: Silent Error Swallowing — Empty `.catch()` in Production Component
- **Severity:** P2
- **Category:** pattern-violation / architecture-violation
- **File:** `portal/Frontend/src/components/common/RepoSelector.tsx:20`
- **Detail:** The component silently swallows a repository-list API failure:
  ```typescript
  repos.list().then((r) => setKnownRepos(r.data)).catch(() => {})
  ```
  CLAUDE.md states: **"Never swallow errors silently — every `catch` block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."** No comment explains the intent. If `repos.list()` fails (network error, backend down), the user sees no indicator and the repo selector silently falls back to the hardcoded default without surfacing the issue.
- **Recommendation:** Replace with `.catch((err) => { console.warn('repos.list failed, using defaults', err) })` at minimum, or propagate to the existing `error` state so the UI can surface it.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-010: Enforcer Regex Generates False-Positive Requirement IDs
- **Severity:** P4
- **Category:** pattern-violation
- **File:** `tools/traceability-enforcer.py:64`
- **Detail:** The enforcer regex `FR-[A-Z0-9-]+` matches seed data IDs in spec prose. The text _"BUG-0010 blocked_by BUG-0003/0004/0005/0006/0007; FR-0004 blocked_by FR-0003; FR-0005 blocked_by FR-0002"_ (from `FR-dependency-seed`) produces false requirement IDs: `FR-0002`, `FR-0003`, `FR-0004`, `FR-0005`, `FR-0007`. These appear as "MISSING" in enforcer output even though they are seed data item IDs, not requirement identifiers. Similarly `FR-1`, `FR-2`, `FR-3` are extracted from tiered-merge-pipeline NFR numbering.
- **Recommendation:** Tighten the enforcer regex to require the ID to appear as a table cell or at line start: `^|\s|\|)FR-[A-Z][A-Z0-9-]+` or validate that extracted IDs match known naming patterns (`FR-\d{3,}`, `FR-WF-\d+`, `FR-TMP-\d+`, `FR-[a-z]+-[a-z]+`).
