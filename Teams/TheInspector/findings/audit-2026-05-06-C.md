### QO-001: FR-dependency-search — `/api/search` Not Mounted in Source/Backend
- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts`
- **Detail:**  
  The spec `FR-dependency-search` requires `GET /api/search?q=` for cross-entity typeahead. `Source/Backend/tests/routes/search.test.ts` has 5 tests covering this endpoint — and explicitly documents (line 3-6) that they **will fail until the route is wired**.  
  `Source/Backend/src/app.ts` mounts only: `workItemsRouter`, `workflowRouter`, `dashboardRouter`, `intakeRouter`. There is no `/api/search` route. The 5 search tests will produce failures on `npm test`.
- **Recommendation:** Create `Source/Backend/src/routes/search.ts` implementing `GET /api/search?q=` with title/description fuzzy match against the workItemStore, and mount it in `app.ts` as `app.use('/api', searchRouter)`.
- **Cross-ref:** TheFixer — backend implementation work.

### QO-002: Traceability Enforcer Scope Gap — 88% of Spec Surface Unvalidated
- **Severity:** P2
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py`
- **Detail:**  
  The enforcer targets `Plans/*/requirements.md` (picking the most recently modified file) and scans `Source/` + `E2E/` only. This leaves **three major spec + code pairings completely unvalidated**:
  1. `Specifications/dev-workflow-platform.md` (80+ FRs) → `portal/` codebase (1073 `Verifies:` comments, never checked)
  2. `Specifications/tiered-merge-pipeline.md` (10 FRs) → `platform/orchestrator/lib/` (no `Verifies:` comments at all)
  3. `Plans/dependency-linking/requirements.md` (16 FRs) → partially portal, partially Source/ — only enforced if it's the most-recently-modified requirements.md

  **Additional risk:** When all `requirements.md` files share the same mtime (e.g. after `git clone`), the enforcer's file-picking is non-deterministic.
- **Recommendation:**  
  1. Extend the enforcer to support multiple target directories (`Source/`, `portal/`, `platform/`).  
  2. Add a `config.specs.all_dirs` field to `inspector.config.yml` listing all spec→code pairs.  
  3. Or: use `--file Specifications/dev-workflow-platform.md` flag with separate enforcer invocations per product.  
  4. Fix mtime tie-breaking: use alphabetical fallback and log which file was selected.
- **Cross-ref:** TheFixer — tooling improvement.

### QO-008: eslint-disable Suppression in Production Frontend Code
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**  
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`  
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:**  
  Both suppressions disable the `react-hooks/exhaustive-deps` rule, which guards against stale closure bugs in `useEffect`/`useCallback` dependencies. Suppressing without documented reasoning creates a maintenance hazard: the hook dependency may be intentionally excluded (infinite loop avoidance) or an actual bug. Neither comment explains why the suppression is safe.
- **Recommendation:** Add a brief comment explaining why the dependency is excluded (e.g., `// excluded: adding 'fetchItems' would cause infinite re-fetch; function is stable`). If the exclusion is incorrect, add the dependency and fix the hook logic.

### QO-009: Silent `.catch(() => ({}))` in API Client
- **Severity:** P3
- **Category:** pattern-violation / architecture-violation
- **File:** `Source/Frontend/src/api/client.ts:26`
- **Detail:**  
  ```ts
  const body = await response.json().catch(() => ({}));
  ```  
  JSON parse errors (malformed response body) are silently discarded. The outer code falls back to `body.message ?? \`Request failed: ${response.status}\``. While functional, the architecture rule states "Never swallow errors silently — every catch block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed." No documentation exists here.
- **Recommendation:** Add a comment: `// Intentionally suppressed — JSON parse failure falls back to HTTP status message` to satisfy the architecture rule.

### QO-012: Route Handlers Call workItemStore Directly (Bypasses Service Layer)
- **Severity:** P4
- **Category:** architecture-violation
- **Files:** `Source/Backend/src/routes/workItems.ts`, `Source/Backend/src/routes/workflow.ts`
- **Detail:**  
  Both route files `import * as store from '../store/workItemStore'` and call CRUD operations directly. The architecture rule states "No direct DB calls from route handlers — use the service layer." While the store is in-memory (not a true DB), the same coupling concern applies: route handlers contain data-access logic (pagination math, filter conditions) that should live in a service.  
  Contrast: `routeWorkItem()`, `assessWorkItem()`, `assignTeam()` are properly in `services/router.ts` and `services/assessment.ts`.
- **Recommendation:** Create `Source/Backend/src/services/workItemService.ts` with functions for list, getById, create, update, softDelete — and have route handlers call service functions only.
