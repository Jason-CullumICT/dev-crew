## Findings

### QO-001: Architecture Violation — Direct DB Calls from Route Handlers in portal/
- **Severity:** P2
- **Category:** architecture-violation
- **Files:** `portal/Backend/src/routes/bugs.ts`, `featureRequests.ts`, `cycles.ts`, `pipelines.ts`, `dashboard.ts`, `teamDispatches.ts`, `learnings.ts`, `search.ts`, `features.ts`
- **Detail:** 51 direct `getDb()` invocations are scattered across 9 route handler files in `portal/Backend/src/routes/`. This violates the CLAUDE.md architecture rule: *"No direct DB calls from route handlers — use the service layer."* The portal `services/` directory exists (bugService, cycleService, featureRequestService, etc.) but routes bypass it for many operations, embedding SQL directly in request handlers. This means business logic is duplicated across service and route layers, untestable in isolation, and bypasses any transactional guarantees the service layer provides.
- **Recommendation:** Move all `getDb()` / `db.prepare()` calls from route files into the appropriate service or a new thin repository layer. Route handlers should call service functions only. Refactoring can be phased — prioritise routes that contain non-trivial logic (cycles, pipelines, teamDispatches).
- **Cross-ref:** TheFixer (bug fixes + refactoring owner)

### QO-007: Pattern Violation — eslint-disable in Production Frontend Code
- **Severity:** P4
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Both files contain `// eslint-disable-next-line react-hooks/exhaustive-deps`. This suppresses the React hooks exhaustive-deps lint rule, which guards against stale-closure bugs. Both suppressions appear to be masking missing hook dependencies rather than intentional omissions.
- **Recommendation:** Fix the underlying hook dependency arrays and remove the eslint-disable comments. If the suppression is intentional, add a comment explaining why the dependency is safe to omit.

### QO-008: Technical Debt — Duplicate Logger Abstraction in Source/Backend
- **Severity:** P4
- **Category:** pattern-violation
- **Files:** `Source/Backend/src/logger.ts`, `Source/Backend/src/utils/logger.ts`
- **Detail:** Two logger files exist in Source/Backend:
  - `src/utils/logger.ts` — the actual structured JSON logger implementation
  - `src/logger.ts` — a re-export compatibility wrapper around `utils/logger.ts`
  This wrapper exists because two different coders imported logger from different paths. It's functional but adds indirection and confusion about the canonical import path.
- **Recommendation:** Standardise all imports to `src/utils/logger.ts` and delete `src/logger.ts`. This is a low-risk refactor — search for all imports of `'../logger'` or `'./logger'` in `src/` and update them.
