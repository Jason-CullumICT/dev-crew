## Findings

### QO-001: FR-070 ID Collision Between Plans
- **Severity:** P1
- **Category:** spec-drift / traceability-integrity
- **Files:**
  - `Plans/image-upload/requirements.md`: FR-070 = "Add `ImageAttachment` shared type"
  - `Plans/orchestrator-cycle-dashboard/requirements.md`: FR-070 = "Create `OrchestratorCyclesPage`"
  - `portal/Frontend/src/components/orchestrator/types.ts:1`: `// Verifies: FR-070` (points to OrchestratorCyclesPage meaning)
  - `portal/Frontend/src/api/client.ts`: also references FR-070 for orchestrator
- **Detail:** Two separate plans both assign FR-070 to unrelated features. The `// Verifies: FR-070` comment in portal/ is ambiguous — it resolves to the orchestrator-cycle-dashboard interpretation, silently ignoring the image-upload interpretation. Any reader (human or automated) following FR-070 will find conflicting specs. The dependency-linking plan compounds this by citing "Specifications/dev-workflow-platform.md (FR-070 — FR-085)" as its spec reference, but those IDs don't exist in that file at all.
- **Recommendation:** Assign unique IDs to all features added after the baseline spec. Retroactively: rename image-upload features FR-IMG-001..FR-IMG-020, orchestrator-cycle features FR-OCD-001..FR-OCD-007. Update all `// Verifies:` comments. Add a PR gate that rejects new `FR-NNN` IDs already assigned in any plan.
- **Cross-ref:** TheFixer — code change needed in portal/Frontend to update traceability comments.

### QO-004: FR-dependency-api-types Incomplete — `as any` Cast in DependencyPicker
- **Severity:** P2
- **Category:** spec-drift / architecture-violation
- **File:** `portal/Frontend/src/components/shared/DependencyPicker.tsx:291-293`
- **Detail:** The `UpdateBugInput` and `UpdateFeatureRequestInput` types in `portal/Shared/api.ts` lack `blocked_by?: string[]`. The requirement (FR-dependency-api-types) explicitly calls for this field so that frontend code can call `PATCH` with dependency arrays without type gymnastics. The DependencyPicker works around the missing type by using `as any` on lines 291 and 293 — a TypeScript bypass that loses type safety and triggers the architecture rule "no `as any` casts needed in frontend for dependency fields." The dependency-linking plan's own delta table marks this "❌ Missing."
- **Recommendation:**
  1. Add `blocked_by?: string[]` to `UpdateBugInput` and `UpdateFeatureRequestInput` in `portal/Shared/api.ts`
  2. Remove `as any` casts from `DependencyPicker.tsx:291-293`
  3. Add `// Verifies: FR-dependency-api-types` to the modified types
- **Cross-ref:** TheFixer — two-file change, Shared + Frontend.

### QO-005: Silent Error Swallowing — Architecture Rule Violation
- **Severity:** P2
- **Category:** architecture-violation
- **Files:**
  - `portal/Frontend/src/components/feature-requests/FeatureRequestDetail.tsx:80` — `.catch(() => {})`
  - `portal/Frontend/src/components/common/RepoSelector.tsx:20` — `.catch(() => {})`
  - `portal/Frontend/src/components/bugs/BugDetail.tsx:82` — `.catch(() => {})`
- **Detail:** CLAUDE.md rule: _"Never swallow errors silently — every `catch` block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."_ All three files use empty arrow-function catch blocks that discard the error entirely. When these fire (e.g., network failure during image re-fetch or repo listing), the UI goes silent — no error banner, no console output, no structured log. Debugging becomes impossible post-production.
- **Recommendation:** Replace each `.catch(() => {})` with at minimum `.catch((err) => logger.warn({ err }, 'non-critical fetch failed'))` or set an error state that surfaces a dismissible warning in the UI.
- **Cross-ref:** TheFixer.

### QO-010: ESLint-Disable Suppressions in Hooks (4 Instances)
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `portal/Frontend/src/hooks/useApi.ts:35` — `eslint-disable-next-line react-hooks/exhaustive-deps`
  - `portal/Backend/src/middleware/errorHandler.ts:21` — `eslint-disable-line @typescript-eslint/no-unused-vars`
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Each suppression hides a potential stale-closure or unused-variable issue. The `exhaustive-deps` suppressions are the most risky: a hook that runs an effect with a stale dep array can silently fail to re-fetch or re-subscribe. The `no-unused-vars` suppression in errorHandler.ts hides that the `next` parameter is kept only for Express's 4-arg error handler signature — a legitimate reason that deserves an inline comment explaining why.
- **Recommendation:** For `exhaustive-deps`: restructure the dependency array or use `useCallback` to stabilize refs. For errorHandler: replace with `_next` (underscore-prefixed parameter) or add `// Express requires 4-arg signature for error handlers` comment.
