# Quality Oracle Audit — 2026-05-18

**Grade: C** (2 P1s, 4 P2s — exceeds B-grade threshold of max_p1:0, max_p2:8)

## Executive Summary

The Source/ codebase implements the **Self-Judging Workflow Engine** cleanly: structured logging, Prometheus metrics for core ops, service-layer separation, no console.log, no empty catch blocks. Within its own scope the implementation has strong hygiene.

However, there is a **fundamental spec-scope mismatch**: `Specifications/` defines two unimplemented applications (dev-workflow-platform FR-001–069, tiered-merge-pipeline FR-TMP-001–010) while Source/ implements the Workflow Engine whose requirements live in `Plans/`, not `Specifications/`. The traceability enforcer produces a false PASS because it only scans a single plan file.

There are also two concrete implementation gaps: the search endpoint is wired in tests but missing from `app.ts`, and the `pending_dependencies` status that the spec requires is absent from the enum.

## Findings

### QO-001: `GET /api/search` not wired — intentionally failing tests
- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts:22-31`, `Source/Backend/tests/routes/search.test.ts:1-6`
- **Detail:** `GET /api/search` (FR-dependency-search) has a full test suite (5 test cases) that explicitly comments `"the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."` The endpoint is referenced by `FR-dependency-endpoints` (DependencyPicker typeahead) but absent from `app.ts`. The traceability enforcer passes because `FR-dependency-search` appears in the test file, but the endpoint doesn't exist.
- **Recommendation:** Add `GET /api/search` handler (filter `store.findAll()` by `q` param on title/description) and register it in `app.ts`. The test contract is already defined.
- **Cross-ref:** TheFixer (implementation gap)

### QO-002: Specifications/dev-workflow-platform.md — 69 FRs with 0% coverage
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md`
- **Detail:** FR-001 through FR-069 define a complete development workflow platform (feature requests, bug reports, development cycles, pipeline runs, CI/CD, approvals, learnings, feature browser). None of these 69 requirements have any `// Verifies: FR-0XX` comment in Source/. The Source/ implements the Self-Judging Workflow Engine instead. This is by design — the platform is being built to build the platform — but it means Specifications/ is not the source of truth for the current implementation.
- **Recommendation:** Either (a) add a `// Spec status: PLANNED — not yet implemented` header to dev-workflow-platform.md to signal intent, or (b) update the traceability enforcer to report on Specifications/ separately with an "implementation pending" category so reviewers see the gap clearly.
- **Cross-ref:** requirements-reviewer

### QO-004: Traceability enforcer gives false PASS — only scans 13 FRs
- **Severity:** P2
- **Category:** architecture-violation / spec-drift

It outputs `TRACEABILITY PASSED: All requirements have implementation references.` — but it completely ignores the 95 FRs in `Specifications/`. ### QO-005: `pending_dependencies` status missing from WorkItemStatus enum
- **Severity:** P2
- **Category:** spec-drift / architecture-violation
- **File:** `Source/Shared/types/workflow.ts:5-15`, `Source/Backend/src/routes/workflow.ts:230-244`
- **Detail:** FR-dependency-dispatch-gating specifies: *"Status transitions to `approved`/`in_development` check all blockers; unresolved blockers → set to `pending_dependencies` instead"*. The `WorkItemStatus` enum has no `PendingDependencies` value. The dispatch route currently returns `400` when blockers exist (gating the dispatch action) rather than silently transitioning the item to `pending_dependencies` with a 200. The traceability comment on line 213 of workflow.ts says `"Support for pending_dependencies blocking"` but the enum member is absent.
- **Recommendation:** Add `PendingDependencies = 'pending-dependencies'` to `WorkItemStatus`, add it to `VALID_STATUS_TRANSITIONS` (`Approved → PendingDependencies`, `PendingDependencies → InProgress`), and update the dispatch route to set status = `pending_dependencies` instead of returning 400.
- **Cross-ref:** TheFixer, api-contract (shared type change)

### QO-007: No Prometheus route latency histogram
- **Severity:** P3
- **Category:** architecture-violation
- **File:** `Source/Backend/src/app.ts:15-19`, `Source/Backend/src/metrics.ts`
- **Detail:** CLAUDE.md states *"Auto-collect route latency via middleware"* and *"Prometheus-compatible metrics at GET /metrics"*. The architecture rule says routes need observability. `app.ts` has only a request-logging middleware (debug level); no histogram records route latency. FR-004 (dev-workflow-platform) also specifies `"route latency histogram"` for the middleware pipeline.
- **Recommendation:** Add an `http_request_duration_seconds` Histogram to `metrics.ts` and a middleware in `app.ts` that records duration per method+route on `res.on('finish')`.
- **Cross-ref:** TheFixer

### QO-008: No OpenTelemetry tracing implementation
- **Severity:** P3
- **Category:** architecture-violation
- **File:** `Source/Backend/src/app.ts`
- **Detail:** CLAUDE.md architecture rules: *"Use OpenTelemetry for distributed tracing"*, *"Auto-instrument HTTP, database, and framework calls"*, *"Propagate W3C `traceparent` header across service boundaries"*. No `@opentelemetry/*` imports exist anywhere in Source/Backend/src/. Trace/span IDs do not appear in logs. FR-WF-013 only specifies structured logging + metrics (implemented ✓) but the CLAUDE.md observability rule is broader.
- **Recommendation:** Add `@opentelemetry/api`, `@opentelemetry/sdk-node`, and `@opentelemetry/auto-instrumentations-node` packages; initialize OTel in a separate `telemetry.ts` loaded before `app.ts`; propagate `traceparent` via express middleware.
- **Cross-ref:** TheFixer

### QO-013: Low Verifies density in test cases
- **Severity:** P4
- **Category:** spec-drift
- **Detail:** Architecture rule: *"Every FR needs a test with `// Verifies: FR-XXX`"*. File-level Verifies comment ratios:

| File | Verifies / Tests |
|------|-----------------|
| `workItems.test.ts` | 6 / 56 (11%) |
| `search.test.ts` | 6 / 39 (15%) |
| `intake.test.ts` | 3 / 22 (14%) |
| `dashboard.test.ts` (routes) | 4 / 22 (18%) |
| `integration.test.tsx` | 10 / 53 (19%) |

Individual test `it()` blocks within a file lack per-test `// Verifies:` tags even when the file header has one. The traceability enforcer only checks that the FR ID appears somewhere in the file — it does not verify per-test coverage.
- **Recommendation:** Add `// Verifies: FR-XXX` to individual `it()` blocks, especially in tests/routes/workItems.test.ts and tests/routes/search.test.ts.
