## QO-001: `GET /api/search` Route Unregistered in Production

- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts` (route absent), `Source/Backend/tests/routes/search.test.ts:1–6`
- **Detail:** `FR-dependency-search` requires a cross-entity search endpoint. The test file `search.test.ts` explicitly documents the gap:
  > *"As of this review cycle the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."*
  The route is missing from `app.ts` entirely — no import, no `app.use('/api/search', ...)`. All 5 tests in `search.test.ts` will fail when the test suite is run.
- **Recommendation:** Create `Source/Backend/src/routes/search.ts` with a `GET /api/search?q=` handler that filters non-deleted work items by title/description, then register it in `app.ts` with `app.use('/api', searchRouter)`.
- **Cross-ref:** QO-003 (dependency-metrics also partially unimplemented)

## QO-002: Traceability Enforcer Blind to `portal/` and `platform/`

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `tools/traceability-enforcer.py:78` (`source_dirs = ["Source", "E2E"]`)
- **Detail:** The enforcer hardcodes only `Source/` and `E2E/` as scan targets. Two entire application trees carry `// Verifies:` comments and implement spec requirements, but are never checked:
  - `portal/` implements `Specifications/dev-workflow-platform.md` (FR-001–069 + FR-dependency-*)
  - `platform/` implements `Specifications/tiered-merge-pipeline.md` (FR-TMP-001–010)
  
  When run without arguments (`python3 tools/traceability-enforcer.py`), the tool reports **TRACEABILITY PASSED** against `Plans/self-judging-workflow/requirements.md`. This is a false green — it masks whether the much larger portal and platform spec surfaces are actually covered.
  
  Running the enforcer against `Specifications/dev-workflow-platform.md` reveals 76 missing FRs (all 73 numeric FRs in that spec), because it scans Source/ instead of portal/.
- **Recommendation:** Extend `source_dirs` to `["Source", "portal", "platform", "E2E"]`. Alternatively, add an `inspector.config.yml` override for `source.dirs` and make the enforcer read it.
- **Cross-ref:** QO-007 (fragile plan selection also affects enforcer accuracy)

## QO-003: `dependencyCheckDuration` Histogram Missing from Metrics

- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/metrics.ts:1–62`
- **Detail:** `FR-dependency-metrics` in `dev-workflow-platform.md` specifies 4 Prometheus metrics:
  1. `dependencyOperations` counter ✅ (line 40)
  2. `dispatchGatingEvents` counter ✅ (line 48)
  3. **`dependencyCheckDuration` histogram** ❌ MISSING
  4. `cycleDetectionEvents` counter ✅ (line 56)
  
  The histogram would measure latency of dependency readiness checks (BFS traversal). Without it, there is no latency visibility for `hasUnresolvedBlockers()` calls, which can be expensive under deep dependency graphs. The acceptance criterion explicitly requires "All 4 metrics visible at `GET /metrics`".
- **Recommendation:** Add to `metrics.ts`:
  ```ts
  // Verifies: FR-dependency-metrics — dependency_check_duration histogram
  export const dependencyCheckDurationHistogram = new Histogram({
    name: 'dependency_check_duration_seconds',
    help: 'Duration of dependency readiness checks (BFS traversal)',
    labelNames: ['item_type'] as const,
    buckets: [0.001, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25],
    registers: [registry],
  });
  ```
  Then instrument `hasUnresolvedBlockers()` in `services/dependency.ts`.
- **Cross-ref:** QO-001 (FR-dependency-search also partially unimplemented)

## QO-007: Traceability Enforcer Uses Most-Recently-Modified Plan (Fragile)

- **Severity:** P3
- **Category:** architecture-violation
- **File:** `tools/traceability-enforcer.py:49–57`
- **Detail:** When run without `--plan` or `--file`, the enforcer picks the most recently modified `requirements.md` across all of `Plans/`:
  ```python
  return max(req_files, key=os.path.getmtime)
  ```
  With a single commit (`7ff40d0 2026-05-19 Inspector audit: initialize`) all files have the same mtime, making selection non-deterministic. In normal workflow, updating any plan's requirements.md would silently redirect enforcement to that plan. The CLAUDE.md verification gates run this tool without arguments — this means the gate's target changes implicitly whenever any plan is touched.
- **Recommendation:** Configure a `specs.enforcer_target` in `inspector.config.yml` (e.g., `Plans/self-judging-workflow/requirements.md`) and make the enforcer prefer that over mtime. Or add a `tools/enforcer-config.txt` file listing the canonical target paths to check.
