### QO-003: Portal Backend Routes Bypass Service Layer (Architecture Violation — Widespread)
- **Severity:** P2
- **Category:** architecture-violation
- **Files:** All 9 portal route files
  - `portal/Backend/src/routes/featureRequests.ts` (17 direct DB calls)
  - `portal/Backend/src/routes/bugs.ts` (16 direct DB calls)
  - `portal/Backend/src/routes/cycles.ts` (11 direct DB calls)
  - `portal/Backend/src/routes/pipelines.ts` (7 direct DB calls)
  - `portal/Backend/src/routes/search.ts` (4 direct DB calls)
  - `portal/Backend/src/routes/dashboard.ts` (4 direct DB calls)
  - `portal/Backend/src/routes/learnings.ts` (4 direct DB calls)
  - `portal/Backend/src/routes/features.ts` (4 direct DB calls)
  - `portal/Backend/src/routes/teamDispatches.ts` (7 direct DB calls)
- **Detail:** Every portal backend route directly imports `getDb` from `database/connection` and runs raw SQL queries inside the request handler. Architecture rule: "No direct DB calls from route handlers — use the service layer." Only `cycles.ts` partially follows the rule (also imports `feedbackService`).
- **Recommendation:** Extract DB logic into service modules under `portal/Backend/src/services/`. Each route should call a typed service function; service functions own the SQL. This is a medium-effort refactor — prioritise high-churn routes first (featureRequests, bugs, cycles). Route via TheFixer.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-004: Source/ Routes Bypass Service Layer (Architecture Violation)
- **Severity:** P2
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/routes/workItems.ts:12` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/workflow.ts:15` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/intake.ts:4` — `import * as store from '../store/workItemStore'`
- **Detail:** Three route handlers in Source/ import directly from the data store, bypassing any service layer. The `workItemStore` functions are essentially the data access layer; routes should call service-layer functions that wrap store operations. `intake.ts` is the worst offender — it ONLY uses the store, with no service indirection. Although this is an in-memory store (not SQL), the architecture rule is explicit: service layer is mandatory between routes and data.
- **Recommendation:** Introduce `Source/Backend/src/services/workItemService.ts` wrapping `workItemStore` operations. Update the three route files to import from the service module. Move business logic (metrics increment, change tracking) into the service. Route via TheFixer.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-007: 113 console.log Calls in Platform Orchestrator
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `platform/orchestrator/lib/workflow-engine.js` (~113 occurrences)
- **Detail:** Architecture rule: "Use the project's logger abstraction, never `console.log`." The orchestrator has no logger abstraction and uses raw `console.log`/`console.error` throughout. This means no structured JSON, no log levels, no trace IDs in production output. This makes orchestrator log correlation with portal/backend traces impossible.
- **Recommendation:** Introduce a simple logger wrapper in `platform/orchestrator/lib/` (e.g., JSON output in NODE_ENV=production, pretty-print in dev). Replace `console.log` calls with structured log calls. Solo session required (platform/ is solo-session-only).

### QO-008: ESLint Suppressions Without Justification
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Two `react-hooks/exhaustive-deps` suppressions with no explanation comment. Per architecture rules: "Never swallow errors silently — every `catch` block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed." The same principle applies to linting suppressions.
- **Recommendation:** Either fix the exhaustive-deps issue (add the missing dependency to the deps array, or extract a ref/callback) OR add a comment explaining why the suppression is intentional (e.g., `// Only run on mount — exhaustive-deps would cause infinite re-fetch`).
