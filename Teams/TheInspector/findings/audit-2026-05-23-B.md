## Findings

### QO-001: Traceability Enforcer Blind to portal/ and platform/
- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py:69–98`
- **Detail:** The enforcer scans only `["Source", "E2E"]`. Two entire application codebases are excluded:
  - `portal/` implements FR-001–069 + FR-dependency-* (dev-workflow-platform spec). Running `python3 tools/traceability-enforcer.py --file Plans/dev-workflow-platform/requirements.md` reports **34 missing requirements** — false failures because the enforcer doesn't see `portal/`.
  - `platform/orchestrator/` implements FR-TMP-001–010 (tiered-merge-pipeline spec). No enforcer run targets this codebase.
  
  The verification gate in CLAUDE.md (`python3 tools/traceability-enforcer.py`) auto-selects `Plans/self-judging-workflow/requirements.md` (most recently modified) — it silently skips all portal and platform requirements. Any agent that runs only the default gate will see PASS while 95+ requirements are unverified.
- **Recommendation:** Extend `source_dirs` in `tools/traceability-enforcer.py` to include `["Source", "E2E", "portal", "platform"]`, OR add separate enforcer invocations per app in CLAUDE.md verification gates.
- **Cross-ref:** TheFixer (tooling fix); affects all teams using the gate.

### QO-002: `pending_dependencies` Status Referenced in Spec but Missing from Enum
- **Severity:** P1
- **Category:** spec-drift
- **File:** `Source/Shared/types/workflow.ts:5–16`, `Source/Shared/api-contracts.md:181–182`
- **Detail:** `api-contracts.md` specifies:
  > "If transitioning to `approved` and `blockedBy` contains any unresolved items → set status to `pending_dependencies` instead"
  > "When a blocker transitions to `completed`/`rejected`, auto-advance dependent from `pending_dependencies` to `approved`"

  `FR-dependency-dispatch-gating` (in Plans/dependency-linking/requirements.md) requires this status transition pattern. However:
  1. `WorkItemStatus` enum has **no `pending_dependencies` member** — the value `'pending-dependencies'` or `'pending_dependencies'` is never defined.
  2. `VALID_STATUS_TRANSITIONS` has no entry for pending_dependencies.
  3. The dispatch endpoint (`POST /:id/dispatch`) blocks dispatch with a `400` error instead of transitioning to pending_dependencies.
  4. The approve endpoint does not downgrade to pending_dependencies when blockers exist.

  The `// Verifies: FR-dependency-dispatch-gating` comment on `VALID_STATUS_TRANSITIONS` is a false claim — the contract behaviour is not implemented.
- **Recommendation:** Add `PendingDependencies = 'pending-dependencies'` to `WorkItemStatus`. Add transition rules: `Approved → PendingDependencies` (when blocked) and `PendingDependencies → Approved` (on cascade). Update approve endpoint to perform the status downgrade; update `onItemResolved` to advance from `PendingDependencies` to `Approved`. The portal app has this correct — mirror that pattern.
- **Cross-ref:** [ESCALATE → TheFixer] for Source/ fix; api-contract agent for Shared/ type change.

### QO-003: `dependencyCheckDuration` Histogram Missing from Source/ Metrics
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/metrics.ts`
- **Detail:** `FR-dependency-metrics` requires 4 metrics: `dependencyOperations` counter, `dispatchGatingEvents` counter, `dependencyCheckDuration` histogram, `cycleDetectionEvents` counter.

In contrast, `portal/Backend/src/metrics.ts` correctly has all four including the histogram (used in `portal/Backend/src/services/dependencyService.ts` to time readiness and cascade checks). The `// Verifies: FR-dependency-metrics` comment in Source/Backend/src/metrics.ts is incomplete.
- **Recommendation:** Add `dependencyCheckDuration = new Histogram({ name: 'dependency_check_duration_seconds', ... })` to Source/Backend/src/metrics.ts. Instrument `isReady()` and `computeHasUnresolvedBlockers()` in Source/Backend/src/services/dependency.ts.
- **Cross-ref:** TheFixer (backend fix).

### QO-004: FR-dependency-api-types Still Open in portal/ (as any Cast)
- **Severity:** P2
- **Category:** spec-drift
- **File:** `portal/Frontend/src/components/shared/DependencyPicker.tsx:291,293`
- **Detail:** Plans/dependency-linking/requirements.md explicitly marks `FR-dependency-api-types` as `❌ Missing`. Verified: `portal/Frontend/src/components/shared/DependencyPicker.tsx` lines 291 and 293 use `as any`:
  ```typescript
  await bugs.update(itemId, { blocked_by: blockerIds } as any);
  await featureRequests.update(itemId, { blocked_by: blockerIds } as any);
  ```
  `UpdateBugInput` and `UpdateFeatureRequestInput` in `portal/Shared/api.ts` lack `blocked_by?: string[]`. This makes the PATCH call untyped — TypeScript cannot catch mismatches in the dependency save path.
- **Recommendation:** Add `blocked_by?: string[]` to `UpdateBugInput` and `UpdateFeatureRequestInput` in `portal/Shared/api.ts`. Remove the `as any` casts. This is a 3-line change.
- **Cross-ref:** TheFixer (portal api-contract fix).

### QO-007: Traceability Enforcer Regex Matches Seed Data IDs as Requirements
- **Severity:** P2
- **Category:** pattern-violation
- **File:** `tools/traceability-enforcer.py:62–65`
- **Detail:** The regex `FR-[A-Z0-9-]+` in `extract_fr_ids()` matches seed data item IDs written in requirements prose. Running `--file Plans/dependency-linking/requirements.md` reports **7 false-missing requirements**: `FR-0002`, `FR-0003`, `FR-0004`, `FR-0005`, `FR-0007`, `FR-070`, `FR-085`. These come from:
  - Seed data narrative: "FR-0004 blocked_by FR-0003; FR-0005 blocked_by FR-0002; FR-0007 blocked_by FR-0003"
  - Spec reference: "Specifications/dev-workflow-platform.md (FR-070 — FR-085)"
  
  The enforcer exits with code 1 on false failures, preventing it from being useful for this plan.
- **Recommendation:** Tighten the regex to require a word boundary and exclude lower-case-only suffixes: e.g., `r'\bFR-[A-Z]{2,}(?:-\d+)?\b'` (require at least 2 uppercase letters before an optional numeric suffix). Alternatively, add an exclusion list in the enforcer for known data-ID patterns.
- **Cross-ref:** TheFixer (tooling fix).

### QO-008: FR-WF-* IDs Exist Only in Plans, Not in Specifications
- **Severity:** P3
- **Category:** spec-drift
- **File:** `Specifications/workflow-engine.md`
- **Detail:** All 13 `FR-WF-*` requirement IDs (`FR-WF-001` through `FR-WF-013`) are defined exclusively in `Plans/self-judging-workflow/requirements.md`. The canonical specification `Specifications/workflow-engine.md` has **no formal FR-WF-XXX section** — it describes the domain model, routing rules, and API endpoints in prose without unique IDs.

  This breaks the spec-first principle: "Specs are source of truth — implementation traces to specs, never the other way around." Currently implementation traces to Plans/, skipping the Specifications/ layer. If `workflow-engine.md` ever changes, there is no way to detect which FR-WF-* IDs are affected.
- **Recommendation:** Either (a) add a formal `## Functional Requirements` table with FR-WF-001–013 IDs to `Specifications/workflow-engine.md`, or (b) establish a documented convention that Plans/ requirements.md IS the specification for its domain, and update CLAUDE.md to clarify the two-layer model.

  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** CLAUDE.md architecture rules require structured reasoning for any suppression. `react-hooks/exhaustive-deps` suppressions often mask stale-closure bugs — the hook reads a dep from component scope but the rule is silenced rather than refactoring the effect.
