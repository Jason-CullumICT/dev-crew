## Findings

### QO-001: Unimplemented Endpoint — GET /api/search
- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts` (route not registered) / `Source/Backend/tests/routes/search.test.ts` (5 tests, all expected to fail)
- **Detail:** The `GET /api/search` endpoint is referenced by `FR-dependency-search` and has 5 written test cases in `search.test.ts`. The test file itself contains an explicit comment: *"GET /api/search endpoint is NOT wired into app.ts. These tests document the expected contract and will FAIL until the route is implemented."* The search route does not exist anywhere in `Source/Backend/src/` — there is no `routes/search.ts`, and no `app.use('/api/search', ...)` in `app.ts`. The `DependencyPicker` frontend component calls `searchItems(query)` via the API client, which hits this missing endpoint.
- **Recommendation:** Create `Source/Backend/src/routes/search.ts` implementing `GET /api/search?q=` that searches work items by title/description, returns `{data: WorkItem[]}`, excludes soft-deleted items, and returns empty `{data:[]}` on blank query. Register in `app.ts` as `app.use('/api/search', searchRouter)`. Add `// Verifies: FR-dependency-search` comments.
- **Cross-ref:** TheFixer to implement; dependency feature is incomplete until this lands.

### QO-002: Traceability Enforcer Checks Only One Plan at a Time
- **Severity:** P2
- **Category:** pattern-violation / spec-drift
- **File:** `tools/traceability-enforcer.py` (auto-detect logic)
- **Detail:** The enforcer auto-selects the **most recently modified** `requirements.md` under `Plans/`. Currently this picks `Plans/self-judging-workflow/requirements.md` (which passes). The other 7 requirements files — including `dependency-linking`, `dev-workflow-platform`, `orchestrated-dev-cycles`, `dev-cycle-traceability`, `image-upload`, `orchestrator-cycle-dashboard`, `duplicate-deprecated-status` — are never checked by the default `python3 tools/traceability-enforcer.py` invocation mandated in the verification gate. Running all plans manually reveals **7 FAILURE results** for plans that target the old portal/ system. This gives a false green light.
- **Recommendation:** Either (a) add a `--all-plans` flag to the enforcer that iterates every `requirements.md` and aggregates results, or (b) update the CLAUDE.md verification gate to explicitly target the active plan: `python3 tools/traceability-enforcer.py --plan self-judging-workflow`. The gate command should be unambiguous about which plan is active.
- **Cross-ref:** The 7 failing plans all reference `portal/` paths — they describe the old dev-workflow-platform app, not the current Source/ app. Those failures are expected for the old system but should be explicitly documented as such (see QO-004).

### QO-003: Route Handlers Directly Access Store — Architecture Violation
- **Severity:** P2
- **Category:** architecture-violation
- **File:** 
  - `Source/Backend/src/routes/workItems.ts:12` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/workflow.ts:15` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/intake.ts:4` — `import * as store from '../store/workItemStore'`
- **Detail:** Three route handlers call store functions directly: `store.findById()`, `store.createWorkItem()`, `store.updateWorkItem()`, `store.softDelete()`, `store.findAll()`. The architecture rule is explicit: **"No direct DB calls from route handlers — use the service layer."** While the store is in-memory rather than a SQL DB, the intent of the rule (separation of concerns, testability, single responsibility) applies equally. Business logic (validation, change-tracking calls) is interleaved with HTTP request/response handling. Services like `assessment.ts`, `router.ts`, and `dependency.ts` correctly provide a service layer, but CRUD operations bypass it.
- **Recommendation:** Introduce a `workItemService.ts` (or `workItemCrudService.ts`) that wraps `store.createWorkItem`, `store.findById`, `store.findAll`, `store.updateWorkItem`, and `store.softDelete`. Route handlers call the service, not the store directly. This follows the pattern already established by `dashboardService.ts` → `getAllItems()`.
- **Cross-ref:** TheFixer; this is a refactor with no behavior change.

### QO-005: Traceability Enforcer Regex Misses Lowercase FR IDs
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `tools/traceability-enforcer.py:62` — regex `r"FR-[A-Z0-9-]+"`
- **Detail:** The enforcer uses `FR-[A-Z0-9-]+` which matches uppercase/numeric IDs only (e.g., `FR-WF-001`, `FR-033`). The `dependency-linking` requirements file uses lowercase IDs like `FR-dependency-types`, `FR-dependency-search`, `FR-dependency-api-client`. These are NOT matched by the enforcer's extraction regex. As a result, the enforcer reports 7 "missing" requirements for `dependency-linking` that are actually implemented (Source has `// Verifies: FR-dependency-types` etc.), while also failing to find the truly missing `FR-dependency-search`. The enforcer produces both false positives and false negatives for this plan.
- **Recommendation:** Change the regex to case-insensitive: `r"FR-[A-Za-z0-9-]+"` and update the matching accordingly. This aligns the extractor with the actual naming conventions used across all requirements files.
- **Cross-ref:** QO-001 (FR-dependency-search is genuinely missing; QO-002 (enforcer reliability).

### QO-006: Duplicate Test Files for WorkItemDetailPage and WorkItemListPage

  - `Source/Frontend/tests/WorkItemListPage.test.tsx` (286 lines) vs `Source/Frontend/tests/pages/WorkItemListPage.test.tsx` (262 lines)
- **Detail:** Both directories contain tests for the same components. The root-level files are shallower (fewer typed imports, more mock overbroadness), while the `pages/` versions are more complete. Running the test suite picks up both, creating redundant coverage and potential confusing false confidence. The `tests/` root versions use `vi.mock('../src/api/client', ...)` while `tests/pages/` use `vi.mock('../../src/api/client', ...)` — different relative paths for the same mock.
- **Recommendation:** Delete the shallower root-level duplicates (`tests/WorkItemDetailPage.test.tsx`, `tests/WorkItemListPage.test.tsx`) and keep the more complete `tests/pages/` versions. Run a full test pass to confirm zero regressions.
- **Cross-ref:** TheFixer.

### QO-007: eslint-disable Comments in Production Source
- **Severity:** P3
- **Category:** pattern-violation
- **File:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Architecture rule: "No disabled linting rules (`eslint-disable`, `nolint`)." Both suppressions are for `react-hooks/exhaustive-deps`. In `useWorkItems.ts`, the hook correctly destructures individual filter fields in the dependency array to avoid object identity issues — the suppress is technically defensible but masks a design smell (passing a mutable object reference as a hook parameter). In `DependencyPicker.tsx`, the same pattern is used.
- **Recommendation:** Replace the object-spreading pattern with a `useRef` stable ref or move to `useMemo` for the filters object. If the suppression is truly necessary, add an explanatory comment that explicitly documents why the full object can't be used safely. Consider filing a TheFixer ticket.
- **Cross-ref:** TheFixer; low-urgency refactor.
