## Findings

### QO-001: Traceability Enforcer Scope is Fatally Misaligned
- **Severity:** P1
- **Category:** spec-drift
- **File:** `tools/traceability-enforcer.py:69` (`source_dirs = ["Source", "E2E"]`)
- **Detail:** The mandatory verification gate (`python3 tools/traceability-enforcer.py`) has two critical blind spots:
  1. **Wrong scan directories**: It scans only `Source/` and `E2E/`. The `portal/` directory implements ~80% of the product's functional requirements (FR-001 to FR-069, FR-dependency-*, FR-070-095, FR-DUP-01-13). When run against any of these plans, the enforcer reports all requirements as "MISSING" because it cannot see portal/, even though they are fully implemented there.
  2. **Single-plan evaluation**: The tool auto-selects only the most-recently-modified `requirements.md` (currently `Plans/self-judging-workflow/requirements.md`, containing 13 FRs). Seven other plans covering ~127 requirements are never checked. Any team completing work on dev-workflow-platform, orchestrated-dev-cycles, or other plans will see "PASSED" for FR-WF-* when their actual plan requirements go unchecked.
- **Impact:** The "TRACEABILITY PASSED" gate message misleads teams into believing all requirements are verified when 91% of requirements are never evaluated by the gate.
- **Recommendation:** 
  ```python
  # Option A: Expand scan directories
  source_dirs = ["Source", "E2E", "portal", "platform"]
  
  # Option B: Add --all-plans flag to check every requirements.md
  # Option C: Update inspector.config.yml to add portal/ to source.dirs
  #   and update CLAUDE.md verification gate to:
  #   for plan in $(ls Plans/*/requirements.md); do
  #     python3 tools/traceability-enforcer.py --file "$plan"
  #   done
  ```
- **Cross-ref:** Update `inspector.config.yml` `source.dirs` to include `portal/` and `platform/`.

### QO-002: Route Handlers Bypass Service Layer (Architecture Violation)
- **Severity:** P2
- **Category:** architecture-violation
- **Files:** 
  - `Source/Backend/src/routes/workItems.ts:12` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/workflow.ts:15` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/intake.ts:4` — `import * as store from '../store/workItemStore'`
- **Detail:** Three route handlers import and call the data store directly (`store.createWorkItem`, `store.findById`, `store.findAll`, `store.updateWorkItem`, `store.softDelete`) rather than going through a service layer. CLAUDE.md architecture rule #2 states: **"No direct DB calls from route handlers — use the service layer."** The in-memory store IS the data layer; routes should interact through dedicated service functions. A service layer exists (`assessment.ts`, `router.ts`, `dependency.ts`, `dashboard.ts`, `changeHistory.ts`) and is correctly used for domain operations, but CRUD operations are direct.
- **Impact:** Business logic is scattered in route handlers. Adding validation, caching, or auditing requires touching route files. Unit-testing CRUD logic requires spinning up the HTTP layer.
- **Recommendation:** Create `Source/Backend/src/services/workItemService.ts` exposing `createItem`, `getItem`, `listItems`, `updateItem`, `deleteItem`; route handlers call service functions only.
- **Cross-ref:** [ESCALATE → TheFixer] for refactoring.

### QO-003: FR-dependency-seed Is Unimplemented
- **Severity:** P2
- **Category:** spec-drift
- **File:** `portal/Backend/src/database/` (missing `seed.ts`)
- **Detail:** The `dependency-linking` plan (FR-dependency-seed) requires creating `portal/Backend/src/database/seed.ts` — an idempotent seeding function that inserts known dependency relationships on server startup:
  - BUG-0010 blocked_by BUG-0003, BUG-0004, BUG-0005, BUG-0006, BUG-0007
  - FR-0004 blocked_by FR-0003
  - FR-0005 blocked_by FR-0002
  - FR-0007 blocked_by FR-0003
  
  Neither the file nor any `// Verifies: FR-dependency-seed` comment exists anywhere in the codebase (checked Source/, portal/, platform/). Only `portal/Backend/src/database/connection.ts` and `schema.ts` exist.
- **Impact:** Out-of-the-box developer experience is broken — the dependency relationships described in acceptance criteria cannot be validated without manual setup. The spec's acceptance criteria (`GET /api/bugs/BUG-0010` returns 5 items in `blocked_by`) will fail on a fresh install.
- **Recommendation:** Create `portal/Backend/src/database/seed.ts` per the spec. Add a call to the seed function in `portal/Backend/src/app.ts` after migrations. Add `// Verifies: FR-dependency-seed` to the file header.
- **Cross-ref:** [ESCALATE → TheFixer].

### QO-004: Traceability Enforcer Produces False Positives on Entity IDs
- **Severity:** P2
- **Category:** pattern-violation
- **File:** `tools/traceability-enforcer.py:63-65`; `Plans/dependency-linking/requirements.md:23`
- **Detail:** The enforcer uses the regex `FR-[A-Z0-9-]+` to extract requirement IDs. In `Plans/dependency-linking/requirements.md`, the spec text contains entity data references like `FR-0002`, `FR-0003`, `FR-0004`, `FR-0005`, `FR-0007` — these are **Feature Request record IDs** in the seed data (e.g., "FR-0007 blocked_by FR-0003"), not functional requirement IDs. The enforcer extracts them as FR IDs to verify and then reports them as "MISSING" because no source file contains `// Verifies: FR-0007`. When running `--plan dependency-linking`, the enforcer reports 3 false "MISSING" requirements (FR-0007, FR-070, FR-085 — the latter two are in portal/ outside the scan scope).
- **Impact:** False failures erode trust in the gate. Teams may learn to ignore failures, masking real traceability gaps.
- **Recommendation:** 
  1. In requirements files, use a notation that disambiguates entity IDs from requirement IDs (e.g., wrap entity refs: `` `BUG-0010` `` inline rather than as bare tokens).
  2. Add an enforcer blocklist for known non-requirement ID patterns: `FR-0\d{3}` (4-digit-zero-padded).
  3. Remove placeholder IDs (`FR-XXX`, `FR-XXXX`, `FR-0XX`) from requirements files (found in dev-workflow-platform, dev-cycle-traceability, image-upload, orchestrator-cycle-dashboard plans).
- **Cross-ref:** Update `tools/traceability-enforcer.py`.

### QO-005: FR-070 to FR-095 and FR-DUP-01 to FR-DUP-13 Are Not in Specifications/
- **Severity:** P3
- **Category:** spec-drift
- **Files:** `Specifications/dev-workflow-platform.md` (tops out at FR-069); portal source references FR-070 to FR-095, FR-DUP-01 to FR-DUP-13
- **Detail:** The `Specifications/` directory is designated as **"Domain truth — the most critical documents."** However, 38+ requirement IDs that are actively implemented and traced in `portal/` have no canonical specification entry:
  - FR-070 to FR-095: Image upload, orchestrator dashboard (in `Plans/image-upload/` and `Plans/orchestrator-cycle-dashboard/`)
  - FR-DUP-01 to FR-DUP-13: Duplicate/deprecated status tracking (in `Plans/duplicate-deprecated-status/`)
  These requirements exist only in `Plans/` (implementation-level), not in `Specifications/` (domain-level truth). The architecture principle "Specs are source of truth — implementation traces to specs, never the other way around" is inverted here: implementation preceded specification.
- **Impact:** New agents or developers have no authoritative spec for ~27% of implemented features. Domain rules for image uploads, orchestrator views, and duplicate status are not canonicalized.
- **Recommendation:** Extend `Specifications/dev-workflow-platform.md` with sections covering FR-070-095 and FR-DUP-01-13, capturing the domain-level intent (not implementation detail) for each feature group.
- **Cross-ref:** Specifications owner (requirements-reviewer role).

### QO-006: eslint-disable Suppressions in Production Frontend Code
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Two production frontend files suppress `react-hooks/exhaustive-deps` linting without inline explanation of why the dependency is intentionally excluded. Unexplained suppressions can hide infinite-render bugs or stale-closure issues.
- **Recommendation:** Add a comment explaining the intentional exclusion immediately after each suppress line. If the dependency truly should be included, fix the hook.

- **Severity:** P4
- **Category:** untested
- **File:** `Source/Frontend/src/pages/DebugPortalPage.tsx` (no matching test file)
- **Detail:** Every other page in `Source/Frontend/src/pages/` has a corresponding test file (`DashboardPage.test.tsx`, `WorkItemListPage.test.tsx`, `WorkItemDetailPage.test.tsx`, `CreateWorkItemPage.test.tsx`). `DebugPortalPage.tsx` is the only page without a test. It renders an iframe embedding a debug portal (`http://localhost:4200`).
