### QO-001: Traceability Enforcer Only Validates the Most-Recently-Modified Plan
- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py:49-57` (fallback: `max(req_files, key=os.path.getmtime)`)
- **Detail:** `python3 tools/traceability-enforcer.py` — the project's mandatory verification gate — silently picks only the single most-recently-modified `requirements.md` across all plans. There are **9 plans** with a `requirements.md`; 8 are never evaluated. The gate reports `TRACEABILITY PASSED` while 56+ requirements across 4 plans are unimplemented. This gives engineers and CI a false green signal.
- **Recommendation:** Change the enforcer to validate **all** `Plans/*/requirements.md` files (or a manifest list), or add a `--all-plans` flag and use it in the verification gate command in `CLAUDE.md`. Minimum fix: error if there are multiple plans and none is explicitly specified.
- **Cross-ref:** All QO-002 through QO-008 are downstream of this blind spot.

### QO-005: Plans/dev-workflow-platform — ~87% Unimplemented (Dev Platform Spec Never Built)
- **Severity:** P1
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md`, `Plans/dev-workflow-platform/requirements.md`
- **Detail:** The `Specifications/dev-workflow-platform.md` describes a full SQLite-backed development platform (Feature Requests, Bug Reports, Development Cycles, Tickets, Votes, Learnings, Feature Browser) with 69 functional requirements. The actual `Source/` implements a completely different system — the in-memory Self-Judging Workflow Engine (FR-WF-001 to FR-WF-013). FR-007 through FR-032 are all confirmed MISSING by the enforcer. The two systems are architecturally distinct:
  - Spec: SQLite + better-sqlite3, Feature Request entities, 7 dedicated pages
  - Implementation: in-memory Map store, WorkItem entity, 4 pages
  This means **the highest-priority domain specification has no matching implementation**.
- **Recommendation:** Establish which spec is authoritative. If the workflow-engine (`Specifications/workflow-engine.md`) has superseded the dev-workflow-platform spec, add a `superseded-by:` note to `dev-workflow-platform.md` and archive its plan. If dev-workflow-platform is still the target, it needs a full build.
- **Cross-ref:** QO-001

### QO-010: eslint-disable Comments in Production Source
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Two `eslint-disable-next-line` suppressions in production source silence the `react-hooks/exhaustive-deps` rule. This rule protects against stale closure bugs in React hooks. Suppressing it without a documented reason means any future reader must manually verify the suppression is intentional and safe.
- **Recommendation:** Either fix the hooks to satisfy the exhaustive-deps rule (preferred), or add an inline comment explaining **why** the suppression is intentional (e.g., `// intentional: effect must only re-run on mount`). Never suppress linting rules silently.
- **Cross-ref:** none
