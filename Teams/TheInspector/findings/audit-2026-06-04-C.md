### QO-001: Orphaned Specification — dev-workflow-platform.md
- **Severity:** P1
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md` (FR-001 through FR-069, 69 requirements)
- **Detail:** This specification describes a "Development Workflow Platform" with feature requests, bug reports, development cycles, pipeline orchestration, and cycle traceability. **None of these 69 FRs have any `// Verifies:` references in the current codebase.** The current source implements the "Self-Judging Workflow Engine" (FR-WF-001 to FR-WF-013), a completely different domain model. Running the enforcer against the spec file fails on all 76 requirement IDs (69 FRs + numeric false-positives). This is either a specification that was superseded and never archived, or a planned second application that hasn't been started. Either way, it creates misleading coverage metrics and confusion about what is actually built.
- **Recommendation:** One of: (a) Archive the spec to `Specifications/archived/` and add a note explaining the pivot; (b) Create a `Plans/dev-workflow-platform-phase2/requirements.md` that scopes the remaining work; (c) Formally deprecate with a header noting its status. Do NOT leave it as a live spec with 0% implementation coverage.
- **Cross-ref:** Affects traceability enforcer scope (see QO-004)

### QO-003: Route Handlers Bypass Service Layer
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:12-13`, `Source/Backend/src/routes/workflow.ts:13-14`
- **Detail:** Architecture rule: *"No direct DB calls from route handlers — use the service layer."* Both route files directly import and call the in-memory store:
  ```ts
  // workItems.ts:12
  import * as store from '../store/workItemStore';
  // workflow.ts:13
  import * as store from '../store/workItemStore';
  ```
  `workItems.ts` has zero service intermediaries — all CRUD operations go route→store. `workflow.ts` mixes store calls with service calls (router service, assessment service), but still reads/writes to the store directly (e.g., `store.findById`, `store.updateWorkItem`) instead of routing through a service. The store is the persistence/data layer and is analogous to a DB in this in-memory architecture. Route handlers should delegate to a `workItemService` layer.
- **Recommendation:** Extract a `Source/Backend/src/services/workItemService.ts` that wraps the store operations (create, findById, findAll, update, softDelete). Route handlers call the service. This preserves the layering required by the architecture rule.
- **Cross-ref:** TheFixer for remediation

### QO-004: Traceability Enforcer Has Three Critical Gaps
- **Severity:** P2
- **Category:** spec-drift / pattern-violation
- **File:** `tools/traceability-enforcer.py:60-65`
- **Detail:** The enforcer has three compounding gaps:

  **Gap 1 — Auto-targeting only checks the latest plan.** The enforcer uses `max(req_files, key=os.path.getmtime)` — it only ever checks ONE requirements file (the most recently modified). All other plans' requirements are silently ignored. The main spec file (`Specifications/dev-workflow-platform.md`) is never checked.

  **Gap 2 — Regex doesn't match lowercase FR IDs.** The pattern `FR-[A-Z0-9-]+` requires uppercase letters after `FR-`. All `FR-dependency-*` requirement IDs (e.g., `FR-dependency-types`, `FR-dependency-search`) contain lowercase letters and are NEVER matched by this pattern. The entire dependency-linking feature family has zero enforcer coverage.

  **Gap 3 — False-positive matching of domain data IDs.** In `Plans/dependency-linking/requirements.md`, the seed data description contains text like *"FR-0004 blocked_by FR-0003"* — these are work item data IDs, not requirement IDs. The enforcer matches them as requirements (`FR-0002`, `FR-0003`, `FR-0004`, `FR-0005`, `FR-0007`), then reports them as MISSING because no `// Verifies: FR-0004` comment exists. This produces false failures when targeting this plan.

- **Recommendation:** (1) Change the pattern to `FR-[A-Za-z0-9_-]+` to match mixed-case IDs. (2) Add a `--all-plans` flag to scan all requirements files. (3) Qualify the FR-ID regex to require `Verifies:` context to avoid domain ID false-positives. (4) Consider adding the Specifications/ dir as an optional additional scan target.

### QO-005: Logger Missing Development Pretty-Print Mode
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/utils/logger.ts:17-24`
- **Detail:** The architecture rule states: *"Use structured JSON logging in production, pretty-printing in development."* FR-WF-013 acceptance criteria: *"All log output is structured JSON in NODE_ENV=production; logger is the only log sink."* The current implementation:
  ```ts
  function emit(level: LogLevel, message: string, context?: Record<string, unknown>): void {
    const entry: LogEntry = { timestamp: ..., level, message, ...};
    process.stdout.write(JSON.stringify(entry) + '\n');  // Always JSON, no dev mode
  }
  ```
  There is no `process.env.NODE_ENV` check. Development output is machine-readable JSON, making local debugging significantly harder for human developers.
- **Recommendation:** Add a dev-mode branch:
  ```ts
  if (process.env.NODE_ENV !== 'production') {
    console.log(`[${level.toUpperCase()}] ${message}`, context ?? '');
  } else {
    process.stdout.write(JSON.stringify(entry) + '\n');
  }
  ```

### QO-006: OpenTelemetry Absent — Architecture Rule Violated
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/` (no OTel files found)
- **Detail:** Architecture rule: *"Use OpenTelemetry for distributed tracing. Auto-instrument HTTP, database, and framework calls. Add custom spans for critical paths. Propagate W3C `traceparent` header across service boundaries."* Additionally: *"Auto-inject trace/span IDs from OpenTelemetry where available."* The backend has zero OTel SDK packages in `package.json`, no tracing instrumentation, no traceparent propagation, and no span IDs in logs. The logger comment in `utils/logger.ts` says "Structured JSON logger" but doesn't inject trace context. FR-WF-013 coverage is partial as a result.
- **Recommendation:** Add `@opentelemetry/sdk-node`, `@opentelemetry/auto-instrumentations-node`; create an `src/tracing.ts` bootstrap; inject trace/span IDs into the logger's context. Add a middleware that extracts/propagates `traceparent` from incoming request headers. Route this through TheFixer.
- **Cross-ref:** [ESCALATE-NOTE → TheGuardians] — missing distributed tracing could mask security-relevant request flows

### QO-008: Dual Logger Abstraction — Wrapper Anti-Pattern
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Backend/src/logger.ts` (wraps `Source/Backend/src/utils/logger.ts`)
- **Detail:** Two logger modules exist:
  - `src/utils/logger.ts` — named export `logger` (the real implementation)
  - `src/logger.ts` — default export `logger` (a compatibility wrapper with a `normalize()` function)
  
  The wrapper was created because different pipeline agents imported the logger with different patterns (`import logger from '../logger'` vs `import { logger } from '../utils/logger'`). The `normalize()` function handles two call signatures: string message and object-with-msg. This is an adapter anti-pattern that adds indirection, maintainability debt, and two potential divergence points for logging behavior.
- **Recommendation:** Standardize on one import pattern. Design `utils/logger` to accept both `(msg: string, ctx?)` and `(obj: {msg: string, ...})` signatures directly, remove `src/logger.ts`, update all imports to `import { logger } from '../utils/logger'`.

### QO-009: eslint-disable Suppresses Hooks Exhaustive-Deps
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/components/DependencyPicker.tsx:82`, `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Both files suppress `react-hooks/exhaustive-deps`. The hook in `useWorkItems.ts` manually enumerates filter keys (`.status`, `.type`, `.priority`, `.source`, `.page`, `.limit`) instead of depending on the object. The DependencyPicker suppression may hide a stale closure risk. Both are technical debt that should be resolved by refactoring the dependency array (e.g., stabilizing the filter object with `useMemo`).
- **Recommendation:** For `useWorkItems.ts`: wrap `filters` in `useMemo` upstream or stringify it for the dep array. For `DependencyPicker.tsx`: review the suppressed effect for stale-closure risks and restructure the effect so it doesn't need suppression.

### QO-010: E2E Package Test Script Broken
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/E2E/package.json:10`
- **Detail:** The E2E workspace test script is:
  ```json
  "test": "echo \"Error: no test specified\" && exit 1"
  ```
  This is the npm default placeholder — it always exits 1. When the verification gate `npm test --workspaces --if-present` runs, the E2E workspace will always fail. Playwright config files (`playwright.config.ts`, `playwright.pipeline.config.ts`) exist and tests are presumably intended to run via `playwright test`, but the npm script doesn't invoke Playwright.
- **Recommendation:** Update `Source/E2E/package.json` to:
  ```json
  "test": "playwright test --config playwright.config.ts"
  ```
  or use `--if-present` behavior more carefully (the workspace has a test script, so `--if-present` still runs it).
