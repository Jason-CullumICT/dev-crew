## QO-001: Specification Domain Mismatch — Product Pivot Undocumented
- **Severity:** P1
- **Category:** spec-drift
- **Files:** `Specifications/dev-workflow-platform.md`, `Specifications/workflow-engine.md`
- **Detail:**  
  `Specifications/` contains `dev-workflow-platform.md` defining **74 requirements** (FR-001 – FR-069+) for a SQLite-backed platform with FeatureRequests, BugReports, DevelopmentCycles, votes, approvals, and pipeline orchestration. **None of these 74 FRs appear in `Source/`.**

  The `Source/` codebase implements a completely different product — a self-judging WorkItem workflow engine — whose spec lives in `Specifications/workflow-engine.md` and `Plans/self-judging-workflow/requirements.md`. The formal `Specifications/` directory is out of sync with what is actually built.

  `Specifications/workflow-engine.md` is the only spec that matches the source code, but it contains **zero formal FR identifiers** (it is entirely prose). This makes machine-checkable traceability impossible for the primary domain spec.

  The `Source/Shared/api-contracts.md` references "FR-070 through FR-085" as WIP for dependency tracking, but these IDs appear nowhere in `Specifications/`.

- **Recommendation:**  
  1. Archive or clearly mark `Specifications/dev-workflow-platform.md` as superseded (e.g., move to `Specifications/archive/` or add a `STATUS: Superseded` banner at the top).  
  2. Add formal FR-WF-XXX identifiers to `Specifications/workflow-engine.md` so it becomes the machine-checkable source of truth.  
  3. Formally define FR-070 – FR-085 (dependency tracking) in `Specifications/` as an addendum to `workflow-engine.md` or as a new spec file.  
  4. Update the traceability enforcer `--file` default to point at `Specifications/` rather than auto-selecting the most-recently-modified plan.
- **Cross-ref:** QO-003 (enforcer scope gap)

## QO-002: Architecture Violation — Route Handlers Call Store Directly
- **Severity:** P2
- **Category:** architecture-violation
- **Files:**  
  - `Source/Backend/src/routes/workItems.ts` (line 12: `import * as store from '../store/workItemStore'`)  
  - `Source/Backend/src/routes/workflow.ts` (line 15: `import * as store from '../store/workItemStore'`)  
  - `Source/Backend/src/routes/intake.ts` (line 4: `import * as store from '../store/workItemStore'`)
- **Detail:**  
  CLAUDE.md mandates: *"No direct DB calls from route handlers — use the service layer."*  
  Three route files bypass the service layer and call `store.findById`, `store.createWorkItem`, `store.updateWorkItem`, `store.softDelete` directly. `routes/dashboard.ts` correctly delegates to `dashboardService` — that pattern is the right model.

  Specific violations:
  - `workItems.ts`: 10 direct store calls (create, findAll, findById ×3, updateWorkItem, softDelete)
  - `workflow.ts`: 10+ direct store calls interleaved with service calls (dependency, router, assessment)
  - `intake.ts`: 2 direct store calls (createWorkItem for Zendesk and automated intake)
- **Recommendation:**  
  Extract a `workItemService.ts` service module that wraps all store reads/writes. Route handlers should only call service functions. This aligns with `routes/dashboard.ts` as the existing correct pattern.  
  Coordinate with `Source/Backend/src/services/dependency.ts` — it also calls the store directly, which is acceptable for a service layer file.
- **Cross-ref:** [ESCALATE → TheFixer]

## QO-007: Two Logger Files in Backend (Single Source of Truth Violation)
- **Severity:** P3
- **Category:** architecture-violation
- **Files:**  
  - `Source/Backend/src/logger.ts` (`// Verifies: FR-WF-013 — Re-export structured logger as default`)  
  - `Source/Backend/src/utils/logger.ts` (`// Verifies: FR-WF-013 — Structured JSON logger (never console.log)`)
- **Detail:**  
  The CLAUDE.md rule "Shared types are single source of truth — no inline type re-definitions across layers" extends to utilities. Two logger files exist: the root `src/logger.ts` is a re-export shim, and `src/utils/logger.ts` is the actual implementation. This is acceptable only if `src/logger.ts` is purely a backward-compat re-export. However, having two files with the same `// Verifies: FR-WF-013` comment and partially overlapping purpose creates confusion for future contributors about which to import.
- **Recommendation:**  
  Verify that `src/logger.ts` is purely `export { default } from './utils/logger'`. If so, document this in a comment. If not, consolidate into one file. All imports across `routes/` and `services/` should use a single canonical path.

## QO-008: Suppressed eslint-disable Rules
- **Severity:** P4
- **Category:** pattern-violation
- **Files:**  
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`  
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:**  
  Two suppressed `react-hooks/exhaustive-deps` rules indicate `useEffect` hooks with intentionally omitted dependencies. This is a known pattern for avoiding re-render loops, but each suppression should carry a comment explaining why the dependency is intentionally excluded. Without explanation, future contributors may accidentally introduce the missing dependency and trigger infinite loops.
- **Recommendation:**  
  Add an inline comment on the same line explaining the intent, e.g.:  
  `// eslint-disable-next-line react-hooks/exhaustive-deps -- intentionally omits X to avoid re-fetch loop`
