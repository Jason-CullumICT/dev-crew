## Findings

### QO-001 — FR-dependency-api-types: Shared types lack `blocked_by` field
- **Severity:** P2
- **Category:** spec-drift / unimplemented-requirement
- **Files:**
  - `portal/Shared/api.ts:32` — `UpdateFeatureRequestInput`
  - `portal/Shared/api.ts:59` — `UpdateBugInput`
  - `portal/Frontend/src/components/shared/DependencyPicker.tsx:291,293`
- **Detail:** `UpdateFeatureRequestInput` and `UpdateBugInput` in the authoritative Shared layer are missing the `blocked_by?: string[]` field required by FR-dependency-api-types. The frontend `DependencyPicker` works around this with `as any` casts at lines 291 and 293. This requirement was flagged as incomplete in `Plans/dependency-linking/requirements.md` and remains open.
- **Recommendation:** Add `blocked_by?: string[]` to both interfaces in `portal/Shared/api.ts`. Remove the `as any` casts in `DependencyPicker.tsx`.
- **Cross-ref:** TheFixer (code fix)

### QO-002 — Architecture: Direct DB calls in `teamDispatches.ts` route handler
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `portal/Backend/src/routes/teamDispatches.ts:37,41,72`
- **Detail:** The route handler calls `getDb()` directly and executes `db.prepare(...)` queries inline — bypassing the service layer. This violates the architecture rule "No direct DB calls from route handlers — use the service layer." The file also has no `// Verifies:` traceability comments and no corresponding test file exists (`portal/Backend/tests/teamDispatches.test.ts` is absent).
- **Recommendation:** Extract DB logic into `portal/Backend/src/services/teamDispatchService.ts`. Add `// Verifies: FR-XXX` comment once the spec is written. Add a test file.
- **Cross-ref:** TheFixer (refactor), TheGuardians (untested route is security surface)

### QO-003 — Duplicate type definitions: `UpdateFeatureRequestInput` and `UpdateBugInput` diverge
- **Severity:** P2
- **Category:** architecture-violation
- **Files:**
  - `portal/Shared/api.ts:32` — `UpdateFeatureRequestInput` (no `blocked_by`)
  - `portal/Backend/src/services/featureRequestService.ts:244` — `UpdateFeatureRequestInput` (has `blocked_by`)
  - `portal/Shared/api.ts:59` — `UpdateBugInput` (no `blocked_by`)
  - `portal/Backend/src/services/bugService.ts:184` — `UpdateBugInput` (has `blocked_by`)
- **Detail:** Both types are defined twice across layers with divergent fields. The architecture rule "Shared types are single source of truth — no inline type re-definitions across layers" is violated. The Shared version is the authoritative one consumed by the frontend, but the backend services define their own richer versions. This is the root cause of QO-001.
- **Recommendation:** Add `blocked_by?: string[]` to both types in `portal/Shared/api.ts` (fixes QO-001 simultaneously). Remove the duplicate definitions in services, importing from Shared instead.
- **Cross-ref:** TheFixer

### QO-004 — Silent error swallowing in BugDetail and FeatureRequestDetail
- **Severity:** P2
- **Category:** architecture-violation / pattern-violation
- **Files:**
  - `portal/Frontend/src/components/bugs/BugDetail.tsx:82`
  - `portal/Frontend/src/components/feature-requests/FeatureRequestDetail.tsx:80`
  - `portal/Frontend/src/components/common/RepoSelector.tsx:20`
- **Detail:** Three `.catch(() => {})` calls silently swallow errors. On BugDetail and FeatureRequestDetail, failed repo-list fetches go unreported, leaving users with an empty repo selector and no explanation. On RepoSelector the same pattern repeats. Architecture rule: "Never swallow errors silently — every `catch` block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."
- **Recommendation:** At minimum, log with `console.error` or the project logger and set an error state variable that renders a user-visible message. If the repo list is genuinely optional, add an inline comment explaining the intentional suppression.
- **Cross-ref:** TheFixer

- **Files:**

  - `portal/Frontend/src/hooks/useApi.ts:35`
- **Detail:** Three `// eslint-disable-next-line react-hooks/exhaustive-deps` suppressions in production hooks. Each likely indicates a missing dependency in a `useEffect` or `useCallback`, which can cause subtle stale-closure bugs.
