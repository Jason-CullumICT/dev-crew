### QO-001: Traceability Enforcer Blind Spot — `portal/` Not Scanned
- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py` (scan targets: `Source/`, `E2E/`)
- **Detail:**
  The verification gate (`python3 tools/traceability-enforcer.py`) scans only `Source/` and `E2E/`.
  The primary production application lives in `portal/` (FR-001 through FR-069+ from
  `dev-workflow-platform.md`), which is entirely invisible to the enforcer.

  **Concrete impact — two failure modes:**
  1. **False failure**: Running `--file Plans/dev-workflow-platform/requirements.md` reports 34
     "MISSING" requirements even though all 34 are correctly traced in `portal/`. Any agent or
     CI step targeting that plan would block on a false negative.
  2. **False pass**: The default invocation picks `Plans/self-judging-workflow/requirements.md`
     (via mtime tie-breaking) and always passes, giving no visibility into whether `portal/`
     traceability is regressing.

  The repository has two apps:
  - `Source/` — Self-Judging Workflow Engine (`workflow-engine.md` / `FR-WF-*`)
  - `portal/` — Dev Workflow Platform (`dev-workflow-platform.md` / `FR-001…FR-069`)

- **Recommendation:**
  Add `portal/` to the enforcer's scan paths. In `tools/traceability-enforcer.py`, line 71:
  ```python
  source_dirs = ["Source", "E2E", "portal"]
  ```
  Also add `portal/` to `inspector.config.yml` → `source.dirs` and `source.test_dirs`.
- **Cross-ref:** QO-003 (inspector.config also misses portal/)

### QO-002: Architecture Violation — Direct SQL in Route Handler (`teamDispatches.ts`)
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `portal/Backend/src/routes/teamDispatches.ts:37-44, 72-75`
- **Detail:**
  The rule is: *"No direct DB calls from route handlers — use the service layer."*
  `teamDispatches.ts` bypasses this entirely: it calls `db.prepare(...).all(...)` and
  `db.prepare(...).run(...)` inline in both the GET and POST route handlers, with zero service
  layer indirection. No `// Verifies:` traceability comments are present either.

  ```ts
  // GET handler (line 37-44) — raw SQL in route
  rows = db.prepare(
    `SELECT * FROM team_dispatches WHERE team = ? ORDER BY dispatched_at DESC LIMIT ?`
  ).all(team, limitNum) as TeamDispatch[];

  // POST handler (line 72-75) — raw SQL in route
  db.prepare(
    `INSERT INTO team_dispatches (id, team, inputs, dispatched_at, actions_url, workflow, repo)
     VALUES (?, ?, ?, ?, ?, ?, ?)`
  ).run(id, team, inputs_json, dispatched_at, actions_url, workflow, repo);
  ```

- **Recommendation:**
  Extract a `teamDispatchService.ts` in `portal/Backend/src/services/` with
  `listDispatches(db, team?, limit)` and `recordDispatch(db, payload)` functions.
  Route handlers should call service functions only. Add `// Verifies:` comment once the
  feature is traced to a spec requirement (or add the requirement if it's unspecced).
- **Cross-ref:** [ESCALATE → TheFixer] for the refactor.

### QO-005: Traceability Enforcer — False Positives from Seed Data References
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `tools/traceability-enforcer.py:63`
- **Detail:**
  The enforcer regex `FR-[A-Z0-9-]+` matches any `FR-` followed by alphanumerics/hyphens,
  including:
  - Seed data references in requirements prose: `"FR-0002"`, `"FR-0003"` appear in
    `Plans/dependency-linking/requirements.md` as seed item IDs, not requirement IDs
  - Template placeholders: `FR-XXX`, `FR-XXXX` appear in requirements file headers
  
  Running the enforcer against `Plans/dependency-linking/requirements.md` produces:
  ```
  [MISSING] FR-0002, FR-0003, FR-0004, FR-0005, FR-0007, FR-070, FR-085, FR-XXX, FR-XXXX
  ```
  All are false positives — none are requirement IDs.

- **Recommendation:**
  Add an exclusion filter to `extract_fr_ids()`. Require requirement IDs to appear on their
  own line as `| FR-…` (table format) or in a comment-like context, or add an allowlist/denylist.
  At minimum, filter out template placeholders:
  ```python
  return [fr for fr in ids if fr not in ('FR-XXX', 'FR-XXXX') and not re.match(r'FR-0\d{3}$', fr)]
  ```

### QO-010: Silent Catch in OTel Initialization
- **Severity:** P4
- **Category:** pattern-violation
- **File:** `portal/Backend/src/lib/tracing.ts:36`
- **Detail:**
  ```ts
  } catch (err) {
    // Tracing initialization failure is non-fatal
  }
  ```
  The comment documents intent (non-fatal), satisfying the "explicitly document" exception.
  However, a silent initialization failure means operators have no observability signal
  that OTel is down. If `OTEL_EXPORTER_OTLP_ENDPOINT` is set but the SDK fails to load,
  tracing silently stops with no log entry.
- **Recommendation:**
  Add a warning log:
  ```ts
  } catch (err) {
    // Tracing initialization failure is non-fatal — app continues without OTel export
    logger.warn({ msg: 'OTel SDK init failed — running without distributed tracing', error: (err as Error).message });
  }
  ```
