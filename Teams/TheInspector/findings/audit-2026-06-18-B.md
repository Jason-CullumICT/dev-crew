## Findings

### QO-001: Traceability enforcer is blind to `portal/`
- **Severity:** P1
- **Category:** architecture-violation / spec-drift
- **File:** `tools/traceability-enforcer.py:70`
- **Detail:** The enforcer hardcodes `source_dirs = ["Source", "E2E"]`. The `portal/` directory is a full production application (backend + frontend + SQLite) implementing `Specifications/dev-workflow-platform.md` (76 FRs) and Plans/dev-workflow-platform requirements. When the enforcer is invoked against `Plans/dev-workflow-platform/requirements.md`, it reports **all 34 FRs as MISSING** even though portal/ has extensive `// Verifies: FR-XXX` coverage. The verification gate defined in CLAUDE.md (`python3 tools/traceability-enforcer.py`) auto-selects Plans/self-judging-workflow (most recently modified), so portal/ is permanently invisible to the gate. A developer could remove all traceability from portal/ and the gate would still PASS.
- **Recommendation:** Add `portal` to `source_dirs` in the enforcer, or make the scan directories configurable via `inspector.config.yml` (`source.dirs`). The config already defines `source.dirs: ["Source/"]` but the enforcer doesn't read it.
- **Cross-ref:** TheFixer (code fix), verification gate in CLAUDE.md

### QO-002: `GET /api/search` endpoint is not implemented — 5 tests failing
- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts` (missing route registration), `Source/Backend/tests/routes/search.test.ts`
- **Detail:** FR-dependency-search requires `GET /api/search?q=` for cross-entity typeahead used by `DependencyPicker`. The test file explicitly documents the gap:
  > "the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."
  All 5 search tests fail. The `DependencyPicker` frontend component calls `workItemsApi.searchItems()` → `/search?q=`, so dependency search is broken at runtime. This is the only failing test suite in the backend (164 passing, 5 failing).
- **Recommendation:** Create `Source/Backend/src/routes/search.ts` with `GET /` that filters the in-memory store by title/description match, excludes soft-deleted items, and register it in `app.ts` as `/api/search`. Add `// Verifies: FR-dependency-search` traceability.
- **Cross-ref:** TheFixer (implementation), FR-dependency-api-client (frontend already wired)

### QO-003: `dependencyCheckDuration` histogram missing from metrics
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/metrics.ts`
- **Detail:** FR-dependency-metrics specifies exactly 4 Prometheus metrics:
  1. `dependencyOperations` counter ✓
  2. `dispatchGatingEvents` counter ✓
  3. **`dependencyCheckDuration` histogram ✗ — absent**
  4. `cycleDetectionEvents` counter ✓
  The histogram is needed to observe the latency of `hasUnresolvedBlockers()` / `isReady()` calls. Without it, dependency check performance cannot be monitored and FR-dependency-metrics is partially unimplemented.
- **Recommendation:** Add to `metrics.ts`:
  ```typescript
  // Verifies: FR-dependency-metrics — dependency_check_duration_seconds
  export const dependencyCheckDuration = new Histogram({
    name: 'dependency_check_duration_seconds',
    help: 'Duration of dependency readiness checks (BFS traversal)',
    labelNames: ['operation'] as const,
    registers: [registry],
  });
  ```
  Then instrument `isReady()` and `hasUnresolvedBlockers()` in `services/dependency.ts`.
- **Cross-ref:** TheFixer (implementation)

### QO-004: Route handlers bypass the service layer (architecture rule violation)
- **Severity:** P2
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/routes/workItems.ts:12` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/intake.ts:4` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/workflow.ts:15` — `import * as store from '../store/workItemStore'`
- **Detail:** CLAUDE.md architecture rule: "No direct DB calls from route handlers — use the service layer." All three route files import and call the store directly (e.g., `store.createWorkItem()`, `store.findById()`, `store.findAll()`). Service files exist (`assessment.ts`, `router.ts`, `changeHistory.ts`, `dependency.ts`, `dashboard.ts`) but basic CRUD operations are not wrapped in a service layer. This couples routes to store internals, making the store hard to swap and business logic hard to test in isolation.
- **Recommendation:** Create `Source/Backend/src/services/workItemService.ts` wrapping all store CRUD operations. Update routes to import from the service instead of the store directly.
- **Cross-ref:** TheFixer (refactor). Note: In a pure in-memory system, this is a lower-priority refactor but the rule is non-negotiable per CLAUDE.md.

### QO-005: Duplicate frontend test files — stale root-level copies
- **Severity:** P2
- **Category:** doc-stale / untested
- **Files:**
  - `Source/Frontend/tests/WorkItemDetailPage.test.tsx` (root) ↔ `Source/Frontend/tests/pages/WorkItemDetailPage.test.tsx` (pages/)
  - `Source/Frontend/tests/WorkItemListPage.test.tsx` (root) ↔ `Source/Frontend/tests/pages/WorkItemListPage.test.tsx` (pages/)
- **Detail:** Both pairs of files exist with slightly different content. The `tests/pages/` versions are more complete (include additional type imports, use `within()`, have expanded mock setup). The root-level files appear to be the older generation. Both run under vitest, doubling test execution and risking conflicting or outdated coverage claims. Currently all 135 frontend tests pass, but this hides that root-level files test a simpler mock surface.
- **Recommendation:** Remove the root-level `tests/WorkItemDetailPage.test.tsx` and `tests/WorkItemListPage.test.tsx`; the `tests/pages/` versions are canonical.
- **Cross-ref:** TheFixer (cleanup)

### QO-006: `eslint-disable-next-line` without justification comments

  - `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Both suppress `react-hooks/exhaustive-deps` without a comment explaining why the omitted dependency is safe to exclude. This masks potential stale-closure bugs.
