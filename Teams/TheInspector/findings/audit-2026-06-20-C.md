### QO-001: `GET /api/search` endpoint is unimplemented — tests will fail
- **Severity:** P1
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts` (missing route registration), `Source/Backend/tests/routes/search.test.ts`
- **Detail:** `FR-dependency-search` requires a `GET /api/search?q=` cross-entity typeahead endpoint used by `DependencyPicker`. A 5-case test suite exists in `tests/routes/search.test.ts` and explicitly documents the route is NOT registered:
  ```
  // NOTE: As of this review cycle the GET /api/search endpoint is NOT wired into
  // Source/Backend/src/app.ts. These tests document the expected contract and will
  // FAIL until the route is implemented.
  ```
  Running `npm test` in `Source/Backend` will produce 5 failing tests. The `DependencyPicker` component calls `searchItems()` (via `workItemsApi.search`) which will return 404 at runtime.
- **Recommendation:** Add a `searchRouter` at `Source/Backend/src/routes/search.ts` that filters the work-item store by `q` across `title` and `description`, then mount it in `app.ts` as `app.use('/api', searchRouter)`. Register `// Verifies: FR-dependency-search` at the top.
- **Cross-ref:** TheFixer for implementation; QA agent should confirm tests pass after fix.

### QO-002: `Specifications/dev-workflow-platform.md` is an orphaned spec for a different system
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md`
- **Detail:** This spec defines FR-001 through FR-069 for a "dev-crew platform" with Feature Requests, Bug Reports, Development Cycles, and a SQLite-backed Express API — a completely different domain from the workflow engine in `Source/`. Zero of these 69 requirements are implemented in `Source/`. The spec was written for a portal-based application (`portal/` directory references appear on lines 467-482). The dependency-linking spec (`Plans/dependency-linking/requirements.md`) was adapted from this portal spec and implemented in `Source/` under FR-dependency-* IDs.
  
  If `inspector.config.yml` is the spec authority (`specs.dir: "Specifications/"`), the project has 0% spec coverage for its largest specification. If the Plans files are the authority, coverage is 93%.
- **Recommendation:** Either (a) archive `Specifications/dev-workflow-platform.md` by moving it to `docs/archive/` and updating `inspector.config.yml` to `specs.dir: "Plans/"`, or (b) explicitly note in the file header that it is a historical reference spec for a different application and not enforced for `Source/`. Option (a) is strongly preferred to prevent future spec-coverage confusion.
- **Cross-ref:** requirements-reviewer should own this decision.

### QO-003: Traceability enforcer is blind to `FR-dependency-*` requirements
- **Severity:** P2
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py`, `inspector.config.yml`
- **Detail:** The enforcer uses "most recently modified `requirements.md`" as its target — currently `Plans/self-judging-workflow/requirements.md` (13 FRs). It does **not** scan `Plans/dependency-linking/requirements.md` (16 `FR-dependency-*` IDs), so `FR-dependency-seed` and `FR-dependency-api-types` (both incomplete per the requirements delta in that file) are invisible to automated gates.

  The `inspector.config.yml` sets:
  ```yaml
  specs:
    dir: "Specifications/"
    patterns:
      enforcer: "python3 tools/traceability-enforcer.py"
  ```
  But the enforcer ignores `Specifications/` entirely. The config advertises a capability the tool doesn't deliver.
- **Recommendation:** Either (a) run `python3 tools/traceability-enforcer.py --file Plans/dependency-linking/requirements.md` as a second gate in CI, or (b) modify the enforcer to accept multiple `--file` arguments or a glob pattern. Additionally update `inspector.config.yml` to explicitly list both requirements files so the mismatch is visible.
- **Cross-ref:** TheFixer can implement multi-file support in the enforcer.

### QO-005: Duplicate frontend test files — `WorkItemDetailPage` and `WorkItemListPage`
- **Severity:** P2
- **Category:** test-quality
- **Files:**
  - `Source/Frontend/tests/WorkItemDetailPage.test.tsx` (368 lines)
  - `Source/Frontend/tests/pages/WorkItemDetailPage.test.tsx` (393 lines)
  - `Source/Frontend/tests/WorkItemListPage.test.tsx` (286 lines)
  - `Source/Frontend/tests/pages/WorkItemListPage.test.tsx` (262 lines)
- **Detail:** Each component has two distinct test files — one in `tests/` (root) and one in `tests/pages/`. Both test the same component. The `tests/pages/` variants use a relative path (`../../src/pages/...`) and import explicit types from Shared, while the `tests/` root variants use shorter paths. This creates:
  - Maintenance burden: two files must be kept in sync when the component changes.
  - False coverage inflation: aggregate test count appears higher than genuine coverage.
  - Risk of divergence: the 393-line `tests/pages/` file has more detailed tests than the 368-line root file; if the root file is updated and pages/ is not, coverage silently degrades.
- **Recommendation:** Consolidate to `tests/pages/WorkItemDetailPage.test.tsx` and `tests/pages/WorkItemListPage.test.tsx` (the richer versions). Remove the root-level duplicates. Update any jest/vitest config that explicitly references them.
- **Cross-ref:** frontend-coder.

### QO-006: OpenTelemetry tracing not implemented — CLAUDE.md architecture rule violated
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/` (entire directory)
- **Detail:** `CLAUDE.md` states:
  > *"Use OpenTelemetry for distributed tracing. Auto-instrument HTTP, database, and framework calls. Add custom spans for critical paths. Propagate W3C `traceparent` header across service boundaries."*

  No OTel code exists anywhere in `Source/`. `grep -ri "opentelemetry\|traceparent"` returns zero results. The `Specifications/workflow-engine.md` does not formally require OTel, but CLAUDE.md's architecture rules are non-negotiable per its own text. `FR-WF-013` covers logging + Prometheus but does not mention OTel — this creates an unlabelled gap between the architecture rule and the formal requirements.
- **Recommendation:** Either (a) add a `FR-WF-014` requirement for OTel and implement it (at minimum: `@opentelemetry/sdk-node` auto-instrumentation + `traceparent` header forwarding), or (b) document in `Plans/self-judging-workflow/requirements.md` that OTel is deferred with a tracking ticket. Do not leave the gap invisible — the CLAUDE.md rule is active.
- **Cross-ref:** backend-coder for implementation; requirements-reviewer to decide scope.

### QO-007: `RouteResult` and `AssessmentResult` interfaces not in Shared types
- **Severity:** P3
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/services/router.ts:60` — `export interface RouteResult`
  - `Source/Backend/src/services/assessment.ts:141` — `export interface AssessmentResult`
- **Detail:** Architecture rule: *"Shared types are single source of truth — no inline type re-definitions across layers."* These two interfaces represent domain-significant response shapes from workflow services. If a frontend page ever needs to type-check router or assessment results directly (e.g., displaying route classification), it cannot import from `Source/Shared/types/workflow.ts` and must either duplicate the type or reach into the backend package — both violations.
- **Recommendation:** Move `RouteResult` and `AssessmentResult` (and `LogEntry`, `LoggerCompat` if they leak into API contracts) into `Source/Shared/types/workflow.ts`. Update imports in router.ts and assessment.ts accordingly.
- **Cross-ref:** api-contract agent for cross-layer coordination.

### QO-008: Silent `.catch(() => ({}))` in API client — missing suppression rationale
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/api/client.ts:26`
- **Detail:**
  ```typescript
  const body = await response.json().catch(() => ({}));
  ```
  Architecture rule: *"Never swallow errors silently — every catch block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."* This catch is intentional (fallback to empty body when a non-2xx response has no JSON), but the suppression reason is undocumented.
- **Recommendation:** Add an inline comment:
  ```typescript
  // Intentionally suppressed: non-2xx responses may have no JSON body (e.g., 204, 502).
  // Falling back to {} so the outer error check can still emit the HTTP status.
  const body = await response.json().catch(() => ({}));
  ```
- **Cross-ref:** frontend-coder.

### QO-009: Two `eslint-disable` suppressions in production source without documented rationale
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Both suppress the `react-hooks/exhaustive-deps` rule. Suppressing this rule without explanation hides potential stale-closure bugs — the classic cause of UI state not refreshing when dependencies change. If the suppression is intentional (e.g., the callback is stable by design), it must say so.
- **Recommendation:** For each suppression, add a comment on the line above explaining why the dependency is intentionally omitted:
  ```typescript
  // searchQuery is intentionally excluded — we debounce via the timeout, not the dep array.
  // eslint-disable-next-line react-hooks/exhaustive-deps
  ```
  If the rationale cannot be articulated, fix the exhaustive-deps warning instead.
- **Cross-ref:** frontend-coder.
