## Findings

### QO-001: GET /api/search NOT REGISTERED — Route Exists in Tests, Not in App
- **Severity:** P1
- **Category:** unimplemented-requirement
- **File:** `Source/Backend/src/app.ts` (missing), `Source/Backend/tests/routes/search.test.ts:1-7`
- **Detail:** `FR-dependency-search` requires a `GET /api/search?q=` cross-entity typeahead endpoint used by `DependencyPicker` for its search input. A complete test suite exists (`search.test.ts`, 5 test cases with real supertest calls), but the route is **not registered** in `app.ts`. The test file itself comments: *"As of this review cycle the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."* The `DependencyPicker` component calls `searchItems()` which hits `GET /api/search` — every search in the UI currently returns 404.
- **Recommendation:** Create `Source/Backend/src/routes/search.ts`, implement the search handler (filter non-deleted work items by title/description), and register `app.use('/api/search', searchRouter)` in `app.ts`. Traceability comment: `// Verifies: FR-dependency-search`.
- **Cross-ref:** TheFixer — backend route implementation needed. TheInspector confirmed test suite ready and waiting.

### QO-002: dependencyCheckDuration Histogram Missing from Metrics
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/metrics.ts`
- **Detail:** `FR-dependency-metrics` specifies 4 Prometheus metrics: `dependencyOperations` counter, `dispatchGatingEvents` counter, `dependencyCheckDuration` histogram, and `cycleDetectionEvents` counter. Three are implemented. The **`dependencyCheckDuration` histogram** is entirely absent — no Histogram is exported, no `.observe()` calls exist anywhere in the dependency service. This means dependency check latency is invisible to operators.
- **Recommendation:** Add a `Histogram` to `metrics.ts`:
  ```ts
  // Verifies: FR-dependency-metrics — dependency_check_duration_seconds
  export const dependencyCheckDurationHistogram = new Histogram({
    name: 'dependency_check_duration_seconds',
    help: 'Duration of dependency readiness checks',
    labelNames: ['operation'],
    registers: [registry],
  });
  ```
  Then wrap `computeHasUnresolvedBlockers` and `isReady` calls with `.startTimer()` / `.observe()`.
- **Cross-ref:** TheFixer — backend metrics gap.

### QO-003: BlockedBadge Missing Amber "Pending Dependencies" State
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Frontend/src/components/BlockedBadge.tsx`, `Source/Frontend/tests/components/BlockedBadge.test.tsx`
- **Detail:** `FR-dependency-blocked-badge` specifies two badge states:
  1. Red badge "Blocked" when `hasUnresolvedBlockers=true` ✅ (implemented)
  2. **Amber badge "Pending Dependencies" when `status='pending_dependencies'`** ❌ (NOT implemented)

  The component only accepts a single `hasUnresolvedBlockers?: boolean` prop. The `status` prop is entirely absent. The test suite also only covers the red/absent states — the amber state is untested. Users in a `pending_dependencies` status state get no visual indicator.
- **Recommendation:** Extend the component:
  ```tsx
  interface BlockedBadgeProps {
    hasUnresolvedBlockers?: boolean;
    status?: string;
  }
  // Add amber badge when status === 'pending_dependencies'
  ```
  Add a corresponding test for the amber state.
- **Cross-ref:** TheFixer — frontend component + test gap.

### QO-004: FR-dependency-dispatch-gating Behavior Deviates from Spec
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/routes/workflow.ts:230-245`, `Source/Shared/types/workflow.ts`
- **Detail:** `FR-dependency-dispatch-gating` specifies: *"Status transitions to `approved`/`in_development` check all blockers; unresolved blockers → set to `pending_dependencies` instead."* The Source/ implementation does not transition to `pending_dependencies` — it returns a `400 Bad Request` with `error: "Cannot dispatch: work item has unresolved blocking dependencies"`. Furthermore, `pending_dependencies` is **not a value in the `WorkItemStatus` enum**. The `VALID_STATUS_TRANSITIONS` table has no entry for it.

  The traceability comment `// Verifies: FR-dependency-dispatch-gating` is accurate that the code *gates dispatch*, but the spec-mandated status mutation (transition to `pending_dependencies`) is absent. The cascade auto-dispatch (`onItemResolved`) correctly handles the upstream unblock, but there is no item in `pending_dependencies` state to re-advance — items remain in `Approved` while blocked.
- **Recommendation:** Options:
  1. **Align implementation with spec** — add `PendingDependencies = 'pending-dependencies'` to `WorkItemStatus`, update `VALID_STATUS_TRANSITIONS`, change dispatch route to set status instead of returning 400.
  2. **Align spec with implementation** — update `FR-dependency-dispatch-gating` to document the 400-error approach and remove `pending_dependencies` references.

  Option 2 is lower risk since the cascade unblock logic works correctly. Either way, update the traceability comment to accurately describe what the code does.
- **Cross-ref:** TheFixer if changing implementation; requirements-reviewer if updating the spec.

### QO-005: Traceability Enforcer Targets Most-Recently-Modified Plan Only
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `tools/traceability-enforcer.py:49-57`, `Teams/TheInspector/inspector.config.yml`
- **Detail:** The enforcer selects its target requirements file by finding the most recently modified `requirements.md` in `Plans/`. Today this resolves to `Plans/self-judging-workflow/requirements.md` (FR-WF-001..013), so FR-dependency-* requirements are **never enforced by default**. If a developer touches any other plan's requirements.md, enforcement silently shifts. The inspector.config.yml specifies the enforcer command but no `--plan` or `--file` argument to pin the scope.

  Current state: running `python3 tools/traceability-enforcer.py` passes (13 FR-WF-* all covered), but it misses 15 FR-dependency-* requirements. The `GET /api/search` gap (QO-001) is undetected by the enforcer.
- **Recommendation:** Update the enforcer invocation in CI/verification gates to explicitly list all active plans:
  ```bash
  python3 tools/traceability-enforcer.py --plan self-judging-workflow
  python3 tools/traceability-enforcer.py --plan dependency-linking
  ```
  Or add a wrapper script that runs the enforcer for each `requirements.md` in Plans/. Update `CLAUDE.md` verification gates accordingly.
- **Cross-ref:** TheInspector owns this tooling fix; low-effort, high-impact.

### QO-006: eslint-disable Comments Without Documented Justification
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Both files suppress `react-hooks/exhaustive-deps` with `// eslint-disable-next-line` without any comment explaining why the suppression is safe. This is a `console.log`-equivalent for lint rules — it hides potential stale-closure bugs. CLAUDE.md architectural rules require all suppressions to be explicitly justified.
- **Recommendation:** Review each suppression. If the dependency exclusion is intentional (e.g., the effect should only run on mount), add a comment:
  ```ts
  // eslint-disable-next-line react-hooks/exhaustive-deps — intentional: only run on mount
  ```
  If not intentional, fix the hook dependency array.
