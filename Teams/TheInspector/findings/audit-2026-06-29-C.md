### QO-001: Traceability Enforcer Blind to `portal/` Codebase
- **Severity:** P1
- **Category:** architecture-violation / spec-drift
- **File:** `tools/traceability-enforcer.py` (scan dirs: `["Source", "E2E"]`)
- **Detail:**
  The enforcer scans only `Source/` and `E2E/`. The `portal/` directory contains 113 TypeScript files
  implementing the primary product spec (`Specifications/dev-workflow-platform.md`, FR-001 – FR-069,
  plus FR-dependency-*, FR-DUP-*, FR-070 – FR-089). None of these are checked by the enforcer.
  When run today, the enforcer reports: `TRACEABILITY PASSED: All requirements have implementation
  references` — but it only verified 13 of 141 total requirements.
  
  Additionally, the enforcer auto-selects the most-recently-modified `requirements.md`, which happens
  to be `Plans/self-judging-workflow/requirements.md`. All other plans (image-upload, dependency-linking,
  orchestrator-cycle-dashboard, duplicate-deprecated-status) are silently skipped.
- **Recommendation:**
  1. Add `portal` to the `source_dirs` list in `tools/traceability-enforcer.py`.
  2. Either run enforcer per-plan (`--plan` flag for each) in the verification gate, or aggregate all
     known plans into a single scan pass.
  3. Update `CLAUDE.md` verification gates accordingly.
- **Cross-ref:** TheFixer (code fix to enforcer)

### QO-002: Duplicate FR IDs Across Plans (FR-070 – FR-076 Collision)
- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **Files:**
  - `Plans/orchestrator-cycle-dashboard/requirements.md` — FR-070 = OrchestratorCyclesPage
  - `Plans/image-upload/requirements.md` — FR-070 = ImageAttachment shared type
- **Detail:**
  Two separate plans assigned identical FR IDs to entirely different requirements:

  | ID | orchestrator-cycle-dashboard | image-upload |
  |----|------------------------------|--------------|
  | FR-070 | Create OrchestratorCyclesPage (page that polls cycles) | Add ImageAttachment shared type |
  | FR-071 | CycleCard component | Add ImageAttachmentListResponse API type |
  | FR-072 | Add stop button to CycleCard | image_attachments DB table + migration |
  | FR-073 | CycleLogStream SSE component | Configure multer middleware |
  | FR-074 | CompletedCyclesSection | Image service (upload/list/delete) |
  | FR-075 | Update App.tsx routing | POST /api/feature-requests/:id/images |
  | FR-076 | Update Sidebar nav label | POST /api/bugs/:id/images |

  This means `// Verifies: FR-070` in source code is ambiguous — it could refer to either feature.
  In practice, `portal/Frontend/src/components/orchestrator/types.ts:1` claims `FR-070` for the
  orchestrator dashboard, while the image-upload implementation in `portal/Backend` also uses the
  same IDs.

  The `Plans/dependency-linking/requirements.md` compounds this by incorrectly claiming:
  > _"Spec reference: Specifications/dev-workflow-platform.md (FR-070 — FR-085)"_
  — these FRs do not exist in that spec; they are plan-level additions only.
- **Recommendation:**
  1. Renumber one plan's IDs. Suggested: rename orchestrator-cycle-dashboard FRs to `FR-OCD-001`
     through `FR-OCD-007` (or similar prefix-based scheme).
  2. Update all `// Verifies:` comments in source to use the corrected IDs.
  3. Enforce prefix-based FR namespacing going forward (e.g., `FR-<PLAN-PREFIX>-NNN`) to prevent
     future collisions across plans.
- **Cross-ref:** TheFixer (renaming), requirements-reviewer (naming convention)

### QO-012: Silent JSON Parse Failure Swallows Error Context
- **Severity:** P4
- **Category:** pattern-violation / architecture-violation
- **File:** `Source/Frontend/src/api/client.ts:26`
- **Detail:**
  ```ts
  const body = await response.json().catch(() => ({}));
  ```
  This silently converts JSON parse failures (e.g., a non-JSON 500 body from the backend) to an
  empty object `{}`. Downstream code that inspects `body.error` will see `undefined` instead of
  the real error message, making debugging harder. CLAUDE.md rule: "Never swallow errors silently".
- **Recommendation:**
  Log the parse failure before returning the fallback:
  ```ts
  const body = await response.json().catch((err) => {
    logger.warn({ err, status: response.status }, 'Failed to parse response JSON');
    return {};
  });
  ```
