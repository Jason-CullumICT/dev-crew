## Findings

### QO-001: Traceability enforcer has blind spot — Specifications/ never enforced

- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py:16-57`
- **Detail:** The enforcer discovers requirements by scanning `Plans/*/requirements.md` (most-recently-modified file). It **never reads `Specifications/*.md`**. This means:
  - `FR-TMP-001` through `FR-TMP-010` (tiered merge pipeline) have zero `// Verifies:` comments anywhere in `Source/` — the tool will never catch this
  - `FR-001` through `FR-069` (dev-workflow-platform) are in a separate codebase (`portal/`) that the enforcer doesn't scan
  - A new spec file in `Specifications/` can be added and it will silently never be enforced
  - The `workflow-engine.md` spec has no FR-XXX identifiers at all, making it entirely untraceable
- **Reproduction:** `python3 tools/traceability-enforcer.py --file Specifications/tiered-merge-pipeline.md` exits 1 with 13 MISSING FRs. `python3 tools/traceability-enforcer.py --file Specifications/dev-workflow-platform.md` exits 1 with 76 MISSING FRs. But the default gate (`python3 tools/traceability-enforcer.py`) reports PASS because it targets only the most-recent Plans/ file.
- **Recommendation:**
  1. Add a second enforcer invocation targeting each Specifications/ file (or a combined run) to the verification gates in `CLAUDE.md`
  2. OR: create `Plans/*/requirements.md` shadow files for each Specification that lists the canonical FR IDs, making the current tool's auto-discovery work
  3. Add FR-XXX identifiers to `Specifications/workflow-engine.md`
  4. Expand `check_traceability()` to optionally scan `portal/` in addition to `Source/` for portal-app specs
- **Cross-ref:** [ESCALATE → TheFixer] — tool fix; [ESCALATE → requirements-reviewer] — workflow-engine.md needs FR IDs

### QO-003: Duplicate test files — stale root-level tests conflict with comprehensive page-level tests

- **Severity:** P2
- **Category:** test-coverage / pattern-violation
- **File:** `Source/Frontend/tests/WorkItemDetailPage.test.tsx` and `Source/Frontend/tests/WorkItemListPage.test.tsx`
- **Detail:** Two pairs of test files exist for the same components. The root-level files (`tests/*.test.tsx`) are **older, less comprehensive versions** of the same tests that now live in `tests/pages/`:

  | Root version | Pages version | Delta |
  |---|---|---|
  | `tests/WorkItemDetailPage.test.tsx` (368 lines) | `tests/pages/WorkItemDetailPage.test.tsx` (393 lines) | Root mocks `assess` (no longer in UI); pages version has 5 more cases, uses `within()` |
  | `tests/WorkItemListPage.test.tsx` (286 lines) | `tests/pages/WorkItemListPage.test.tsx` (262 lines) | Different mock setup and import paths |

  Both pairs run in CI simultaneously. The root-level `WorkItemDetailPage.test.tsx` still mocks `assess: vi.fn()` which was removed from the UI — indicating the root tests are stale and not being maintained.
- **Failure scenario:** A developer changes the detail page API contract and updates `tests/pages/WorkItemDetailPage.test.tsx` but misses `tests/WorkItemDetailPage.test.tsx` — tests pass but stale mocks silently diverge from reality.
- **Recommendation:** Delete `Source/Frontend/tests/WorkItemDetailPage.test.tsx` and `Source/Frontend/tests/WorkItemListPage.test.tsx` (root level). Retain the `tests/pages/` and `tests/components/` versions. Run `npm test` to confirm no regressions before deleting.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-004: Route handlers bypass service layer — direct store access violates architecture rule

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:12`, `Source/Backend/src/routes/workflow.ts:15`
- **Detail:** Both route files import directly from `../store/workItemStore`:
  ```ts
  // workItems.ts:12
  import * as store from '../store/workItemStore';
  // workflow.ts:15
  import * as store from '../store/workItemStore';
  ```
  The architecture rule states: **"No direct DB calls from route handlers — use the service layer."** While the store is in-memory (not SQLite), this bypasses the intended layering. By contrast, `dashboard.ts` correctly uses only `dashboardService`. The service layer exists for routing (`router.ts`), assessment (`assessment.ts`), change history (`changeHistory.ts`), and dependency (`dependency.ts`) but not for basic CRUD — so route handlers reach into the store directly for create/read/update/delete operations.
- **Failure scenario:** Business logic (validation, status transitions, change tracking) starts accumulating in route handlers instead of services, making it untestable in isolation. Already occurring: `workItems.ts` does validation, enum checks, and dependency orchestration in the route body.
- **Recommendation:** Create `Source/Backend/src/services/workItemService.ts` that wraps store CRUD with validation and business logic. Route handlers call service functions only. This would also centralize the pagination/filtering logic currently split between the route and store.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-005: eslint-disable suppressing react-hooks/exhaustive-deps without documented justification

- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/components/DependencyPicker.tsx:82`, `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:**
  ```ts
  // DependencyPicker.tsx:82
  // eslint-disable-next-line react-hooks/exhaustive-deps
  // useWorkItems.ts:63
  // eslint-disable-next-line react-hooks/exhaustive-deps
  ```
  Architecture rules say disabled linting rules should be flagged. Neither suppression carries a comment explaining **why** the dependency array is intentionally incomplete. This can hide stale closures or infinite loop bugs.
- **Recommendation:** Add an inline comment explaining the intentional omission (e.g., `// deliberately omit X — adding it would cause infinite re-fetch on every render`). If the omission is not intentional, fix the exhaustive-deps to prevent stale closure bugs.
