## Findings

### QO-001: Domain Spec Has Zero Source Coverage
- **Severity:** P1
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md`
- **Detail:** `Specifications/dev-workflow-platform.md` defines 65 functional requirements (FR-001 through FR-069) — the stated "domain truth" per CLAUDE.md. Not a single one appears as a `// Verifies: FR-NNN` comment anywhere in `Source/`. Entire feature areas exist in spec with no implementation: SQLite migrations (FR-002), Feature Request APIs (FR-005–FR-012), Bug Report APIs (FR-013), Development Cycle APIs (FR-014–FR-016), Pipeline APIs (FR-033–FR-049), Dev Cycle Traceability (FR-050–FR-069), and OpenTelemetry tracing (FR-021).

  The source code instead implements a different requirement set (`FR-WF-*` from Plans), which overlaps only partially with the spec (dashboard, CRUD, workflow actions, observability basics). The spec describes a much larger system: SQLite persistence, feature-request voting, dev cycle management, AI pipeline orchestration.

- **Recommendation:** Either (a) reconcile the spec to match what was built (annotate implemented FRs, mark unimplemented ones with status), or (b) create `// Verifies: FR-XXX` comments in source for every spec requirement that the source does implement. Without reconciliation, the spec is misleading and the enforcer gives false confidence.
- **Cross-ref:** QO-002 (enforcer blind spot enables this gap to go undetected)

### QO-002: Traceability Enforcer Has Critical Blind Spot
- **Severity:** P1
- **Category:** spec-drift
- **File:** `tools/traceability-enforcer.py:49–57`
- **Detail:** The enforcer auto-discovers requirements by selecting the **most recently modified** `requirements.md` file under `Plans/`. It does not read from `Specifications/` at all, despite the inspector config explicitly declaring `specs.dir: "Specifications/"`. The result is a passing green badge that covers only 13 Plan-level FRs while 75 domain-spec FRs are never checked. Any agent that runs the enforcer and sees "PASSED" will incorrectly conclude traceability is complete.
- **Recommendation:** Extend the enforcer to also scan `Specifications/` for `FR-\d+` patterns (as configured in `inspector.config.yml`) and report separately. Or add an explicit `--spec` flag that gates on the domain spec. The current "most-recently-modified" heuristic must not be the sole traceability gate.
- **Cross-ref:** QO-001

### QO-003: Route Handlers Call Store Directly — Service Layer Bypassed
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts`, `Source/Backend/src/routes/workflow.ts`, `Source/Backend/src/routes/intake.ts`
- **Detail:** CLAUDE.md rule: *"No direct DB calls from route handlers — use the service layer."* Despite two service modules existing (`router.ts`, `assessment.ts`), most route handlers bypass the service layer and call `store.*` directly:

  | Route File | Direct Store Calls |
  |------------|-------------------|
  | `workItems.ts` | `store.createWorkItem`, `store.findById`, `store.findAll`, `store.updateWorkItem`, `store.softDelete` |
  | `workflow.ts` | `store.findById` (×5), `store.updateWorkItem` (×3) |
  | `intake.ts` | `store.createWorkItem` (×2) |

  Business logic (validation, state machine enforcement, change tracking) is embedded directly in route handlers rather than in services. This prevents unit testing of business rules in isolation and makes the layering inconsistent.
- **Recommendation:** Extract all store interactions into service functions. Route handlers should only: parse request, delegate to service, serialize response. The `routeWorkItem` and `assessWorkItem` patterns in `services/router.ts` and `services/assessment.ts` show the correct approach — replicate it.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-004: Logger Missing Dev Pretty-Print Mode
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Backend/src/utils/logger.ts`
- **Detail:** FR-WF-013 requires *"structured JSON logging in production, pretty-printing in development"* (also FR-003 in the domain spec). The `utils/logger.ts` implementation always emits raw JSON via `process.stdout.write(JSON.stringify(entry))` with no `NODE_ENV` check. In development, every log line is machine-format JSON, which significantly degrades developer experience and violates both the plan-level and spec-level requirement.
- **Recommendation:** Add `NODE_ENV` check: if `development`, use a readable format (e.g., `[LEVEL] timestamp message context`); otherwise emit JSON. Example:
  ```typescript
  const isDev = process.env.NODE_ENV === 'development';
  // in emit():
  if (isDev) process.stdout.write(`[${level.toUpperCase()}] ${message} ${JSON.stringify(context ?? {})}\n`);
  else process.stdout.write(JSON.stringify(entry) + '\n');
  ```
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-005: Split Logger Abstraction — Two Logger Modules
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/logger.ts`, `Source/Backend/src/utils/logger.ts`, `Source/Backend/src/store/workItemStore.ts`
- **Detail:** Two logger modules exist:
  - `src/utils/logger.ts` — canonical implementation, named export `{ logger }`
  - `src/logger.ts` — compatibility wrapper with default export

  All files except `workItemStore.ts` import from `src/logger.ts` (default). `workItemStore.ts` imports `{ logger }` from `src/utils/logger.ts` directly. This splits the logger into two call-site interfaces: the store calls `logger.info('msg', ctx)` while routes call `logger.info({ msg, ...ctx })`. The wrapper normalizes this difference, but the split itself is unnecessary complexity and can cause confusion.
- **Recommendation:** Pick one interface (prefer `logger.info(msg, ctx)`), delete `src/logger.ts`, and update all imports to go directly to `src/utils/logger.ts`. The normalization layer serves no purpose if the calling convention is standardized.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-006: Duplicate Test Files for Same Components
- **Severity:** P2
- **Category:** test-coverage
- **File:** `Source/Frontend/tests/WorkItemDetailPage.test.tsx`, `Source/Frontend/tests/pages/WorkItemDetailPage.test.tsx`, `Source/Frontend/tests/WorkItemListPage.test.tsx`, `Source/Frontend/tests/pages/WorkItemListPage.test.tsx`
- **Detail:** Both `WorkItemDetailPage` and `WorkItemListPage` have two separate test files — one in `tests/` (older, shallower mocks) and one in `tests/pages/` (newer, typed imports with full workflow types). This creates:
  1. Two test runs covering the same component — redundant CI time
  2. Divergent assertions — the `tests/` versions mock differently from the `tests/pages/` versions
  3. Maintenance trap — fixing a bug requires updating two files, and they can drift apart

  The `tests/pages/` versions appear more complete (they import full TypeScript types, use `within()`). The `tests/` root versions are legacy.
- **Recommendation:** Remove the root-level `tests/WorkItemDetailPage.test.tsx` and `tests/WorkItemListPage.test.tsx`. Keep the `tests/pages/` versions. Verify no test cases exist exclusively in the root versions before deleting.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-007: Shared-Type Components Lack Tests
- **Severity:** P3
- **Category:** test-coverage

- **Detail:** Four UI components have no test files at all. These components are used across multiple pages (e.g., `StatusBadge` and `PriorityBadge` appear in both list and detail views). FR-032 requires *"Frontend Vitest/RTL tests for key components; each test carries `// Verifies: FR-XXX`."* `Layout`, `StatusBadge`, `PriorityBadge`, and `TypeBadge` are key shared components with no coverage.
- **Recommendation:** Add `tests/components/Layout.test.tsx`, `StatusBadge.test.tsx`, `PriorityBadge.test.tsx`, `TypeBadge.test.tsx`. Each should verify the correct CSS class or text is rendered for each input value (e.g., each priority enum value maps to correct color class).

### QO-008: ESLint Dependency Suppression Without Documentation
- **Severity:** P3
- **Category:** pattern-violation
- **Files:** `Source/Frontend/src/components/DependencyPicker.tsx:82`, `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Two `// eslint-disable-next-line react-hooks/exhaustive-deps` suppressions exist without any comment explaining *why* the dependency was intentionally omitted. This pattern can silently introduce stale-closure bugs when the component evolves.
- **Recommendation:** Add an inline comment explaining the intentional omission: e.g., `// intentional: run only on mount; deps would cause infinite loop`. If the suppression is genuinely needed, document it; if not, fix the dependency array.
