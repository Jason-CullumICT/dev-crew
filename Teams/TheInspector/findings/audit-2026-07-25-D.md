## Findings

### QO-001: Specifications/ Is Not the Source of Truth — Implementation Traces to Plans/ Only

- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **Files:** `Specifications/dev-workflow-platform.md`, `Specifications/tiered-merge-pipeline.md`, `Specifications/workflow-engine.md`, `Plans/self-judging-workflow/requirements.md`
- **Detail:**
  CLAUDE.md mandates the workflow `Specifications → Plans → Source → Tests` and states "Specs are source of truth — implementation traces to specs, never the other way around." In practice the opposite is true:
  - `Specifications/dev-workflow-platform.md` defines FR-001 to FR-069 (Feature Requests, Bug Reports, Dev Cycles with SQLite). The entire `Source/` codebase implements a **different product** — a Work Item workflow engine (in-memory store). Zero of the 69 requirements are traced.
  - `Specifications/tiered-merge-pipeline.md` defines FR-TMP-001 to FR-TMP-010 for the merge pipeline orchestrator. No traceability exists in `Source/` or `platform/`.
  - `Specifications/workflow-engine.md` _does_ describe the product that is built, but it contains **no FR-XXX identifiers** at all — making it untraceable by design.
  - The only traceable spec is `Plans/self-judging-workflow/requirements.md` (FR-WF-XXX). That file lives under `Plans/`, not `Specifications/`.
  - Result: `Specifications/` is an orphaned document directory. No enforcement gate reads it.
- **Recommendation:**
  Choose one of two resolutions:
  1. **Spec-first (preferred):** Add FR-WF-XXX IDs to `Specifications/workflow-engine.md`, remove them from the Plans requirements file, and re-run the enforcer pointing at `Specifications/workflow-engine.md`. Archive or mark `dev-workflow-platform.md` as superseded.
  2. **Plans-first (pragmatic):** Update CLAUDE.md to declare `Plans/*/requirements.md` as the canonical traceability source and update the enforcer to scan both `Specifications/` and `Plans/` directories.
  Either way, mark `dev-workflow-platform.md` (FR-001 to FR-069) and `tiered-merge-pipeline.md` (FR-TMP-XXX) with a status header (`> Status: SUPERSEDED / NOT IMPLEMENTED`) so future auditors know they are intentionally untraced.
- **Cross-ref:** [ESCALATE → TheFixer] for spec updates; team lead decision required.

### QO-002: Traceability Enforcer Reports False PASSED — Wrong Spec Scope

- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **File:** `tools/traceability-enforcer.py:1`, `Teams/TheInspector/inspector.config.yml:37`
- **Detail:**
  `inspector.config.yml` declares:
  ```yaml
  enforcer: "python3 tools/traceability-enforcer.py"
  ```
  But the enforcer auto-discovers the **most-recently-modified** `requirements.md` under `Plans/` — it has no awareness of `Specifications/`. Running it produces:
  ```
  Targeting requirements from: Plans/self-judging-workflow/requirements.md
  TRACEABILITY PASSED: All requirements have implementation references.
  ```
  This PASSED result is accurate for `Plans/self-judging-workflow`, but completely ignores the 79 requirements in `Specifications/`. Any CI or review gate that relies on this tool believes the project is fully traced when it is not.
- **Recommendation:**
  Extend the enforcer with a `--specs-dir` mode that scans all `*.md` files in `Specifications/` for `FR-[A-Z0-9-]+` patterns and checks them against `Source/`. Add a CLAUDE.md-level gate: `python3 tools/traceability-enforcer.py --file Specifications/workflow-engine.md`.
- **Cross-ref:** QO-001.

### QO-003: Route Handlers Directly Access Store — Service Layer Bypassed

- **Severity:** P2
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/routes/workItems.ts:44,88,134,141` — `store.findById`, `store.updateWorkItem`, `store.createWorkItem`, `store.softDelete`
  - `Source/Backend/src/routes/workflow.ts:44,71,119,155,175,217,269,317,359` — `store.findById`, `store.updateWorkItem`
- **Detail:**
  CLAUDE.md: "No direct DB calls from route handlers — use the service layer." The in-memory `workItemStore` is the persistence layer (equivalent to a DB). Both route files perform lookup and mutation operations directly (`store.findById(id)`, `store.updateWorkItem(id, ...)`) rather than delegating to a service.
  
  For comparison, `routeWorkItem()`, `assessWorkItem()`, `assignTeam()`, `setDependencies()` are correctly encapsulated in services. The inconsistency means business logic for approval, rejection, dispatch, and CRUD is split between routes and services — no single layer owns the mutation contract.
  
  Failure scenario: a new validation rule added to `workItems.ts` route won't apply to the `workflow.ts` route, which also calls `store.updateWorkItem` directly — state corruption risk.
- **Recommendation:**
  Create a `workItemService.ts` (or extend existing `router.ts`) that owns `findById`, `update`, `create`, `softDelete`. Route handlers call the service; the service calls the store.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-004: OpenTelemetry Tracing Absent — Architecture Rule Violated

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/app.ts`, `Source/Backend/src/` (all files)
- **Detail:**
  CLAUDE.md architecture rule (non-negotiable): "Use OpenTelemetry for distributed tracing. Auto-instrument HTTP, database, and framework calls. Add custom spans for critical paths. Propagate W3C `traceparent` header across service boundaries."
  
  A grep across all backend source files finds zero OTel imports (`@opentelemetry/*`, `traceparent`, `trace.`). The project has structured logging and Prometheus metrics (FR-WF-013), but no distributed tracing.
  
  Failure scenario: An incident requiring cross-service trace correlation cannot be investigated; spans are missing from any APM system; the architecture contract is silently broken.
- **Recommendation:**
  Add `@opentelemetry/sdk-node` + `@opentelemetry/auto-instrumentations-node` as backend dependencies. Initialize in `app.ts` (before route registration). Add custom spans in `router.ts` (route decision), `assessment.ts` (pod execution), `workflow.ts` (dispatch). Propagate `traceparent` in intake webhook handlers. Verify with `FR-WF-013` acceptance criteria update.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-005: `GET /api/search` Endpoint Not Registered — Tests Will Fail

- **Severity:** P2
- **Category:** untested / spec-drift
- **Files:**
  - `Source/Backend/tests/routes/search.test.ts:1-7` (documents the gap explicitly)
  - `Source/Backend/src/app.ts` (search route absent)
- **Detail:**
  `search.test.ts` explicitly states:
  ```
  // NOTE: As of this review cycle the GET /api/search endpoint is NOT wired into
  // Source/Backend/src/app.ts. These tests document the expected contract and will
  // FAIL until the route is implemented.
  ```
  The test file verifies `FR-dependency-search` but the route never got wired. Every test in this file is a confirmed failure. The test suite either suppresses these failures or they represent unresolved red.
  
  Additionally, the Frontend API client (`client.ts`) exposes `workItemsApi.searchItems()` which calls `GET /api/search` — so the frontend will also fail at runtime for this feature.
- **Recommendation:**
  Implement `GET /api/search?q=` in `workItems.ts` (or a new `search.ts` route) and register it in `app.ts`. The store already supports text matching via `findAll()` with filters; a search endpoint is a thin wrapper. Remove the comment once wired.
- **Cross-ref:** [ESCALATE → TheFixer]

  - `Source/Frontend/src/hooks/useDashboard.ts` — orchestrates dashboard API state

  - `Source/Frontend/src/components/TypeBadge.tsx`, `PriorityBadge.tsx`, `StatusBadge.tsx`, `Layout.tsx`

### QO-008: Two `eslint-disable` Suppressions in Production Code — Undocumented Risk

- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:**
  Both suppressions silence `react-hooks/exhaustive-deps`, which guards against stale-closure bugs. The `DependencyPicker.tsx` comment has no justification; `useWorkItems.ts` has none either. Suppressing this rule without a documented reason means future readers cannot distinguish "intentionally suppressed — proven safe" from "suppressed to make the lint pass."
- **Recommendation:**
  Add a one-line comment explaining why the dependency is intentionally omitted (e.g., `// selectedIdSet and blocksIdSet are derived in-render; adding them would cause infinite rerenders`). If the suppression is not defensible, fix the hook dependency instead.
