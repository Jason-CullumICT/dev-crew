## Findings

### QO-001: `GET /api/search` endpoint not wired in — DependencyPicker typeahead is broken at runtime
- **Severity:** P1
- **Category:** spec-drift / correctness
- **File:** `Source/Backend/src/app.ts` (missing registration) / `Source/Backend/tests/routes/search.test.ts:1`
- **Detail:**
  `FR-dependency-search` requires `GET /api/search?q=` for cross-entity typeahead used
  by the `DependencyPicker` modal. The test file itself carries an explicit notice:
  > "NOTE: As of this review cycle the GET /api/search endpoint is NOT wired into
  > Source/Backend/src/app.ts. These tests document the expected contract and will
  > FAIL until the route is implemented."
  The frontend `DependencyPicker` calls `/api/search?q=<query>` on every keystroke
  (debounced). With no matching route Express will 404, catch is suppressed
  (`// Search errors are intentionally suppressed`), and results fall back to empty —
  silently breaking the dependency-picker feature end-to-end.
- **Recommendation:**
  1. Create `Source/Backend/src/routes/search.ts` implementing `GET /api/search?q=`
     against the in-memory store (filter by title/description, exclude `deleted` items).
  2. Register `app.use('/api/search', searchRouter)` in `app.ts`.
  3. The existing tests in `search.test.ts` define the full contract — make them green.
- **Cross-ref:** TheFixer (implementation gap); frontend DependencyPicker silently degrades

### QO-002: `dependencyCheckDuration` Prometheus histogram absent — FR-dependency-metrics partially unmet
- **Severity:** P2
- **Category:** spec-drift / observability
- **File:** `Source/Backend/src/metrics.ts`
- **Detail:**

  - `dependencyOperations` counter ✅ (line 41)
  - `dispatchGatingEvents` counter ✅ (line 48)
  - `cycleDetectionEvents` counter ✅ (line 56)
  - `dependencyCheckDuration` **histogram** ❌ — entirely absent

  3 counters; it does not exercise the missing histogram. The CLAUDE.md architecture

  ```ts
    help: 'Duration of dependency readiness checks (BFS traversal)',
    labelNames: ['type'] as const,
    registers: [registry],
  });
  ```
  Instrument `isReady()` / `hasUnresolvedBlockers()` in `dependency.ts`.
  Add a metrics test that verifies the histogram label appears at `/metrics`.
- **Cross-ref:** TheFixer; metrics test needs updating

### QO-003: OpenTelemetry tracing entirely absent — hard architecture rule violated
- **Severity:** P2
- **Category:** architecture-violation / observability
- **File:** `Source/Backend/src/app.ts`, `Source/Backend/src/services/`
- **Detail:**
  CLAUDE.md states (non-negotiable):
  > "Use OpenTelemetry for distributed tracing. Auto-instrument HTTP, database, and
  > framework calls. Add custom spans for critical paths. Propagate W3C `traceparent`
  > header across service boundaries."

  No `@opentelemetry/` packages are imported anywhere in `Source/`. No `traceparent`
  header propagation exists. No custom spans are added for assessment, routing, or
  dispatch paths. The arch rule lists OTel as "architecture rule, not optional."

  The spec `dev-workflow-platform.md` FR-021 and the workflow engine spec both
  require OTel tracing; neither is implemented.
- **Recommendation:**
  Install `@opentelemetry/sdk-node`, `@opentelemetry/auto-instrumentations-node`.
  Create `Source/Backend/src/telemetry.ts` and call it before `app.ts` initialization.
  Add `traceparent` propagation via `@opentelemetry/propagator-w3c-trace-context`.
  Add custom spans in `routeWorkItem()`, `runAssessmentPod()`, `dispatchWorkItem()`.
- **Cross-ref:** TheGuardians (security spans help audit trail); TheFixer

### QO-010: Two logger modules — compatibility shim is technical debt
- **Severity:** P3
- **Category:** simplification / hygiene
- **File:** `Source/Backend/src/logger.ts` + `Source/Backend/src/utils/logger.ts`
- **Detail:**
  `utils/logger.ts` is the real structured logger. `logger.ts` is a compatibility
  shim that wraps it with a `normalize()` function to unify call signatures. All
  production code imports from `logger.ts` (the shim). This double-indirection
  exists because different coders used different call patterns and the shim was added
  to bridge them. It's dead weight — the shim's `normalize()` only handles
  `string | Record<string,unknown>` input, which could be handled with a single
  overloaded function in `utils/logger.ts`.
- **Recommendation:**
  Consolidate: update `utils/logger.ts` to export a default with a unified
  `(msgOrObj: string | Record<string,unknown>, ctx?: Record<string,unknown>) => void`
  signature per level. Remove `logger.ts`. Update all imports.
- **Cross-ref:** TheFixer

- **Severity:** P4
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`,
  `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:**
  Two production files suppress the `react-hooks/exhaustive-deps` lint rule. While
  the suppressions appear intentional (the `useWorkItems.ts` case enumerates deps
  explicitly; the `DependencyPicker.tsx` case avoids search-on-mount), the CLAUDE.md
  architecture rule states no disabled linting rules without documentation. Neither
  suppression has an explanatory comment beyond the inline lint-disable directive.
  The `useWorkItems.ts` case in particular should be reviewed — the deps array
  omits `filters` (the whole object) in favour of each sub-key, which is correct
  but non-obvious.
- **Recommendation:**
  Add a one-line comment above each `eslint-disable` explaining WHY it is safe to
  suppress: e.g. `// Safe: all filter sub-keys are listed individually below` for
  useWorkItems; `// Safe: search fires on user input only, not on mount` for
  DependencyPicker.
