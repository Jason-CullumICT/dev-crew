### QO-003: `dependencyCheckDuration` Prometheus histogram absent
- **Severity:** P2
- **Category:** pattern-violation
- **File:** `Source/Backend/src/metrics.ts:1`
- **Detail:** `FR-dependency-metrics` specifies 4 observability instruments: `dependencyOperations` counter, `dispatchGatingEvents` counter, `dependencyCheckDuration` histogram, `cycleDetectionEvents` counter. All three counters are implemented. The `dependencyCheckDuration` histogram (for measuring BFS cycle-detection and blocker-check latency) is absent. This means slow dependency checks are invisible in production — the histogram is the only instrument that would surface a pathological cycle detection over a large dependency graph.
- **Recommendation:** Add to `metrics.ts`:
  ```ts
  export const dependencyCheckDurationHistogram = new Histogram({
    name: 'dependency_check_duration_seconds',
    help: 'Duration of dependency readiness and cycle detection checks',
    labelNames: ['operation'] as const,
    buckets: [0.001, 0.005, 0.01, 0.05, 0.1, 0.5],
    registers: [registry],
  });
  ```
  Instrument `detectCycle()` and `computeHasUnresolvedBlockers()` with `.startTimer()` / `.observeDuration()`. [ESCALATE → TheFixer]

### QO-005: `WorkItemStatus` enum missing `pending_dependencies` value
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Source/Shared/types/workflow.ts:5`
- **Detail:** `FR-dependency-types` requires `pending_dependencies` to be added to the work item status enum. The current `WorkItemStatus` enum has 9 values (`backlog` → `failed`) but no `pending_dependencies`. The dispatch gating logic in `workflow.ts` blocks dispatch with a 400 error rather than setting the item to `pending_dependencies` status — the specified behavior. Update `dispatchAction` in `workflow.ts` to set `status: WorkItemStatus.PendingDependencies` instead of returning 400. This is a Shared type change — coordinate frontend/backend. [ESCALATE → TheFixer]
- **Cross-ref:** `Source/Backend/src/routes/workflow.ts:231`, `Source/Backend/src/services/dependency.ts`

### QO-008: Two logger modules with inconsistent usage
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Backend/src/logger.ts` / `Source/Backend/src/utils/logger.ts`
- **Detail:** The backend has two logger modules: `src/utils/logger.ts` (named export `{ logger }`, calls `emit(level, msg, ctx)`) and `src/logger.ts` (default export, compat wrapper that normalises object-style calls). Every file except `workItemStore.ts` imports from `../logger`. `workItemStore.ts` imports directly from `../utils/logger`. This means log entries from the store have a different call path. The normalize wrapper in `src/logger.ts` also strips the `msg` key from objects, flattening `{ msg, ...rest }` into positional args — the actual JSON emitted by the store is `{ timestamp, level, message, context }` while routes would produce the same shape through the compat layer, so end JSON is consistent, but the redundant module adds maintenance debt and confusion.
- **Recommendation:** Migrate all imports to `src/utils/logger.ts` (named export). Remove `src/logger.ts`. Update all callers to use `logger.info('message', { key: val })` style.
