The current state violates "do not suppress test output" and leaves the test suite red.

## QO-002: Routes Bypass Service Layer — Architecture Violation

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:12`, `Source/Backend/src/routes/workflow.ts:15`, `Source/Backend/src/routes/intake.ts:4`
- **Detail:** All three route files import `* as store from '../store/workItemStore'` and call store functions directly (`store.findById`, `store.updateWorkItem`, `store.createWorkItem`, `store.softDelete`). CLAUDE.md is explicit: **"No direct DB calls from route handlers — use the service layer."** Worst offender is `workflow.ts`: the approve/reject/dispatch handlers also build `ChangeHistoryEntry` objects and mutate `item.changeHistory` in-place before pushing to the store — that is business logic inside a route handler.
- **Failure scenario:** Any future change to store internals (e.g., adding persistence, caching, or validation) must be replicated across all three route files instead of being centralised in services. The pattern also prevents unit testing route business logic without hitting the store.
- **Recommendation:** Extract approve/reject/dispatch logic into a `workflowService.ts`. Route handlers should call `workflowService.approve(id, reason)` etc. The CRUD routes should delegate to a `workItemService.ts` that mediates all store access.
- **Cross-ref:** TheFixer

## QO-005: Dual Logger Implementations — Single-Source-of-Truth Violation

- **Severity:** P2
- **Category:** architecture-violation
- **Files:** `Source/Backend/src/utils/logger.ts:27`, `Source/Backend/src/logger.ts:5`, `Source/Backend/src/store/workItemStore.ts:10`
- **Detail:** Two logger objects exist:
  - `utils/logger.ts` — the actual implementation; takes `(msg: string, ctx?)` arguments
  - `logger.ts` — a wrapper that normalises `string | Record<string,unknown>` first arg (for the `{msg, ...}` spread pattern used by routes and services)

  `workItemStore.ts` imports directly from `utils/logger` using the two-arg signature. All other source files import from the top-level wrapper. Two callers with different interfaces for the same concern — a direct violation of "Shared types are single source of truth — no inline type re-definitions across layers."
- **Failure scenario:** A change to the `utils/logger` signature (e.g., adding a `traceId` param) must be replicated in both the wrapper and any direct consumers. A consumer using the wrong interface silently drops log context.
- **Recommendation:** Export a single logger from `utils/logger.ts` with the normalising wrapper built in, delete `logger.ts`, and update all imports to use `utils/logger`. One module, one interface.
- **Cross-ref:** TheFixer

## QO-006: Logger Does Not Respect LOG_LEVEL or NODE_ENV

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/utils/logger.ts:17`
- **Detail:** The logger implementation always:
  - Emits every log level (no `LOG_LEVEL` gate)
  - Uses structured JSON format (no dev pretty-printing)
  - Ignores `NODE_ENV`

  CLAUDE.md architecture rules: "Use structured JSON logging in production, **pretty-printing in development**" and "**`LOG_LEVEL` env var controls verbosity**."
- **Failure scenario:** Running in development, a developer cannot read logs (wall of minified JSON). Setting `LOG_LEVEL=error` has no effect — debug and info logs flood the output.
- **Recommendation:** Add `const level = process.env.LOG_LEVEL ?? 'info'` level filtering and `if (process.env.NODE_ENV !== 'production')` pretty-format branch. Or replace the hand-rolled logger with `pino` (already used in portal/Backend) which handles both concerns out of the box.
- **Cross-ref:** TheFixer
