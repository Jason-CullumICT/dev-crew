## QO-001: Primary Spec (dev-workflow-platform.md) Has Zero Source Coverage

- **Severity:** P1
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md`
- **Detail:** `Specifications/dev-workflow-platform.md` is described in CLAUDE.md as "The most critical documents." It defines 69 functional requirements (FR-001 through FR-069) covering a full 7-subsystem dev platform (FR intake, AI voting, human approval, bug tracking, dev cycles, CI/CD, learnings) backed by SQLite. Zero lines of source code carry a `// Verifies: FR-0NN` comment. The source codebase instead implements `workflow-engine.md` using the separate ID scheme `FR-WF-001..013` sourced from `Plans/self-judging-workflow/requirements.md`.

  This means one of two things is true — both are serious:
  - **Case A**: The implemented system is the wrong system. The team built `workflow-engine.md` but the authoritative spec is `dev-workflow-platform.md`. Large divergence in tech stack (SQLite vs in-memory), data model, and business rules.
  - **Case B**: `dev-workflow-platform.md` is a future/aspirational spec that was never started. The spec directory is mislabeled as "most critical" when it is actually aspirational, and the canonical requirements live in `Plans/`.

  Either way, no implementation traces back to the named "source of truth" specification.

- **Recommendation:**
  1. Determine which case applies and document the decision in CLAUDE.md.
  2. If Case B: move FR-WF-* requirements into `Specifications/` (or update CLAUDE.md to point to Plans as the requirements source), and update the traceability enforcer's target.
  3. If Case A: align implementation with dev-workflow-platform.md or update the spec to match what was built.

- **Cross-ref:** Affects QO-004 (enforcer scope). Escalate to requirements-reviewer before next sprint.

## QO-006: `eslint-disable` Suppresses react-hooks/exhaustive-deps

- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Two suppressions of `react-hooks/exhaustive-deps` exist in recently-modified frontend files. Missing dependencies in useEffect/useCallback hooks are a common source of stale-closure bugs (hook fires but uses outdated values from a previous render). Suppressing the rule rather than fixing the dependency array hides the underlying issue.
- **Recommendation:** Remove each `eslint-disable` comment and fix the hook dependency arrays properly — either add the missing dependencies or use `useCallback`/`useRef` to stabilise function references. At minimum, document why the suppression is safe via an inline comment that explains the intentional design.
- **Cross-ref:** Route to frontend-coder. No security risk, but real bug risk under concurrent state updates.

## QO-007: Hardcoded URL Fallback in DebugPortalPage

- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/pages/DebugPortalPage.tsx:5`
- **Detail:** `const portalUrl = import.meta.env.VITE_PORTAL_URL || 'http://localhost:4200';` — CLAUDE.md architecture rule: "No hardcoded secrets — use environment variables via `.env`". Hardcoding `localhost:4200` as a fallback means the component silently works in dev but could behave unexpectedly in any non-local environment where the env var is absent (e.g., CI or staging). The fallback masks the misconfiguration.
- **Recommendation:** Remove the `|| 'http://localhost:4200'` fallback. Either require the env var (throw/render error when absent) or add `VITE_PORTAL_URL=http://localhost:4200` to `.env.example` and `.env.development`. The env var path is correct; the inline fallback is not.
- **Cross-ref:** [ESCALATE → TheGuardians] if this component is reachable in production; otherwise route to frontend-coder via TheFixer.
