## Findings

### QO-001: FR-dependency-api-types NOT implemented — `as any` cast active in production
- **Severity:** P2
- **Category:** spec-drift
- **File:** `portal/Shared/api.ts:32,59` and `portal/Frontend/src/components/shared/DependencyPicker.tsx:291,293`
- **Detail:** `UpdateBugInput` and `UpdateFeatureRequestInput` in `portal/Shared/api.ts` do not include the required `blocked_by?: string[]` field (FR-dependency-api-types). As a workaround, `DependencyPicker.tsx` uses `as any` casts on lines 291 and 293 when calling `.update()` with the `blocked_by` payload. This means the PATCH body is type-unsafe end-to-end: type errors in the dependency field will not be caught at compile time.
- **Recommendation:** Add `blocked_by?: string[]` to both input types in `portal/Shared/api.ts`; remove the `as any` casts in `DependencyPicker.tsx`. Add `// Verifies: FR-dependency-api-types` comment to the new fields.
- **Cross-ref:** `Plans/dependency-linking/requirements.md` row FR-dependency-api-types marked ❌ in the plan's status table.

### QO-002: FR-dependency-seed NOT implemented — dependency seed data absent
- **Severity:** P2
- **Category:** spec-drift
- **File:** `portal/Backend/src/database/` (file `seed.ts` is missing)
- **Detail:** FR-dependency-seed specifies an idempotent `seed.ts` that inserts known dependency relationships (BUG-0010 blocked_by BUG-0003/0004/0005/0006/0007; FR-0004 blocked_by FR-0003; FR-0005 blocked_by FR-0002; FR-0007 blocked_by FR-0003) on server startup. The `portal/Backend/src/database/` directory contains only `connection.ts` and `schema.ts` — no `seed.ts` exists. This means the acceptance criterion "GET /api/bugs/BUG-0010 returns 5 items in blocked_by" cannot be met in a fresh environment.
- **Recommendation:** Create `portal/Backend/src/database/seed.ts`; wire it into `portal/Backend/src/index.ts` startup call. Add `// Verifies: FR-dependency-seed` traceability. Ensure idempotent guard (do not re-insert if links already exist).
- **Cross-ref:** `Plans/dependency-linking/requirements.md` row FR-dependency-seed marked ❌.

### QO-003: Traceability enforcer hardcodes `Source/` — silently misses `portal/` implementations
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `tools/traceability-enforcer.py:70`
- **Detail:** The enforcer hard-codes `source_dirs = ["Source", "E2E"]`. The dev-workflow-platform codebase lives in `portal/` (FR-001–FR-095, FR-DUP-*, FR-dependency-*). When the enforcer is run against any portal-targeted plan (e.g., `Plans/dependency-linking/requirements.md`), it reports 7 false failures because it cannot see `portal/` implementations that do carry `// Verifies: FR-XXX` comments. Simultaneously, it *silently never scans* `portal/` against the dev-workflow-platform plan, giving a false sense of full coverage. The tiered-merge-pipeline requirements (`FR-TMP-*`) live in `platform/` and are equally invisible to the enforcer.
- **Recommendation:** Extend the enforcer to read `source_dirs` from `inspector.config.yml` (the config already defines `source.dirs: ["Source/"]`), or add a `--dirs` CLI flag. A minimal fix: add `portal` and `platform/orchestrator` to the scan list and let plans declare which dirs apply.
- **Cross-ref:** CLAUDE.md verification gate: `python3 tools/traceability-enforcer.py` — currently this gate only validates FR-WF-* (self-judging-workflow plan, auto-selected by recency), making it unable to catch drift in portal/ or platform/.

### QO-005: Two logger modules coexist in `Source/Backend/src/`
- **Severity:** P3
- **Category:** architecture-violation
- **File:** `Source/Backend/src/logger.ts` and `Source/Backend/src/utils/logger.ts`
- **Detail:** `src/utils/logger.ts` is the canonical structured JSON logger. `src/logger.ts` is a compatibility shim that re-exports it with a different calling convention (accepts `string | Record<string,unknown>` as first arg). Both carry `// Verifies: FR-WF-013` comments. The shim's comment says it exists because "Backend-coder-2's workflow routes import logger as default from this module." This dual-module pattern creates ambiguity about the correct import path and accumulates tech debt. New contributors may import either, leading to inconsistent call signatures.
- **Recommendation:** Consolidate: update the routes that import from `./logger` to import from `./utils/logger` directly (adjusting call sites to always pass `string` as first arg), then delete `src/logger.ts`. This eliminates the wrapper.

### QO-006: `eslint-disable-next-line react-hooks/exhaustive-deps` in two production hooks/components
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63` and `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Two `eslint-disable-next-line react-hooks/exhaustive-deps` suppressions exist in production code. Per architecture rules, suppressing linting rules without documentation is a code smell. The hooks rule violation can mask stale-closure bugs where the hook re-fetches on wrong dependency changes (or never re-fetches when it should).
- **Recommendation:** For each suppression: audit whether the missing dependency is safe to omit (document reasoning in a comment above the disable line), or fix the hook signature to correctly express the dependency without suppression.
