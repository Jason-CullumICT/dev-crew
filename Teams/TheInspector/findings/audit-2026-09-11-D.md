## QO-003: Traceability enforcer default scope masks two failing plans

- **Severity:** P2
- **Category:** pattern-violation
- **File:** `tools/traceability-enforcer.py:57`
- **Detail:** `get_active_requirements()` falls back to `max(req_files, key=os.path.getmtime)` — the most recently modified `requirements.md`. On this codebase that resolves to `Plans/self-judging-workflow/requirements.md` (100% covered), silently skipping the two failing plans. The CLAUDE.md verification gate command `python3 tools/traceability-enforcer.py` (without `--file`) always exits 0, giving developers a false green signal. This means the gate command documented in CLAUDE.md is effectively broken for multi-plan projects.
- **Recommendation:** Update the CLAUDE.md "Verification gates" section to enumerate all three plans explicitly, OR modify `traceability-enforcer.py` to scan all `Plans/**/requirements.md` files and fail if any has missing FRs. Example fix for `main()`: iterate `plans_dir.glob("**/requirements.md")`, call `check_traceability()` for each, accumulate failures, exit 1 if any exist.

## QO-004: Route handlers bypass the service layer (direct store calls)

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:12`, `Source/Backend/src/routes/intake.ts:4`, `Source/Backend/src/routes/workflow.ts:15`
- **Detail:** All three route files import and call `workItemStore` directly (`import * as store from '../store/workItemStore'`). The store exposes `createWorkItem`, `findById`, `findAll`, `updateWorkItem`, `softDelete`. Route handlers invoke these functions directly, violating the architecture rule: "No direct DB calls from route handlers — use the service layer." While the data layer is in-memory (not a SQL database), the principle is identical: business logic and data access are embedded in HTTP route handlers rather than isolated in a service layer. The existing `assessment.ts`, `router.ts`, `dependency.ts`, `changeHistory.ts`, and `dashboard.ts` files show the correct service pattern — routes should call those abstractions.
- **Recommendation:** Extract a `workItemService.ts` service module. Move `createWorkItem`, `getWorkItemById`, `listWorkItems`, `updateWorkItem`, `softDeleteWorkItem` into it. Route handlers import from the service, not from the store. The store becomes an internal implementation detail of the service.
- **Cross-ref:** [ESCALATE → TheFixer] for refactoring

## QO-005: Duplicate test files for WorkItemDetailPage and WorkItemListPage

- **Severity:** P3
- **Category:** test-coverage
- **File:** `Source/Frontend/tests/WorkItemDetailPage.test.tsx` AND `Source/Frontend/tests/pages/WorkItemDetailPage.test.tsx`; similarly for `WorkItemListPage`
- **Detail:** Both test paths exist and both carry `// Verifies: FR-WF-011` / `// Verifies: FR-WF-010` comments. They are not identical — the `tests/pages/` versions are slightly larger (393 vs 368 lines for detail; 262 vs 286 lines for list). Having two files testing the same component creates ambiguity: which is authoritative? New test cases may be added to one but not the other. In CI, both run, but if they diverge, it's unclear which represents the current spec.
- **Recommendation:** Consolidate into a single canonical file per component. Merge unique test cases into `tests/pages/` (the larger, more recent set) and delete the top-level duplicates. Update traceability comments in the surviving file.
- **Cross-ref:** [ESCALATE → TheFixer]

## QO-006: `eslint-disable-next-line` suppressions without documented justification

- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`, `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Both files suppress `react-hooks/exhaustive-deps` with `// eslint-disable-next-line`. Per the architecture rule "Never swallow errors silently — every `catch` block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed," the same principle should apply to linting suppressions. No comment explains why the dependency array is intentionally incomplete. This risks stale closure bugs.
- **Recommendation:** Add an inline comment after each suppress explaining the intentional omission (e.g., `// intentionally omit X to avoid infinite re-fetch loop`), or better, refactor the effect to correctly declare dependencies using `useCallback`.
- **Cross-ref:** N/A
