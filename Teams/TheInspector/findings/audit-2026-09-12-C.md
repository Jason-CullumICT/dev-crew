## Findings

### QO-001: Unregistered Route — GET /api/search Missing from app.ts
- **Severity:** P1
- **Category:** correctness
- **File:** `Source/Backend/src/app.ts` / `Source/Backend/tests/routes/search.test.ts:1`
- **Detail:** The FR-dependency-search requirement calls for `GET /api/search` as a cross-entity typeahead endpoint. The test file `Source/Backend/tests/routes/search.test.ts` **explicitly documents** that the route is not wired: *"NOTE: As of this review cycle the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."* — yet `app.ts` has no `import` or `app.use` for a search router.
- **Failure scenario:** Any call to `GET /api/search?q=<term>` returns 404 on the live app. The DependencyPicker typeahead silently returns no results. Users cannot search for items to link as blockers.
- **Recommendation:** Create `Source/Backend/src/routes/search.ts`, implement the endpoint (filtering workItemStore by title/description), mount it in `app.ts` with `app.use('/api', searchRouter)`, and confirm the existing search tests pass.
- **Cross-ref:** TheFixer (code fix); FR-dependency-search

### QO-002: Spec/Implementation Divergence — dev-workflow-platform.md (69 FRs) Has Zero Source Coverage
- **Severity:** P2
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md`
- **Detail:** `Specifications/dev-workflow-platform.md` is the canonical domain spec referenced in `CLAUDE.md` and defines 69 functional requirements (FR-001…FR-069) covering Feature Requests, Bug Reports, Development Cycles, Pipeline Orchestration, and CI/CD. **Zero** of these FR IDs appear in any `// Verifies:` comment in `Source/`. The source instead implements a `WorkItem`-based workflow engine specified in `Specifications/workflow-engine.md`. These are fundamentally different systems: the platform spec manages named `FeatureRequest`/`BugReport`/`DevelopmentCycle` entities; the source manages generic `WorkItem` objects routed through an assessment pod.
- **Failure scenario:** Any developer consulting the primary spec to understand what is built will be misled. The spec says `GET /api/feature-requests` exists; the app serves `GET /api/work-items`. The spec says bugs are tracked separately as `BugReport`; the app treats bugs as a `WorkItem` type. This creates onboarding risk and makes spec-based audits unreliable.
- **Recommendation:** This is a strategic decision that must be made explicitly: either (a) update `dev-workflow-platform.md` to reflect the WorkItem domain actually built, retiring FR-001…069 as superseded; or (b) confirm the platform spec is a future phase and add a prominent header to that effect. Either way, add a Note in `CLAUDE.md` clarifying which spec governs the current Source/.
- **Cross-ref:** requirements-reviewer; Specifications team

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `tools/traceability-enforcer.py`
- **Detail:** The enforcer auto-selects the most recently modified `requirements.md` under `Plans/`. This means it only enforces `Plans/self-judging-workflow/requirements.md` (FR-WF-001…013). All FR-dependency-* requirements and all FR-TMP-* requirements are invisible to the gating check. A passing enforcer result is reported as "TRACEABILITY PASSED: All requirements have implementation references" — which is technically accurate for that one plan but misleading at the project level. The two other active requirement sets (dependency-linking plan and tiered-merge-pipeline spec) are never gated.
- **Failure scenario:** A coder ships without FR-dependency-* Verifies comments; the gate still passes. Future regressions in dependency functionality are undetected by the verification gate.
- **Recommendation:** Run the enforcer against each plan separately (or add a `--all` flag that checks every `requirements.md` under `Plans/`). At minimum, add `Plans/dependency-linking/requirements.md` pointing at the FR-dependency-* IDs so the gate covers them.
- **Cross-ref:** tools/ maintainer

### QO-006: Silent Error Swallow in api/client.ts — Violates "Never Swallow Errors" Rule
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Frontend/src/api/client.ts:26`
- **Detail:** Line 26: `const body = await response.json().catch(() => ({}));` — the `.catch(() => ({}))` absorbs any JSON parse error and substitutes an empty object. This violates the architecture rule: *"never swallow errors silently — every catch block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."* No comment explains why this is intentional.
- **Failure scenario:** If the backend returns a malformed or non-JSON body (e.g., an HTML error page from a proxy), the client silently treats it as `{}`, discards the actual error, and the caller sees an empty response with no indication of failure. Error diagnostics are lost.
- **Recommendation:** Either re-throw (letting the caller handle) or log the parse error and rethrow: `const body = await response.json().catch((err) => { console.error('JSON parse failed:', err); throw err; });` — or replace with the project's logger abstraction if one exists on the frontend.
- **Cross-ref:** TheFixer

### QO-007: eslint-disable Suppressions — Two Hooks May Have Stale Closure Bugs
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`, `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Both files suppress `react-hooks/exhaustive-deps` with `// eslint-disable-next-line`. This rule exists to prevent bugs where effects/callbacks close over stale values. Suppressing it without explanation is tech debt that can hide subtle state bugs on re-renders.
- **Recommendation:** Add inline comments justifying each suppression (e.g., "stable ref — intentionally not in deps"). If the deps are truly missing, add them and verify the behavior.
- **Cross-ref:** TheFixer
