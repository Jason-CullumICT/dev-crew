## Findings

### QO-001: Traceability Enforcer Is Single-Plan — 7 Plans Silently Unenforced
- **Severity:** P2
- **Category:** spec-drift
- **File:** `tools/traceability-enforcer.py` (enforcer design), `Plans/*/requirements.md`
- **Detail:** The enforcer's fallback selects the `max(..., key=os.path.getmtime)` file — always one plan. With 8 requirements files across 8 plans (dependency-linking, dev-cycle-traceability, orchestrated-dev-cycles, image-upload, duplicate-deprecated-status, orchestrator-cycle-dashboard, dev-workflow-platform, self-judging-workflow), only the most-recently-modified plan is ever checked. The other 7 — including plans with known open delta items — receive zero automated enforcement. A regression in any of those plans passes the verification gate silently.
- **Recommendation:** Pass `--all-plans` mode to enforcer (or add it): loop over every `Plans/*/requirements.md` and run the trace check for each. Alternatively, maintain a `Plans/active-plans.txt` manifest that the enforcer reads.
- **Cross-ref:** QO-002, QO-003, QO-004 (all open delta items in un-enforced plans)

### QO-002: FR-dependency-api-types — `blocked_by` Field Missing from Update Inputs (portal)
- **Severity:** P2
- **Category:** spec-drift
- **File:** `portal/Shared/api.ts:32` (`UpdateFeatureRequestInput`), `portal/Shared/api.ts:59` (`UpdateBugInput`)
- **Detail:** The dependency-linking plan (FR-dependency-api-types) requires `blocked_by?: string[]` on both update input types. Both interfaces are present in `portal/Shared/api.ts` but lack the field. This was documented as ❌ Missing in the plan delta and is still unimplemented. The portal's `DependencyPicker` frontend must use an `as any` cast to call PATCH with `blocked_by`, bypassing TypeScript safety end-to-end.
- **Recommendation:** Add `blocked_by?: string[]` to `UpdateFeatureRequestInput` and `UpdateBugInput` in `portal/Shared/api.ts`, then remove the `as any` cast(s) in `portal/Frontend/src/components/shared/DependencyPicker.tsx`.
- **Cross-ref:** QO-001 (enforcer blind to this plan)

### QO-003: FR-dependency-seed — Seed File Missing (portal)
- **Severity:** P2
- **Category:** spec-drift
- **File:** `portal/Backend/src/database/` (missing `seed.ts`)
- **Detail:** The dependency-linking plan (FR-dependency-seed) requires an idempotent `seed.ts` that inserts 4 known dependency relationships on server startup (BUG-0010 blocked_by BUG-0003/0004/0005/0006/0007; FR-0004 blocked_by FR-0003; FR-0005 blocked_by FR-0002; FR-0007 blocked_by FR-0003). The `portal/Backend/src/database/` directory only contains `connection.ts` and `schema.ts`. No seed file exists. Fresh dev/staging environments will have no dependency seed data, making the dependency feature untestable without manual setup.
- **Recommendation:** Create `portal/Backend/src/database/seed.ts` per the plan spec; call it from server startup after schema init with an idempotency guard.

### QO-005: Logger Never Pretty-Prints in Development (Spec Deviation)
- **Severity:** P3
- **Category:** architecture-violation
- **File:** `Source/Backend/src/utils/logger.ts:14-23`
- **Detail:** FR-003 and FR-WF-013 both require "structured JSON in production; pretty-printing in development." The logger always calls `process.stdout.write(JSON.stringify(entry) + '\n')` regardless of `NODE_ENV`. There is no `process.env.NODE_ENV` check anywhere in the logger. Development logs are unreadable dense JSON blobs, violating the spec acceptance criteria: "All log output is structured JSON in NODE_ENV=production; logger is the only log sink."
- **Recommendation:** Add a NODE_ENV branch: in development (or when `LOG_LEVEL` dev mode is detected), pretty-print with `JSON.stringify(entry, null, 2)` or use `pino-pretty`. In production, keep compact JSON.
- **Cross-ref:** None

### QO-007: Error Discrimination by String-Matching in Dependency Endpoint (Fragile)
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Backend/src/routes/workflow.ts:330-348`
- **Detail:** The catch block for `POST /api/work-items/:id/dependencies` determines HTTP status code by string-matching the caught error's `.message`: `includes('self')` → 400, `includes('not found')` → 404, `includes('cycle') || includes('circular')` → 409, else → 500. This is fragile: if `Source/Backend/src/services/dependency.ts` ever changes its error message text (e.g., "circular dependency detected" → "cycle detected"), the catch block silently returns 500 instead of 409. The architecture rule is "never swallow errors silently" — this pattern can silently downgrade explicit 409s to 500s.
- **Recommendation:** Use custom error subclasses (`class SelfReferenceError extends Error`, `class CircularDependencyError extends Error`) in the dependency service, then catch by type (`instanceof`) in the route handler. This is robust to message rewording.
- **Cross-ref:** None

### QO-008: Logger API Inconsistency — workItemStore vs. All Other Backend Files
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Backend/src/store/workItemStore.ts:10`
- **Detail:** `workItemStore.ts` imports `{ logger }` directly from `'../utils/logger'` (named export, two-arg API: `logger.info('message', { ctx })`). Every other backend file (`app.ts`, all routes, all services, `errorHandler.ts`) imports the default export from `'../logger'` (single-object API: `logger.info({ msg: 'message', ...ctx })`). The two exports have different calling conventions. A developer adding code to `workItemStore.ts` while following the conventions seen in routes/services would use the wrong logger import or API.
- **Recommendation:** Migrate `workItemStore.ts` to import from `'../logger'` (default) using the object API, and delete or unexport the named export from `utils/logger` to eliminate the dual-API surface.
- **Cross-ref:** None

### QO-009: Two `eslint-disable-next-line` Suppressions Without Justification
- **Severity:** P4
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`, `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Both suppress `react-hooks/exhaustive-deps`. The rule catches stale-closure bugs. The suppressions may be intentional (the deps are deliberately omitted for performance/correctness), but there are no inline comments explaining why suppression is correct. This violates the pattern check and creates maintenance risk — future developers may not know whether the omission is safe.
- **Recommendation:** Add a one-line comment above each `eslint-disable` explaining why the dep is intentionally omitted. Example: `// filter deps excluded intentionally — string-only values, no object instability risk`.
- **Cross-ref:** None
