## Findings

### QO-001: Canonical spec (FR-001..FR-069) has zero implementation coverage
- **Severity:** P1
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md:337-452`
- **Detail:** `Specifications/dev-workflow-platform.md` defines 69 formal requirements (FR-001 through FR-069) for a feature-request/bug-report/development-cycle platform. None of these are referenced anywhere in `Source/`. The current implementation is the "Self-Judging Workflow Engine" (FR-WF-001..013 in `Plans/`), a completely different product. The canonical spec file therefore either describes an abandoned product or an unstarted milestone. The traceability enforcer does NOT scan against this spec — it only checks `Plans/self-judging-workflow/requirements.md`. This creates a false 100% coverage signal while 69 requirements are completely invisible.
- **Recommendation:** Clarify the status of FR-001..FR-069. If this is a future milestone, add a `status: future` label in the spec. If it is a separate product entirely, move it to `docs/` or `Plans/` and remove it from the canonical `Specifications/` truth. Update the traceability enforcer to also scan against `Specifications/dev-workflow-platform.md` FR requirements, or explicitly mark that spec as out-of-scope for the current codebase.
- **Cross-ref:** Requirements Reviewer (spec ownership), TheFixer (enforcer update)

### QO-003: Route handlers import store directly — architecture rule violation
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:12`, `Source/Backend/src/routes/workflow.ts:15`, `Source/Backend/src/routes/intake.ts:4`
- **Detail:** Architecture rule states **"No direct DB calls from route handlers — use the service layer."** Three route files import and call `workItemStore` directly:
  - `workItems.ts`: `store.createWorkItem`, `store.findAll`, `store.findById`, `store.updateWorkItem`, `store.softDelete`
  - `workflow.ts`: `store.findById`, `store.updateWorkItem`, `store.getAll` (via various workflow actions)
  - `intake.ts`: `store.createWorkItem`
  
  There is no intermediary service layer for WorkItem CRUD — only for specific sub-concerns (assessment, changeHistory, dashboard, dependency, router). This couples route logic to store details.
- **Recommendation:** Extract WorkItem CRUD operations into a `workItemService.ts` (alongside the existing `assessment.ts`, `dashboard.ts`, etc.). Route handlers should call `workItemService.*` not `store.*` directly. This is a medium refactor — route to TheFixer.
- **Cross-ref:** [ESCALATE → TheFixer]

### QO-007: ESLint rules suppressed without documented justification
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`, `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Two `// eslint-disable-next-line react-hooks/exhaustive-deps` suppressions exist in production source. The architecture rules require using the project's patterns without workarounds. Both suppressions likely hide missing dependencies in `useEffect` hooks that could cause stale-closure bugs in edge cases.
- **Recommendation:** Fix the underlying dependency arrays instead of suppressing the rule. If suppression is genuinely correct (e.g., intentional one-time-mount effect), add a comment explaining WHY: `// eslint-disable-next-line react-hooks/exhaustive-deps -- intentional: fetch on mount only, params are stable refs`.

### QO-008: DependencyPicker silently suppresses search errors — no logging
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/components/DependencyPicker.tsx:56-58`
- **Detail:** The catch block for the search call deliberately suppresses errors: `// Search errors are intentionally suppressed: UI falls back to empty results`. While the comment provides justification, this violates the architecture rule: **"Never swallow errors silently — every catch block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."** The comment documents the why, but there is no logging. A network failure or server error will silently produce an empty results list with no observability.
- **Recommendation:** Add a `console.warn` or frontend logger call before setting empty results: `logger.warn('dependency search failed, falling back to empty results', { error })`. This retains the UX fallback while preserving observability.

### QO-010: Two logger abstractions — utils/logger.ts and logger.ts
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Backend/src/logger.ts`, `Source/Backend/src/utils/logger.ts`
- **Detail:** Two logger files exist:
  - `Source/Backend/src/utils/logger.ts` — the real structured logger
  - `Source/Backend/src/logger.ts` — a compatibility wrapper that re-exports `utils/logger` with a different signature

  The CLAUDE.md rule is "Use the project's logger abstraction, never `console.log`" — but which abstraction is canonical? Some files import from `../logger` (the wrapper), others from `../utils/logger` (the real one). This fragmentation risks different log formats in production.
- **Recommendation:** Choose one canonical logger path and update all imports to use it. Deprecate or remove the wrapper if it's only needed for backward compatibility with a few files.
