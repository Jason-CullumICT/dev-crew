## Findings

### QO-001: Domain Spec vs Implementation — Fundamental System Mismatch
- **Severity:** P2
- **Category:** spec-drift
- **Files:** `Specifications/dev-workflow-platform.md`, `Source/Backend/src/`, `Source/Frontend/src/`
- **Detail:** `Specifications/dev-workflow-platform.md` (the domain truth per CLAUDE.md) defines 74 unique FR IDs (FR-001 through FR-069) describing a SQLite-backed system with entities: `FeatureRequest`, `BugReport`, `DevelopmentCycle`, `Ticket`, `Vote`, `Learning`, `Feature`. The current implementation is an in-memory `WorkItem` workflow engine — a fundamentally different domain model. Zero of the domain spec's 74 FRs are referenced anywhere in `Source/`. The active plan `Plans/self-judging-workflow/requirements.md` (FR-WF-001 to FR-WF-013) was built as a replacement scope, but the domain spec in `Specifications/` has not been updated to reflect this pivot.
- **Recommendation:** Either (a) update `Specifications/dev-workflow-platform.md` to match the WorkItem domain (retire FR-001..FR-069 with tombstone notes, add FR-WF-* as canonical), or (b) create a new domain spec file for the WorkItem system and deprecate the old one. The domain truth must match the implementation.
- **Cross-ref:** RequirementsReviewer should own this update.

### QO-002: Unimplemented Feature — `GET /api/search` Route Not Wired
- **Severity:** P2
- **Category:** spec-drift / untested
- **File:** `Source/Backend/tests/routes/search.test.ts:1`
- **Detail:** The search route test file (`Verifies: FR-dependency-search`) explicitly documents that `GET /api/search` is **not registered** in `Source/Backend/src/app.ts`. The test comment reads: *"As of this review cycle the GET /api/search endpoint is NOT wired into app.ts. These tests document the expected contract and will FAIL until the route is implemented."* No `Source/Backend/src/routes/search.ts` exists; the endpoint is absent from `app.ts`. This means 100% of search tests will fail when run.
- **Recommendation:** Implement `Source/Backend/src/routes/search.ts` and register it in `app.ts`, or move the requirement to a backlog item and remove/mark the tests as `test.skip` so CI passes cleanly.
- **Cross-ref:** [ESCALATE → TheFixer] for implementation.

### QO-003: Architecture Rule Violation — Routes Import Store Directly (No Service Layer)
- **Severity:** P2
- **Category:** architecture-violation
- **Files:** 
  - `Source/Backend/src/routes/workItems.ts:12` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/workflow.ts:15` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/intake.ts:4` — `import * as store from '../store/workItemStore'`
- **Detail:** CLAUDE.md architecture rule: *"No direct DB calls from route handlers — use the service layer."* All three route files import and invoke `store.*` directly: `store.createWorkItem`, `store.findById`, `store.findAll`, `store.updateWorkItem`, `store.softDelete`. There is a `services/` directory with `assessment.ts`, `router.ts`, `dependency.ts`, `dashboard.ts`, `changeHistory.ts`, but no `workItemService.ts` to mediate CRUD operations. The store is the in-memory data layer (equivalent to a DB); route handlers must not reach it directly.
- **Recommendation:** Create `Source/Backend/src/services/workItemService.ts` exposing `createItem`, `getItem`, `listItems`, `updateItem`, `deleteItem`. Refactor the three route files to import from the service, not the store.
- **Cross-ref:** [ESCALATE → TheFixer].

### QO-004: Traceability Enforcer Scope Too Narrow — Passes with False Confidence
- **Severity:** P2
- **Category:** spec-drift
- **File:** `tools/traceability-enforcer.py`
- **Detail:** The enforcer targets the **most-recently-modified** `requirements.md` in `Plans/` (currently `Plans/self-judging-workflow/requirements.md`). It passes (100%) because the 13 FR-WF-* requirements are all traced. However, it never checks: (a) domain specs in `Specifications/` with 74 unimplemented FRs, (b) older plan requirements files (e.g., `Plans/dev-workflow-platform/requirements.md` which has its own FR-001..FR-069 superset), or (c) `FR-dependency-*` style IDs which don't match the `FR-\d+` regex pattern. A pipeline that reports "TRACEABILITY PASSED" while 74 domain FRs are completely absent creates systemic risk.
- **Recommendation:** Extend the enforcer with a `--all-plans` flag that checks every `requirements.md` in `Plans/`. Also add a `Specifications/` sweep mode. Add a coverage summary per spec file to the report.

### QO-005: Logger Always Emits JSON — No Development Pretty-Print Mode
- **Severity:** P3
- **Category:** spec-drift
- **File:** `Source/Backend/src/utils/logger.ts:1`
- **Detail:** FR-WF-013 and FR-003 specify *"structured JSON in production, pretty-printing in development."* The logger always calls `process.stdout.write(JSON.stringify(entry))` regardless of `NODE_ENV`. The `LOG_LEVEL` env var referenced in CLAUDE.md is not read by the logger. Development experience suffers as all log output is minified JSON.
- **Recommendation:** Add `NODE_ENV` check: when `NODE_ENV !== 'production'`, use a human-readable format (e.g., `[INFO] message {context}`).

### QO-006: Duplicate Logger Implementations — Compat Shim Adds Confusion
- **Severity:** P3
- **Category:** architecture-violation
- **Files:** `Source/Backend/src/logger.ts`, `Source/Backend/src/utils/logger.ts`
- **Detail:** Two logger files exist. `src/logger.ts` is a compatibility wrapper that re-exports `utils/logger` with a different call signature (`msgOrObj: string | Record`). This was created as a shim because different route/service authors used different import paths. The existence of two loggers is confusing, creates maintenance surface, and the shim pattern itself adds unnecessary indirection.
- **Recommendation:** Standardize on `src/utils/logger.ts` as the canonical logger, update the signature if needed, and remove `src/logger.ts`. Update all imports across the codebase.

### QO-007: Non-Standard FR ID Scheme — `FR-dependency-*` IDs Bypass Traceability Enforcer
- **Severity:** P3
- **Category:** spec-drift
- **Files:** `Source/Backend/tests/services/dependency.test.ts:1`, `Source/Backend/tests/services/types.test.ts:1`
- **Detail:** Several test files use freeform IDs like `FR-dependency-service`, `FR-dependency-backend-tests`, `FR-dependency-search`, `FR-dependency-dispatch-gating`. The traceability enforcer's regex is `FR-\d+` — these freeform IDs don't match. There is no `Plans/*/requirements.md` that defines these IDs either, meaning they reference requirements that exist nowhere formally. They're orphaned traceability markers.
- **Recommendation:** Register these requirements in a `Plans/dependency-linking/requirements.md` with numeric IDs (e.g., FR-DEP-001), or align with the numeric FR-WF-* scheme. Update all `Verifies:` comments to use the registered IDs.

### QO-008: ESLint-Disable Comments in Production Frontend Code
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Two disabled ESLint rules in production source. `react-hooks/exhaustive-deps` violations typically indicate missing dependencies in `useEffect`/`useCallback`/`useMemo` hooks, which can cause stale closure bugs.
- **Recommendation:** Fix the underlying hook dependency issue rather than disabling the lint rule. If the suppression is intentional (e.g., infinite-loop prevention), add a comment explaining why the dependency is intentionally omitted.
