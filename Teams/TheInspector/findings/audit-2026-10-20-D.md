## QO-001: Specification Identity Crisis — Main Spec is for a Different System

- **Severity:** P2
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md`
- **Detail:** `Specifications/dev-workflow-platform.md` defines 69 FRs (FR-001 through FR-069) for a "Development Workflow Platform" built around FeatureRequest, BugReport, DevelopmentCycle, and PipelineRun entities. The actual source code implements a completely different system — a "Self-Judging Workflow Engine" with WorkItem, WorkRouter, and AssessmentPod — whose requirements live in `Plans/self-judging-workflow/requirements.md`. The FR ID format is also entirely different (FR-001 vs FR-WF-001), making automated cross-checking impossible. **None** of the 69 FRs in the primary specification have a matching `// Verifies: FR-XXX` comment anywhere in `Source/`.
- **Recommendation:** One of two resolutions is needed: (a) Archive `dev-workflow-platform.md` to a `Specifications/archived/` folder and create a new spec that describes the _workflow engine_ that was actually built; or (b) Determine that the workflow engine is the _platform infrastructure_ and update `dev-workflow-platform.md` to reflect the current domain model. The CLAUDE.md rule "Specs are source of truth — implementation traces to specs, never the other way around" is currently violated.
- **Cross-ref:** TheATeam, Requirements Reviewer — requires spec authorship decision before any new features are added.

## QO-002: FR-dependency-search — Endpoint Not Registered (Failing Tests Suppressed by Design)

- **Severity:** P2
- **Category:** spec-drift / untested
- **File:** `Source/Backend/src/app.ts`, `Source/Backend/tests/routes/search.test.ts`
- **Detail:** `FR-dependency-search` requires `GET /api/search?q=` cross-entity typeahead endpoint. The test file (`search.test.ts:1-6`) explicitly documents: "GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests will FAIL until the route is implemented." Checking `app.ts` confirms no `/api/search` route is registered. This is a knowingly broken requirement: the tests exist and will fail at runtime.
- **Recommendation:** Implement and register the `/api/search` route, or if intentionally deferred, add the test file to a `.skip` with a linked issue tracker entry and stop calling the enforcer "PASSED" while the gap exists.
- **Cross-ref:** [ESCALATE → TheFixer] — backend implementation task.

## QO-003: OpenTelemetry / W3C traceparent — Architecture Rule with Zero Implementation

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/` (all files)
- **Detail:** `CLAUDE.md` Observability architecture rules require: "Use OpenTelemetry for distributed tracing", "Auto-instrument HTTP, database, and framework calls", "Add custom spans for critical paths", "Propagate W3C `traceparent` header across service boundaries." The backend `package.json` lists `pino` and `prom-client` as direct dependencies, but `@opentelemetry/api` appears only as a transitive dependency (via `prom-client`) and is never imported or used anywhere in `Source/Backend/src/`. There are zero calls to `startSpan`, `createSpan`, or any OTel API. The `traceparent` header is never read or forwarded. Prometheus metrics and structured logging are correctly implemented — only OTel tracing is missing.
- **Recommendation:** Install `@opentelemetry/sdk-node`, `@opentelemetry/auto-instrumentations-node` as direct dependencies. Add an OTel setup file (e.g. `src/tracing.ts`) that initializes the SDK and auto-instruments Express. Propagate `traceparent` in the request-logging middleware.
- **Cross-ref:** [ESCALATE → TheFixer] — backend infrastructure task.

## QO-004: Traceability Enforcer Targets Wrong Spec — False PASSED Signal

- **Severity:** P2
- **Category:** architecture-violation
- **File:** `tools/traceability-enforcer.py`
- **Detail:** Running `python3 tools/traceability-enforcer.py` reports `TRACEABILITY PASSED: All requirements have implementation references.` — but it is scanning only `Plans/self-judging-workflow/requirements.md` (13 FRs, all correctly implemented). It does not scan the primary spec `Specifications/dev-workflow-platform.md` (69 unimplemented FRs) or `Plans/dependency-linking/requirements.md` (2 unimplemented FRs). The auto-discovery logic picks the most-recently-modified requirements file, which happens to be the one that passes.
