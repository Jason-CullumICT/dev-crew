## QO-001: Traceability Enforcer Has a Spec Blindspot (Scope Gap)

- **Severity:** P2
- **Category:** spec-drift
- **File:** `tools/traceability-enforcer.py` (default invocation)
- **Detail:** The verification gate `python3 tools/traceability-enforcer.py` auto-selects the most recently modified `requirements.md` — currently `Plans/self-judging-workflow/`. Running the gate against `Plans/dev-workflow-platform/requirements.md` reveals **34 missing requirement traces** (FR-001 through FR-032). These all come from the `dev-workflow-platform` plan which targets the portal layer, not Source/. However, there is no mechanism to confirm that assumption automatically — the enforcer simply never checks them. If anyone adds FR-001–032 code in Source/ without traces, the gate won't catch it.
- **Recommendation:** Either (a) document in `CLAUDE.md` and the enforcer's README that the platform spec lives in a separate layer and is explicitly excluded, or (b) add a `--exclude-plan` config option so multiple plans are checked in CI with the correct exclusions. At minimum, add a CI step that runs the enforcer against each known requirements.md and explicitly marks platform plans as out-of-scope.
- **Cross-ref:** TheFixer can implement the multi-plan check; requirements-reviewer can annotate platform specs.

## QO-004: Inline Type Definitions in Backend Services (Architecture Violation)

- **Severity:** P3
- **Category:** architecture-violation
- **File:** `Source/Backend/src/services/router.ts:60`, `Source/Backend/src/services/assessment.ts:141`
- **Detail:** CLAUDE.md architecture rule: "Shared types are single source of truth — no inline type re-definitions across layers." Two exported interfaces live in backend service files instead of `Source/Shared/types/`:
  - `RouteResult` (`router.ts:60`) — an exported interface crossing service boundaries
  - `AssessmentResult` (`assessment.ts:141`) — an exported interface with verdict/notes/suggestedChanges

  These are not currently imported by the frontend, so cross-layer drift isn't present yet. But exporting them from service files (rather than Shared/) violates the single-source principle and creates risk if the frontend ever needs them.
- **Recommendation:** Move `RouteResult` and `AssessmentResult` to `Source/Shared/types/workflow.ts`; update imports in backend. Frontend can then import from Shared without a backend dependency.
- **Cross-ref:** api-contract role.

## QO-005: Two eslint-disable Suppressions in Production Code

- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/components/DependencyPicker.tsx:82`, `Source/Frontend/src/hooks/useWorkItems.ts:63`
- **Detail:** Both files suppress `react-hooks/exhaustive-deps` with `// eslint-disable-next-line`. This is a lint bypass that hides potentially stale closure bugs. In `useWorkItems.ts`, the hook manually lists specific filter fields to avoid re-running on every render — a reasonable pattern, but the suppression masks the issue rather than solving it. In `DependencyPicker.tsx`, the debounce callback deps are suppressed.
- **Recommendation:** Replace the suppressions with explicit `useCallback`/`useMemo` dependency stabilization or document why the specific deps are intentionally excluded inline (e.g., `// stable ref — intentionally excluded`). If the suppression is truly needed, convert to a named `// eslint-disable-next-line react-hooks/exhaustive-deps -- reason: <specific explanation>`.
- **Cross-ref:** frontend-coder scope.
