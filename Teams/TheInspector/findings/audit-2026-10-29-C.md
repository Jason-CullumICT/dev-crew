## Findings

### QO-001: `pending_dependencies` status defined in api-contracts but absent from WorkItemStatus enum

- **Severity:** P1  
- **Category:** spec-drift  
- **File:** `Source/Shared/types/workflow.ts:5`  
- **Detail:** `Source/Shared/api-contracts.md` (lines 181–182) specifies a `pending_dependencies` status as a first-class WorkItem state: when a PATCH targets `approved` and unresolved blockers exist, the item silently becomes `pending_dependencies` instead. Additionally `BlockedBadge` is specified to render an amber badge for this state. However `WorkItemStatus` enum has no `PendingDependencies` value. The dispatch endpoint (workflow.ts:231) gates at the *dispatch* action instead of at the *approve* transition, returning HTTP 400 — contrary to the spec which requires a 200 with `status=pending_dependencies`. The approve action (workflow.ts:93) performs no blocker check at all.  
- **Failure scenario:** `POST /api/work-items/:id/approve` on an item with unresolved blockers succeeds and sets status=`approved`. Later `POST /api/work-items/:id/dispatch` returns 400 — surprising the caller who expected 200 with pending state, and breaking any UI that polls for auto-dispatch after approve.  
- **Recommendation:**  
  1. Add `PendingDependencies = 'pending_dependencies'` to `WorkItemStatus` enum  
  2. Add to `VALID_STATUS_TRANSITIONS`: `Approved → [InProgress, PendingDependencies]` and `PendingDependencies → [Approved]`  
  3. In `workflow.ts` approve handler — after transition succeeds, call `computeHasUnresolvedBlockers(id)`; if true, set status to `PendingDependencies` instead  
  4. In `dependency.ts` `onItemResolved` — cascade dependents from `PendingDependencies → Approved`, not directly to `InProgress`  
- **Cross-ref:** QO-003 (BlockedBadge amber state also affected)

### QO-002: `dependencyCheckDuration` histogram missing from metrics (3 of 4 FR-dependency-metrics implemented)

- **Severity:** P2  
- **Category:** spec-drift  
- **File:** `Source/Backend/src/metrics.ts:40`  
- **Detail:** `FR-dependency-metrics` specifies four Prometheus instruments: `dependencyOperations` counter ✅, `dispatchGatingEvents` counter ✅, `cycleDetectionEvents` counter ✅, and `dependencyCheckDuration` **histogram** ✗. The histogram is entirely absent — not defined, not exported, not incremented. The acceptance criterion explicitly names all four at `GET /metrics`.  
- **Failure scenario:** Running `GET /metrics` will not surface `dependency_check_duration_bucket` or `_count`/`_sum` lines. Alerting rules or SLO dashboards relying on dependency check latency have no data source.  
- **Recommendation:** Add a `Histogram` from `prom-client` for `dependency_check_duration_seconds` with label `operation` and instrument it around calls in `dependency.ts` that compute unresolved-blocker state (e.g. `computeHasUnresolvedBlockers`, `isReady`).

### QO-003: `BlockedBadge` missing amber state for `pending_dependencies` status

- **Severity:** P2  
- **Category:** spec-drift  
- **File:** `Source/Frontend/src/components/BlockedBadge.tsx:10`  
- **Detail:** `FR-dependency-blocked-badge` specifies: *red badge for `hasUnresolvedBlockers=true`; amber badge labelled "Pending Dependencies" when `status='pending_dependencies'`; renders nothing otherwise.* The implementation only accepts `hasUnresolvedBlockers?: boolean` — no `status` prop. The amber state path is entirely unimplemented and the component can never display it. Blocked by QO-001 (status doesn't exist in enum), but the component spec is independently unmet.  
- **Failure scenario:** When (after QO-001 fix) an item enters `pending_dependencies` state, the UI shows no badge — the user sees no visual indication that the item is waiting on blockers.  
- **Recommendation:** After QO-001 is resolved — add `status?: WorkItemStatus` prop to `BlockedBadgeProps`; render amber badge (`backgroundColor: '#f59e0b'`, label "Pending Dependencies") when `status === WorkItemStatus.PendingDependencies`; update all call sites in list/detail pages.

### QO-005: Traceability enforcer silently ignores multi-plan projects

- **Severity:** P2  
- **Category:** architecture-violation  
- **File:** `tools/traceability-enforcer.py:40`  
- **Detail:** The enforcer auto-selects the **most recently modified** `requirements.md` in `Plans/`. With two active plans (`self-judging-workflow` and `dependency-linking`), only one is checked per bare `python3 tools/traceability-enforcer.py` invocation. Any regression in `FR-dependency-*` traceability silently goes undetected. The CLAUDE.md verification gate (`python3 tools/traceability-enforcer.py`) will print "PASSED" even if all `FR-dependency-*` comments are removed from source.  
- **Failure scenario:** A coder removes a `// Verifies: FR-dependency-service` comment from `dependency.ts`. The gate passes because `self-judging-workflow/requirements.md` doesn't contain that FR ID. The gap is invisible until the next explicit `--plan dependency-linking` run.  
- **Recommendation:** Either: (a) update `CLAUDE.md` verification gate to run `python3 tools/traceability-enforcer.py --plan self-judging-workflow && python3 tools/traceability-enforcer.py --plan dependency-linking`, OR (b) extend the enforcer with a `--all` flag that iterates every `Plans/*/requirements.md` and reports coverage per plan with an aggregate exit code.

### QO-006: Duplicate frontend test files — maintenance ambiguity

- **Severity:** P3  
- **Category:** test-coverage  
- **File:** `Source/Frontend/tests/WorkItemDetailPage.test.tsx`  
- **Detail:** Two pairs of test files cover the same components:  
  - `Source/Frontend/tests/WorkItemDetailPage.test.tsx` ↔ `Source/Frontend/tests/pages/WorkItemDetailPage.test.tsx`  
  - `Source/Frontend/tests/WorkItemListPage.test.tsx` ↔ `Source/Frontend/tests/pages/WorkItemListPage.test.tsx`  
  Both files in each pair appear to run (neither is `*.skip`). The `pages/` variants import from `../../src/pages/...` (correct relative path) while the root variants import from `../src/pages/...` — both valid. There is no canonical owner and they may diverge independently.  
- **Failure scenario:** A developer fixes a test in the root copy not knowing the `pages/` copy also fails; CI appears green on one but the other accumulates stale assertions.  
- **Recommendation:** Delete the root `tests/WorkItemDetailPage.test.tsx` and `tests/WorkItemListPage.test.tsx` (they predate the `pages/` directory migration), keeping only the `pages/` variants which use the correct relative import paths.

### QO-007: OpenTelemetry absent from Source/Backend (CLAUDE.md architecture rule)

- **Severity:** P3  
- **Category:** architecture-violation  
- **File:** `Source/Backend/package.json`  
- **Detail:** CLAUDE.md mandates OpenTelemetry as a non-negotiable architecture rule: *"Add custom spans for critical paths; Propagate W3C `traceparent` header across service boundaries; Auto-inject trace/span IDs from OpenTelemetry where available."* No `@opentelemetry/*` packages appear in `Source/Backend/package.json`. No spans are created in any service. No `traceparent` header is propagated. The per-plan spec `FR-WF-013` only requires Prometheus metrics, which are implemented, but the project-wide rule goes further.  
- **Failure scenario:** Distributed trace waterfall is blind to all workflow engine operations. Debugging dispatch latency spikes or assessment pod timeouts requires log archaeology rather than trace-graph inspection.  
- **Recommendation:** Add `@opentelemetry/sdk-node`, `@opentelemetry/instrumentation-http`, `@opentelemetry/instrumentation-express` and initialize in `app.ts`. Add custom spans in `assessment.ts` pod orchestration, `router.ts` routing logic, and `dependency.ts` BFS cycle detection. Note: this is lower priority than P1/P2 findings.

### QO-008: `eslint-disable` suppressing `react-hooks/exhaustive-deps` without explanation

- **Severity:** P3  
- **Category:** pattern-violation  
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`  
- **Detail:** Two `// eslint-disable-next-line react-hooks/exhaustive-deps` comments exist in production source (`useWorkItems.ts:63`, `DependencyPicker.tsx:82`). These suppress a rule that detects stale closures in `useEffect`. Suppression without an inline rationale is technical debt — it cannot be distinguished from "intentional stable callback reference" vs "forgot to add dep and haven't noticed the bug yet."  
- **Failure scenario:** If the dependency array becomes stale due to a refactor, the effect won't re-run when it should, causing UI to show cached/wrong data without any lint warning.  
- **Recommendation:** Either (a) add a brief comment explaining the rationale (e.g., `// intentional: refreshKey acts as the single trigger; adding all filter fields would cause infinite loop`), OR (b) refactor to use `useCallback` to stabilize the dependency reference, enabling the lint rule to pass cleanly.
