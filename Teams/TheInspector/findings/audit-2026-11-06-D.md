## Findings

### QO-001: Routes bypass service layer — direct store access
- **Severity:** P1
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/routes/workflow.ts:15` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/workItems.ts:12` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/intake.ts:4` — `import * as store from '../store/workItemStore'`
- **Detail:** All three route modules call the store directly (`store.findById`, `store.update`, `store.create`, etc.) rather than delegating to the service layer. CLAUDE.md architecture rule: *"No direct DB calls from route handlers — use the service layer."* The in-memory store is the data layer; the same rule applies regardless of storage medium. `workflow.ts` additionally mixes direct store calls with service calls (`routeWorkItem`, `assessWorkItem`) in the same handler, creating split-brain logic.
- **Recommendation:** Create thin service wrappers for CRUD operations (`workItemService.ts`). Route handlers call services; services call the store. This decouples business logic from transport.
- **Cross-ref:** TheFixer for fix; TheATeam if planned work includes a service-layer refactor.

### QO-002: Traceability enforcer does not cover Specifications/
- **Severity:** P1
- **Category:** spec-drift
- **File:** `tools/traceability-enforcer.py:1`
- **Detail:** The enforcer auto-selects the most-recently-modified `Plans/*/requirements.md` and scans for `FR-WF-XXX` IDs. It has no knowledge of `Specifications/dev-workflow-platform.md` (85 FRs) or `Specifications/tiered-merge-pipeline.md` (10 FRs). Running the enforcer reports **PASSED** while 95 authoritative Specification requirements have zero implementation references. This creates a false-green gate: CI appears compliant while the domain specs are entirely untraced.
- **Recommendation:** Extend `traceability-enforcer.py` to also scan `Specifications/` for `FR-\d+` and `FR-TMP-\d+` IDs, then cross-reference against Source/. Add a `--specs` flag and update the CI gate. Alternatively, explicitly document that Specifications/ are aspirational/future-state and update CLAUDE.md to reflect the two-tier model (plan-level vs. domain-level traceability).
- **Cross-ref:** `Teams/TheInspector/inspector.config.yml` — `specs.dir: "Specifications/"` and `specs.patterns.traceability: "FR-\\d+"` are configured but the enforcer ignores them.

- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md:341` (FR-001 through FR-069 + FR-dependency-*)

Either way, Specifications/ must reflect reality.
- **Cross-ref:** TheATeam for implementation planning; requirements-reviewer for spec updates.

### QO-004: Duplicate logger modules — potential import confusion
- **Severity:** P2
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/utils/logger.ts` — primary structured logger implementation
  - `Source/Backend/src/logger.ts` — compatibility wrapper re-exporting from utils/logger
- **Detail:** Two logger files coexist. `src/logger.ts` exists because "backend-coder-2's workflow routes import `logger` as default from this module" (per file comment). This creates two valid import paths for the same logger. Future contributors may import from either, making it impossible to enforce consistent log structure. The QA report lists both under FR-WF-013 as intentional, but the design doc notes it as a workaround.
- **Recommendation:** Standardize on a single import path. Either: add a default export to `utils/logger.ts` and delete `src/logger.ts`; or move the canonical module to `src/logger.ts` and update `utils/logger.ts` to re-export from it. Update all imports across the codebase to use the canonical path.
- **Cross-ref:** TheFixer for cleanup.

### QO-005: `eslint-disable` suppresses exhaustive-deps warnings
- **Severity:** P2
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/hooks/useWorkItems.ts:63`
  - `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Both files suppress `react-hooks/exhaustive-deps` with `// eslint-disable-next-line`. This rule catches stale closure bugs in `useEffect`/`useCallback`. Disabling it without documented justification means effects may silently read stale dependency values, causing subtle UI correctness issues under re-renders. CLAUDE.md does not explicitly prohibit eslint-disable but the architecture rule against silent errors applies by analogy.
- **Recommendation:** For each suppression: either add a code comment explaining why the omitted dependency is intentional and safe, or refactor to satisfy the lint rule (e.g., use `useCallback` with stable references, extract the dependency, or use a ref). Do not leave bare eslint-disable with no rationale.
- **Cross-ref:** TheFixer.
