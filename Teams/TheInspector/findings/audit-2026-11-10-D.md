## Findings

### QO-001: Verification Gate Is a False Green
- **Severity:** P1
- **Category:** spec-drift / traceability
- **File:** `tools/traceability-enforcer.py` (gate config)
- **Detail:** The mandatory verification gate `python3 tools/traceability-enforcer.py` auto-discovers the most-recently-modified `requirements.md` from `Plans/` only. It never reads `Specifications/`. When run against `Specifications/dev-workflow-platform.md`, it reports 76/76 FRs missing (100% failure). Against `Specifications/tiered-merge-pipeline.md`, 13/13 missing. The gate shows green for every pipeline run while primary domain specs have 0% traceability coverage. Any team relying on the green gate for compliance confidence is operating on a false signal.
- **Recommendation:** Add a multi-spec mode to the enforcer: scan all `Specifications/**/*.md` as well as `Plans/**/requirements.md`. Gate must fail if any spec has FRs with zero source references. At minimum, add `--all-specs` flag and call it in the verification gate sequence.
- **Cross-ref:** TheFixer (enforcer fix), requirements-reviewer (spec ownership)

### QO-004: Architecture Violation — Routes Call Store Directly (3 Route Files)
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/routes/workItems.ts:12`, `Source/Backend/src/routes/workflow.ts:15`, `Source/Backend/src/routes/intake.ts:6`
- **Detail:** Three route handlers import and call `store.*` functions directly:
  - `workItems.ts`: `store.createWorkItem`, `store.findAll`, `store.findById`, `store.updateWorkItem`, `store.softDelete` (7 direct calls)
  - `workflow.ts`: `store.findById`, `store.updateWorkItem` (multiple calls on 7 routes)
  - `intake.ts`: `store.createWorkItem` (direct call)
  
  Architecture rule: "No direct DB calls from route handlers — use the service layer." The store IS the data layer. Only `dashboard.ts` correctly routes through a service (`dashboardService.*`). This pattern couples route handlers to the store implementation, makes testing harder, and violates the separation of concerns rule.
- **Recommendation:** Create service wrappers for work item CRUD operations (e.g., `workItemService.ts`) that the route handlers call. Move business logic (validation beyond input checking, metric increments) into the service layer. Route handlers should only parse HTTP input and delegate.
- **Cross-ref:** TheFixer (backend-coder)

### QO-005: OpenTelemetry Tracing Not Implemented
- **Severity:** P2
- **Category:** architecture-violation
- **File:** `Source/Backend/src/` (all files)
- **Detail:** The architecture rule mandates: "Use OpenTelemetry for distributed tracing. Auto-instrument HTTP, database, and framework calls. Add custom spans for critical paths. Propagate W3C `traceparent` header across service boundaries." A grep across all backend source files finds zero OTel imports, zero `traceparent` header handling, and zero custom spans. The spec also defines FR-021: "OpenTelemetry tracing: instrument HTTP routes and database calls; propagate W3C traceparent header." `LOG_LEVEL` env var handling exists but trace/span IDs do not appear in log output.
- **Recommendation:** Add `@opentelemetry/sdk-node`, `@opentelemetry/auto-instrumentations-node`, configure SDK in a `telemetry.ts` init module loaded before `app.ts`. Propagate `traceparent` via express middleware. Inject trace/span IDs into logger context.
- **Cross-ref:** TheFixer (backend-coder), [ESCALATE → TheGuardians if audit data is ever exposed externally]

### QO-006: Traceability Enforcer Regex Silently Drops Lowercase FR IDs
- **Severity:** P3
- **Category:** spec-drift / traceability
- **File:** `tools/traceability-enforcer.py:68`
- **Detail:** The enforcer uses `re.compile(r"FR-[A-Z0-9-]+")` which only matches uppercase alphabetic characters after `FR-`. This means IDs like `FR-dependency-service`, `FR-dependency-endpoints`, `FR-dependency-dispatch-gating`, `FR-dependency-blocked-badge`, `FR-dependency-picker`, `FR-dependency-section`, `FR-dependency-api-client`, `FR-dependency-metrics` (all lowercase) are **never** extracted from `Plans/dependency-linking/requirements.md` and **never** checked in source. Running the enforcer against that plan reports `FR-0002, FR-0003, ...` as missing while silently ignoring the 15 `FR-dependency-*` IDs. The code has correct `// Verifies: FR-dependency-*` comments but the gate can never verify them.
- **Recommendation:** Change regex to `r"FR-[A-Za-z0-9-]+"` (add lowercase `a-z`). Validate by running against `Plans/dependency-linking/requirements.md` — should now show the FR-dependency-* IDs.
- **Cross-ref:** TheFixer (tools/traceability-enforcer.py fix)

### QO-007: `eslint-disable` Suppressions Without Documented Rationale
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/hooks/useWorkItems.ts:63`, `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Both files suppress `react-hooks/exhaustive-deps` with no explanatory comment:
  ```ts
  // eslint-disable-next-line react-hooks/exhaustive-deps
  ```
  Architecture rule: "Never swallow errors silently — every catch block must either re-throw, log with full context, or **explicitly document why the error is intentionally suppressed**." The same principle applies to lint suppressions — a suppression without rationale is an undocumented deviation. Missing deps in hooks can cause stale closures.
- **Recommendation:** Add an inline comment explaining why the dep(s) are intentionally omitted, e.g., `// eslint-disable-next-line react-hooks/exhaustive-deps -- intentionally excludes `filters` to avoid re-fetch loop`. Or fix the hook to include the deps correctly.
- **Cross-ref:** TheFixer (frontend-coder)

### QO-008: Hardcoded `localhost` URL in Frontend Production Code
- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/pages/DebugPortalPage.tsx:5`
- **Detail:**
  ```ts
  const portalUrl = import.meta.env.VITE_PORTAL_URL || 'http://localhost:4200';
  ```
  While the env var takes precedence, the hardcoded fallback `http://localhost:4200` means any deployment without `VITE_PORTAL_URL` set will silently serve a broken iframe pointing at localhost. Architecture rule: "No hardcoded secrets -- use environment variables via .env." The spirit of the rule covers hardcoded infra URLs too — the app should fail visibly or surface an empty state rather than point to a non-existent local address.
- **Recommendation:** Remove the localhost fallback. If the portal URL is missing, render an informational message: `"Portal URL not configured (VITE_PORTAL_URL)"` rather than a broken iframe.
- **Cross-ref:** TheFixer (frontend-coder)
