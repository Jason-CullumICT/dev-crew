## QO-001: Architecture Violation — Route Handlers Bypass the Service Layer

- **Severity:** P1
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/routes/workflow.ts` (12 direct store calls: lines 44, 71, 99, 119, 155, 175, 217, 269, 317, 359, and more)
  - `Source/Backend/src/routes/workItems.ts` (6 direct store calls: lines 44, 73, 79, 89, 134, and more)
  - `Source/Backend/src/routes/intake.ts` (2 direct store calls: lines 19, 42)
- **Detail:** All three route modules directly `import * as store from '../store/workItemStore'` and invoke store functions (findById, createWorkItem, updateWorkItem, findAll) inside request handlers. CLAUDE.md states this is non-negotiable: *"No direct DB calls from route handlers — use the service layer."* The in-memory store is the DB-equivalent in this architecture. Business logic (status transitions, field validation, change history) is currently split between routes and services, making routes hard to test in isolation and coupling HTTP concerns to persistence.
- **Recommendation:** Create thin service wrappers (`WorkItemService`) that the routes call. Move all store access into service functions. Routes should only do: request parsing, service call, response formatting. The existing `services/` directory already has `dashboard.ts`, `assessment.ts`, `router.ts`, `dependency.ts` — follow that pattern.
- **Cross-ref:** TheFixer should own this refactor; each route module already has test coverage so regression risk is managed.

## QO-003: Primary Domain Specification Describes an Application That Isn't Built in Source/

- **Severity:** P2
- **Category:** spec-drift
- **File:** `Specifications/dev-workflow-platform.md` (FR-001 to FR-069, lines 341–405+)
- **Detail:** `dev-workflow-platform.md` defines a full platform with SQLite database, `FeatureRequest`, `BugReport`, `DevelopmentCycle`, `Ticket` entities, and 7 subsystems (Intake → AI Voting → Human Approval → Backlog → Dev Cycle → CI/CD → Documentation). None of these entities or routes exist in `Source/`. `Source/` implements a WorkItem-based in-memory workflow engine with a completely different data model and status state machine. Zero Verifies: comments in Source/ trace to FR-001 through FR-069. CLAUDE.md's foremost rule: *"Specs are source of truth — implementation traces to specs, never the other way around."* Here, the inverse happened: a new application was built against a fresh plan (self-judging-workflow) while the primary domain spec was left unchanged.
- **Recommendation:** Update `Specifications/dev-workflow-platform.md` to reflect what is actually built in `Source/` — or create a new authoritative spec document for the WorkItem-based engine and mark `dev-workflow-platform.md` as the spec for the portal project (archived/external). This is the most urgent documentation debt in the repo.
- **Cross-ref:** Requires requirements-reviewer to own the spec update; solo-session coordination.

## QO-006: ESLint exhaustive-deps Suppressions Without Explanation

- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Both suppressions silence the `react-hooks/exhaustive-deps` rule with no accompanying comment explaining why. This rule exists to prevent stale closures where callbacks reference outdated state/props. Without an explanation, reviewers cannot evaluate whether the suppression is intentional and safe, or an oversight.
- **Recommendation:** Add a one-line comment explaining the intentional omission: e.g. `// intentionally omit fetchFn from deps — it's stable but would cause infinite re-fetch`. If the dep truly should be included, add it and test.
- **Cross-ref:** TheFixer low-priority.

## QO-007: Hardcoded localhost:4200 Portal URL in DebugPortalPage

- **Severity:** P3
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/pages/DebugPortalPage.tsx:5`
- **Detail:** `const portalUrl = import.meta.env.VITE_PORTAL_URL || 'http://localhost:4200';` — The env var fallback is correct practice, but `localhost:4200` as the production default will silently render a broken iframe in any deployed environment. If `VITE_PORTAL_URL` is not set at build time, the iframe points nowhere useful.
- **Recommendation:** Either (a) make `VITE_PORTAL_URL` required with a build-time error if absent, or (b) show a placeholder/disabled state when the URL is a localhost default in non-local environments. Document `VITE_PORTAL_URL` in `.env.example`.
