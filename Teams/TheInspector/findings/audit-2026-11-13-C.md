## Findings

### QO-001: Traceability Enforcer Defaults to Single Plan — 7 of 8 Plans Never Checked
- **Severity:** P1
- **Category:** spec-drift / tool-gap
- **File:** `tools/traceability-enforcer.py` (line 46 — `max(req_files, key=os.path.getmtime)`)
- **Detail:** The CLAUDE.md verification gate runs `python3 tools/traceability-enforcer.py` with no arguments. The enforcer then picks the **most recently modified** `requirements.md` in `Plans/` — currently `self-judging-workflow`. This means 7 other plans are silently skipped every CI/gate run. Five of those plans have `## Verdict: APPROVED` and have requirements that exist in `Plans/` but have zero `// Verifies:` coverage:
  - `dev-cycle-traceability`: FR-068, FR-069 missing
  - `duplicate-deprecated-status`: FR-DUP-11, FR-DUP-12, FR-DUP-13 missing
  - `orchestrated-dev-cycles`: FR-048, FR-049 missing
  - `orchestrator-cycle-dashboard`: FR-075, FR-076 missing
  - `image-upload`: FR-070, FR-071+ missing
- **Recommendation:** Change the enforcer default from "most recently modified" to "all plans" mode, or add a `--all` flag and invoke it in the verification gate. Alternatively, maintain a manifest of active plans in `inspector.config.yml` under `specs.active_plans` and enforce all listed plans.
- **Cross-ref:** TheFixer (enforcer fix is a tools/ change, solo-session owned)

### QO-002: `Specifications/` Directory Has Zero Traceability Enforcement
- **Severity:** P1
- **Category:** spec-drift / architecture-violation
- **File:** `Specifications/dev-workflow-platform.md` (77 unique FR-001 … FR-069+ IDs)
- **Detail:** CLAUDE.md declares: *"Specifications/ — Domain truth. The most critical documents."* and *"Specs are source of truth — implementation traces to specs, never the other way around."* Yet the traceability enforcer only scans `Plans/`, never `Specifications/`. The main spec (`dev-workflow-platform.md`) contains 77 unique functional requirements (FR-001 to FR-069+) with zero corresponding `// Verifies:` comments anywhere in `Source/`.

  **Root cause ambiguity:** The current `Source/` implements the **Self-Judging Workflow Engine** (in-memory store, work items, assessments), which matches `Specifications/workflow-engine.md` and `Plans/self-judging-workflow/`. The `dev-workflow-platform.md` spec describes a **different product** (feature request tracking with SQLite, development cycles, bug reports). This creates two possible interpretations:
  1. The project pivoted — `dev-workflow-platform.md` is an *abandoned* spec that was never marked obsolete.
  2. The project intends to implement both — the workflow engine is live, the platform spec is a roadmap.

  Either way, the enforcement gap means there is no automated signal of which interpretation is correct or when the platform spec requirements become stale.
- **Recommendation:** Classify each spec file with a status (`active | superseded | roadmap`). Extend the enforcer to scan `Specifications/` for active specs. Mark `dev-workflow-platform.md` as `superseded` or `roadmap` to eliminate the ambiguity.
- **Cross-ref:** requirements-reviewer (spec classification), TheFixer (enforcer extension)

### QO-003: Route Handlers Import Directly from Store — Architecture Violation
- **Severity:** P2
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/routes/workflow.ts:15` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/intake.ts:4` — `import * as store from '../store/workItemStore'`
  - `Source/Backend/src/routes/workItems.ts:12` — `import * as store from '../store/workItemStore'`
- **Detail:** Architecture rule: *"No direct DB calls from route handlers — use the service layer."* All three route files bypass the service layer and call store functions directly (e.g., `store.createWorkItem()`, `store.findAll()`, `store.findById()`). The store is the in-memory persistence layer — equivalent to the DB tier. Direct access from routes couples routing logic to storage implementation, making the store difficult to swap or mock, and scatters business logic across the routing layer.
- **Recommendation:** Introduce a `workItemService.ts` and `intakeService.ts` facade. Route handlers call service functions; services call store functions. This matches the pattern already used for `assessment.ts`, `router.ts`, `changeHistory.ts`, and `dependency.ts`.
- **Cross-ref:** TheFixer (backend-coder)

### QO-004: Silent Error Swallowing in Frontend API Client
- **Severity:** P2
- **Category:** pattern-violation
- **File:** `Source/Frontend/src/api/client.ts:26`
- **Detail:** `const body = await response.json().catch(() => ({}));` — the `.catch(() => ({}))` callback swallows JSON parse errors silently, returning an empty object when the parse fails. Architecture rule: *"Never swallow errors silently — every catch block must either re-throw, log with full context, or explicitly document why the error is intentionally suppressed."* When a server returns malformed JSON (or a non-JSON response like a 502 HTML error page), this code silently returns `{}`, which then propagates as a fake-success response to the caller.
- **Recommendation:** Log the parse failure and re-throw, or add a comment documenting the intentional suppression: e.g., `// Intentionally silent: non-JSON responses (e.g., 502 HTML) return empty body; caller handles via response.ok check`.
- **Cross-ref:** TheFixer (frontend-coder)

### QO-005: Traceability Enforcer Extracts IDs from Prose — False Positives
- **Severity:** P2
- **Category:** tool-correctness
- **File:** `tools/traceability-enforcer.py:60` — `pattern = re.compile(r"FR-[A-Z0-9-]+")`
- **Detail:** The enforcer extracts ALL strings matching `FR-[A-Z0-9-]+` from requirements files, including IDs mentioned in **prose descriptions** and **data examples**. `Plans/dependency-linking/requirements.md` mentions `FR-0002`, `FR-0003`, `FR-0004`, `FR-0005`, `FR-0007` as seed-data item IDs inside a table cell description — not as requirement IDs. The enforcer treats these as requirements and reports them missing. Similarly, placeholder text `FR-XXX`, `FR-XXXX`, `FR-0XX` in unfinished requirements templates is extracted and reported as missing.

  Consequence: teams learn to ignore enforcer failures ("those FR-000X failures are always false positives"), which erodes trust and means real gaps are missed.
- **Recommendation:** Restrict extraction to rows where the ID appears in the **first column of a Markdown table** (pipe-delimited row starting with `| FR-`), not in arbitrary prose. Example: `re.findall(r'^\|\s*(FR-[A-Z0-9-]+)\s*\|', content, re.MULTILINE)`. Also skip IDs matching the template placeholder pattern `FR-X+`.
- **Cross-ref:** TheFixer (tools/ — solo-session owned)

### QO-006: OpenTelemetry Tracing Not Implemented
- **Severity:** P3
- **Category:** architecture-violation / spec-drift
- **File:** `Source/Backend/` (no `@opentelemetry/*` imports found anywhere)
- **Detail:** CLAUDE.md architecture rule: *"Use OpenTelemetry for distributed tracing; Auto-instrument HTTP, database, and framework calls; Add custom spans for critical paths; Propagate W3C `traceparent` header across service boundaries."* `FR-WF-013` covers structured logging and Prometheus metrics (both implemented), but OTel tracing is not. No `@opentelemetry/sdk-node`, `@opentelemetry/auto-instrumentations-node`, or traceparent header propagation exists in source.
- **Recommendation:** Add OTel SDK initialization in `Source/Backend/src/app.ts`, auto-instrument HTTP routes and service calls, propagate `traceparent` via Express middleware. This is a P3 (not P1) because logging and metrics are present and the system is functional.
- **Cross-ref:** TheFixer (backend-coder), [ESCALATE → TheGuardians] if sensitive operations are added without tracing

### QO-007: `eslint-disable-next-line` in React Hooks
- **Severity:** P3
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/hooks/useWorkItems.ts:63`
  - `Source/Frontend/src/components/DependencyPicker.tsx:82`
- **Detail:** Both files silence `react-hooks/exhaustive-deps` with `// eslint-disable-next-line`. This rule catches missing effect dependencies that cause stale closures. Disabling it without explanation is a code smell — the dependency is either genuinely stable (should be documented) or missing (should be fixed).
- **Recommendation:** Either add the missing dependency to the array, or if the omission is intentional, add a comment explaining why (e.g., `// omitting fetchItems — intentionally only runs on mount`).
- **Cross-ref:** TheFixer (frontend-coder)
