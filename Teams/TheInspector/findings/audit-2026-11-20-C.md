## QO-001: `GET /api/search` not registered — DependencyPicker search is broken
- **Severity:** P1
- **Category:** spec-drift / unimplemented
- **Files:**
  - `Source/Backend/src/app.ts` (route never registered)
  - `Source/Frontend/src/api/client.ts:103` (calls `/api/search`)
  - `Source/Frontend/src/components/DependencyPicker.tsx:54` (calls `searchItems()`)
  - `Source/Backend/tests/routes/search.test.ts:1-6` (documents the gap explicitly)
- **Detail:** `FR-dependency-search` requires `GET /api/search?q=` for cross-entity typeahead used by the DependencyPicker modal. The route handler logic exists (tested in `search.test.ts`), but is **never mounted** in `app.ts`. The search test file itself carries a note: *"As of this review cycle the GET /api/search endpoint is NOT wired into Source/Backend/src/app.ts. These tests document the expected contract and will FAIL until the route is implemented."* The frontend client calls `request('/search?q=...')` → resolves to `GET /api/search?q=` → returns 404 in production.
- **Failure scenario:** User opens DependencyPicker and types a search query. `GET /api/search?q=auth` returns HTTP 404 (falls through to Express 404 handler). Typeahead shows no results. No error is surfaced to the user. Dependencies cannot be discovered or added via search.
- **Recommendation:** Add a `searchRouter` in `Source/Backend/src/routes/` that handles `GET /` using the existing `workItemStore.findAll` with a text filter, then mount it: `app.use('/api/search', searchRouter)`. The test contract in `search.test.ts` defines the expected behavior.
- **Cross-ref:** TheFixer for implementation; `FR-dependency-search` is the controlling spec requirement.

## QO-002: Traceability enforcer blind to 69 Specification FRs — systemic gap
- **Severity:** P1
- **Category:** spec-drift / traceability
- **File:** `tools/traceability-enforcer.py` (enforcer scope), `Specifications/dev-workflow-platform.md` (unverified FRs)
- **Detail:** `tools/traceability-enforcer.py` auto-detects the most recently modified `requirements.md` in `Plans/` and enforces only those IDs. It currently targets `Plans/self-judging-workflow/requirements.md` with 13 FR-WF-* IDs, all of which pass. However, the governing Specification (`Specifications/dev-workflow-platform.md`) contains **69 numeric FRs (FR-001 to FR-069)** — none of which appear in any `// Verifies:` comment in `Source/`. The CLAUDE.md mandate states: *"Every FR needs a test with `// Verifies: FR-XXX` traceability comments"* — this is unfulfilled for the entire Specification layer.

  The implementation team correctly traced to Plan-level IDs (FR-WF-XXX) which are a narrower scope derived from the Specifications. But the chain from Specifications → Plans → Source is broken: there is no mapping from FR-001..FR-069 to FR-WF-001..FR-WF-013, and the enforcer never checks the Specification FRs.

- **Failure scenario:** `python3 tools/traceability-enforcer.py` reports `TRACEABILITY PASSED` with 13/13. An auditor or CI gate concludes that all requirements are covered. In reality, FR-002 (backend schema migrations), FR-021 (OpenTelemetry tracing), FR-035 (pipeline_runs tables), FR-048 (pipeline backend tests) and 65 other Specification FRs have zero verifiable implementation evidence.
- **Recommendation (two-part):**
  1. **Short term:** Add a second enforcement pass in `traceability-enforcer.py` that also scans `Specifications/` for FR IDs and verifies they appear in `Source/` (or in a cross-reference map file). Flag as failure if any Specification FR has zero source references.
  2. **Long term:** Add a `Plans/*/requirements-crossref.md` that explicitly maps each Plan FR (FR-WF-XXX) to its parent Specification FR (FR-XXX). The enforcer can then validate the full chain transitively.
- **Cross-ref:** TheATeam for the mapping doc; requirements-reviewer for Specification alignment.

## QO-003: Duplicate test files for WorkItemDetailPage and WorkItemListPage
- **Severity:** P2
- **Category:** test-coverage / architecture-violation
- **Files:**
  - `Source/Frontend/tests/WorkItemDetailPage.test.tsx` (368 lines, older)
  - `Source/Frontend/tests/pages/WorkItemDetailPage.test.tsx` (393 lines, newer — more comprehensive)
  - `Source/Frontend/tests/WorkItemListPage.test.tsx` (286 lines, older)
  - `Source/Frontend/tests/pages/WorkItemListPage.test.tsx` (262 lines, newer)
- **Detail:** Both versions test the same components with overlapping `// Verifies: FR-WF-010` and `// Verifies: FR-WF-011` traceability. The `pages/` subdirectory versions are newer, have more test cases (WorkItemDetailPage: 393 vs 368 lines), and appear to be the authoritative set. The root-level versions were not removed when the `pages/` versions were added. Vitest's default glob picks up both; every test run executes duplicate coverage, and any divergence between the two files will produce confusing false signals.
- **Failure scenario:** A developer adds a regression test to `tests/pages/WorkItemDetailPage.test.tsx` to cover a bug fix. The older `tests/WorkItemDetailPage.test.tsx` does not cover the same edge case. CI sees all tests green (the new test passes). The root-level file never gets updated. Future refactors break only the new test; reviewers are confused by why coverage dropped.
- **Recommendation:** Decide which is authoritative (likely `tests/pages/`), then remove the root-level duplicates `tests/WorkItemDetailPage.test.tsx` and `tests/WorkItemListPage.test.tsx`. Verify test count is unchanged after removal.
- **Cross-ref:** TheFixer for cleanup.

## QO-004: `eslint-disable` in production code without justification
- **Severity:** P2
- **Category:** pattern-violation
- **Files:**
  - `Source/Frontend/src/hooks/useWorkItems.ts:63` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
  - `Source/Frontend/src/components/DependencyPicker.tsx:82` — `// eslint-disable-next-line react-hooks/exhaustive-deps`
- **Detail:** Both suppressions disable the `react-hooks/exhaustive-deps` rule with no inline explanation of why the dependency is intentionally omitted. Architecture rules require that every disabled lint rule be explicitly documented. Without a comment, the next developer cannot distinguish between "intentionally omitted to avoid an infinite re-render loop" and "lazily suppressed to make CI pass." Missing deps in `useEffect` can mask stale-closure bugs.
- **Failure scenario:** A developer adds a new state variable used in the effect in `useWorkItems.ts` but doesn't add it to the dependency array (because the eslint rule is already suppressed and they don't know why). The hook reads a stale value silently.
- **Recommendation:** Add an inline comment explaining why the dep is omitted, e.g.:
  ```ts
  // eslint-disable-next-line react-hooks/exhaustive-deps
  // `fetch` is intentionally omitted — it is a stable function reference and
  // including it would trigger an infinite fetch loop on every render.
  ```
- **Cross-ref:** TheFixer for documentation.

## QO-005: Logger abstraction duplicated across two modules
- **Severity:** P3
- **Category:** architecture-violation
- **Files:**
  - `Source/Backend/src/utils/logger.ts` (string-based interface, original)
  - `Source/Backend/src/logger.ts` (wrapper for object-based compat, re-exports)
- **Detail:** Two logger implementations exist. Routes written by backend-coder-2 import from `src/logger.ts` (object API: `logger.info({ msg: '...' })`). The underlying implementation in `utils/logger.ts` uses a string-based API. The `src/logger.ts` wrapper normalizes between them. While functional, this violates the "single source of truth for shared types" rule and adds an unnecessary indirection layer. Future contributors will not know which to import without reading both files.
- **Failure scenario:** A new backend service imports from `utils/logger` directly (bypassing the wrapper). It calls `logger.info('some message', ctx)` — this works. Then it also uses object-style `logger.info({ msg: 'x' })` — this fails at runtime since `utils/logger` doesn't handle object args, but TypeScript doesn't catch it because both are `string | Record<string, unknown>`. Logs are silently dropped or malformed.
- **Recommendation:** Consolidate to a single logger module. Either update `utils/logger.ts` to accept both calling conventions, or delete it and have `src/logger.ts` be the canonical module. Update all imports.
