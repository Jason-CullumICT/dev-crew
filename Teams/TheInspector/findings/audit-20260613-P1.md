## Critical Findings (P1)

### DEP-001: Handlebars.js JavaScript Injection via AST Type Confusion
- **Severity:** P1 / CRITICAL
- **Category:** CVE / Code Injection
- **Package:** handlebars
- **Affected Version:** >=4.0.0 <=4.7.8
- **Files:** 
  - Source/Backend/package-lock.json (transitive)
- **CVE IDs:**
  - GHSA-2w6w-674q-4c4q (CRITICAL, CVSS 9.8)
  - GHSA-3mfm-83xf-c92r (HIGH, CVSS 8.1)
  - GHSA-xhpv-hc6g-r9c6 (HIGH, CVSS 8.1)
  - GHSA-9cx6-37pm-9jff (HIGH, CVSS 7.5)
  - Plus 4 additional CVEs
- **Detail:** 
  Handlebars.js versions 4.0.0 through 4.7.8 are vulnerable to arbitrary JavaScript code execution through AST type confusion. An attacker can:
  - Inject malicious code via @partial-block tampering
  - Execute arbitrary JavaScript via dynamic partial parameters
  - Cause denial-of-service via malformed decorator syntax
  - Bypass prototype access controls
  
  This affects any code that processes untrusted handlebars templates.

- **Fix:** 
  ```bash
  npm update handlebars@latest
  ```
  Requires upgrading to handlebars >= 4.7.9

- **Cross-ref:** 
  - [ESCALATE → TheGuardians] - Template injection is a critical code injection vector
  - May be exploitable if the application processes user-supplied templates
  - Check if Handlebars is used for email templating or dynamic content generation

### DEP-002: Protobufjs Arbitrary Code Execution
- **Severity:** P1 / CRITICAL
- **Category:** CVE / Code Injection
- **Package:** protobufjs
- **Affected Version:** <=7.5.5
- **Files:**
  - platform/orchestrator/package-lock.json (transitive)
  - portal/Backend/package-lock.json (transitive)
- **CVE IDs:**
  - GHSA-xq3m-2v4x-88gg (CRITICAL, CVSS 9.8)
  - GHSA-75px-5xx7-5xc7 (HIGH, CVSS 8.1)
  - Plus 6 additional CVEs
- **Detail:**
  Protobufjs <=7.5.5 contains multiple critical vulnerabilities:
  1. Arbitrary code execution through .proto descriptor loading
  2. Prototype pollution leading to code generation gadgets
  3. Process-wide DoS via unsafe option paths
  4. Unbounded recursion in JSON descriptor expansion
  
  Risk is high if the application:
  - Loads .proto files from untrusted sources
  - Processes user-supplied protobuf messages
  - Uses generated toObject() methods on untrusted data

- **Fix:**
  ```bash
  npm update protobufjs@latest
  ```
  Requires upgrading to protobufjs >= 7.5.8

- **Cross-ref:**
  - [ESCALATE → TheGuardians] - Code execution via deserialization
  - Used by gRPC dependencies, which are network-facing in orchestrator/portal
  - Verify all .proto files are from trusted sources

### DEP-003: Vitest Arbitrary File Read/Execution
- **Severity:** P1 / CRITICAL
- **Category:** CVE / Information Disclosure + Code Execution
- **Package:** vitest
- **Affected Version:** <3.2.6 (affects 2.0.5+ in Source/Frontend, portal/Frontend)
- **Files:**
  - Source/Frontend/package-lock.json (direct dev dependency: vitest ^2.0.5)
  - portal/Frontend/package-lock.json (direct dev dependency)
- **CVE ID:** GHSA-5xrq-8626-4rwp (CRITICAL, CVSS 9.8)
- **Detail:**
  When Vitest UI server is enabled (via `vitest --ui` or in test runner config), an unauthenticated attacker can:
  - Read arbitrary files from the filesystem
  - Execute arbitrary code via file read endpoints
  - Escape the sandbox and compromise the developer machine
  
  **Context:** This is a dev-only vulnerability but affects:
  - Local development machines
  - CI/CD pipelines that run Vitest UI
  - Any environment where Vitest server listens on 0.0.0.0 or externally accessible network

- **Fix:**
  ```bash
  npm update vitest@latest
  ```
  Requires upgrading to vitest >= 3.2.6
  
  **Immediate mitigation:** Disable Vitest UI in production/CI, ensure it only binds to 127.0.0.1

- **Cross-ref:**
  - [ESCALATE → TheGuardians] - File read + code execution in dev tooling
  - Check CI/CD configuration for Vitest UI exposure
  - Verify no test servers exposed to network in CI

## High-Severity Findings (P2)

### DEP-004: esbuild Remote Code Execution (Supply Chain)
- **Severity:** P2 / HIGH
- **Category:** CVE / Supply Chain
- **Package:** esbuild
- **Affected Version:** >=0.17.0 <0.28.1
- **Files:**
  - Source/Frontend/package-lock.json (transitive via vite)
  - portal/Frontend/package-lock.json (transitive via vite)
  - portal/Backend/package-lock.json (transitive via multiple deps)
- **CVE ID:** GHSA-gv7w-rqvm-qjhr (HIGH, CVSS 8.1)
- **Detail:**
  esbuild Deno module is missing binary integrity verification. An attacker can:
  - Intercept the npm registry fetch via `NPM_CONFIG_REGISTRY`
  - Serve malicious esbuild binary during `npm install`
  - Execute arbitrary code with npm's privileges
  
  This is a supply chain attack during dependency installation.

- **Fix:**
  ```bash
  npm update esbuild@latest
  ```
  Ensure vite and related deps are also updated (vite >= 5.0.0 or current latest)

- **Risk Level:** Moderate if CI/CD is on untrusted networks, High if developers use public WiFi

- **Category:** CVE / Denial of Service
